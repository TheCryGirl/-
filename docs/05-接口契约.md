## 一、总体约定

### 1.1 服务与端口

| 服务 | 端口 | 职责 | 负责人 |
| --- | --- | --- | --- |
| gateway | 9000 | 统一入口、路由、鉴权过滤 | 哭女 |
| user-service | 9001 | 用户、地址、认证 | 来财 |
| product-service | 9002 | 商品、SKU、库存 | yy |
| cart-service | 9003 | 购物车 | fd |
| order-service | 9004 | 订单、状态机 | yy |
| payment-service | 9005 | 支付、回调、退款 | 韬哥 |

前端只访问网关 `http://localhost:9000`，**不直连任何服务**。

### 1.2 路径规则

- 网关对外：`/api/<服务名>/<资源>`，例如 `/api/orders/123`
- 服务内部：不带 `/api` 前缀，例如 order-service 自身监听 `/orders/123`
- 内部服务间调用走 `FeignClient`，不经过网关

### 1.3 统一响应结构

**所有接口**返回这个结构，HTTP 状态码只用于表达协议层结果（200 / 401 / 403 / 500），业务成功与否看 `code`。

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1761000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | int | 0 成功，非 0 失败 |
| message | string | 出错时给用户看的中文提示 |
| data | object | 业务数据，失败时为 null |
| timestamp | long | 服务器毫秒时间戳，用于排查 |

### 1.4 错误码

错误码统一 5 位，前两位表示服务归属。**前端按码分支处理，不解析 message 文本。**

| 错误码 | 含义 | 归属 |
| --- | --- | --- |
| 0 | 成功 | 全局 |
| 10001 | 参数校验失败 | 全局 |
| 10002 | 未登录或令牌无效 | 全局 |
| 10003 | 无权限执行该操作 | 全局 |
| 10004 | 请求过于频繁 | 全局 |
| 20001 | 账号或密码错误 | user |
| 20002 | 账号已存在 | user |
| 20003 | 昵称已被占用 | user |
| 20004 | 账号已被冻结 | user |
| 20005 | 用户不存在 | user |
| 30001 | 商品不存在 | product |
| 30002 | 商品已下架 | product |
| 30003 | 库存不足 | product |
| 30004 | 预占记录不存在 | product |
| 30005 | 规格组合冲突 | product |
| 40001 | 购物车条目不存在 | cart |
| 40002 | 数量超出可售库存 | cart |
| 50001 | 订单不存在 | order |
| 50002 | 幂等令牌重复提交 | order |
| 50003 | 订单状态不允许该操作 | order |
| 50004 | 订单已超时 | order |
| 60001 | 支付单不存在 | payment |
| 60002 | 回调验签失败 | payment |
| 60003 | 回调金额不一致 | payment |
| 60004 | 退款金额超出实付 | payment |

### 1.5 认证

- 登录成功后签发 JWT，前端存放在 `localStorage.token`
- 除白名单接口外，所有请求带 `Authorization: Bearer <token>`
- JWT payload：`{ "userId": "U001", "role": "BUYER", "exp": 1761000000 }`
- **网关统一校验**，校验通过后把 `userId` 放进请求头 `X-User-Id` 传给下游服务；下游服务**不再重复解析 JWT**

**白名单**（无需令牌）：

```
POST /api/users/register
POST /api/users/login
GET  /api/products/**
GET  /api/categories/**
```

### 1.6 分页

请求：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| page | int | 1 | 从 1 开始 |
| size | int | 20 | 每页条数，上限 100 |

响应 `data`：

```json
{
  "page": 1,
  "size": 20,
  "total": 137,
  "pages": 7,
  "list": []
}
```

### 1.7 时间与金额

| 项 | 约定 |
| --- | --- |
| 时间 | `yyyy-MM-dd HH:mm:ss`，统一北京时间 |
| 金额 | **分为单位的整数**（`long`），避免浮点误差。`10050` 表示 100.50 元 |
| ID | 字符串（`String`），不用自增数字，防止被枚举 |

> 金额用整数的原因见 BR-04「价格精确到分」。前端展示时除以 100，不要在传输层用小数。

### 1.8 幂等

涉及创建订单、支付这类可能重复提交的接口，必须在请求头带：

```
Idempotency-Key: <UUID>
```

由前端每次提交时生成。服务端按 key 去重，重复请求返回首次的结果（不报错，返回同样内容）。

### 3.5 库存预占 —— **本项目最关键的一组接口**

#### POST /api/products/skus/reserve

由 order-service 在下单时调用。

请求：

```json
{
  "orderId": "O50001",
  "expireAt": "2026-10-20 21:30:00",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

响应 `data`：

```json
{
  "reservationId": "R60001",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

**实现要求**：

```sql
-- 每个 SKU 一条，先到先得；任一条失败则回滚整批
UPDATE sku
SET stock_locked = stock_locked + #{quantity},
    stock_available = stock_available - #{quantity},
    version = version + 1
WHERE sku_id = #{skuId}
  AND stock_available >= #{quantity};
```

**影响行数为 0 表示库存不足**，返回 `30003`，调用方必须整体回滚（BR-15 不得留下半成品订单）。

**幂等要求**：同一 `orderId` 重复调用，返回首次的 `reservationId`，不重复扣减（利用 `orderId` 唯一索引）。

#### POST /api/products/skus/release

订单超时取消或买家主动取消时调用。

请求：

```json
{ "orderId": "O50001" }
```

响应 `data`：`{ "released": true }`

**实现要求**：

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    s.stock_available = s.stock_available + r.quantity,
    r.status = 'RELEASED'
WHERE r.status = 'LOCKED';
```

> BR-17：释放必须幂等，重复调用不得重复回补。靠 `r.status = 'LOCKED'` 这个条件保证，已释放的不会再匹配。

#### POST /api/products/skus/confirm

支付回调成功后调用，把预占转为真实扣减。

请求：`{ "orderId": "O50001" }`

响应 `data`：`{ "confirmed": true }`

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    r.status = 'CONFIRMED'
WHERE r.status = 'LOCKED';
```

## 五、order-service / 订单服务

### 5.1 订单状态机

```
        ┌──────────┐
        │ 待支付   │ PENDING_PAYMENT
        └────┬─────┘
             │ 支付成功回调
      ┌──────▼──────┐        超时/买家取消
      │  待发货      │        ┌──────────┐
      │ PAID        │        │  已取消   │
      └──────┬──────┘        │ CANCELLED│
             │ 卖家发货        └──────────┘
      ┌──────▼──────┐
      │  已发货      │
      │ SHIPPED     │
      └──────┬──────┘
             │ 买家确认收货 / 15 天自动
      ┌──────▼──────┐
      │  已完成      │
      │ COMPLETED   │
      └──────┬──────┘
             │ 退款成功
      ┌──────▼──────┐
      │  已退款      │
      │ REFUNDED    │
      └─────────────┘
```

| 状态值 | 说明 |
| --- | --- |
| PENDING_PAYMENT | 待支付（下单后默认） |
| PAID | 已支付，待发货 |
| SHIPPED | 已发货，待收货 |
| COMPLETED | 已完成 |
| CANCELLED | 已取消 |
| REFUNDED | 已退款（终态） |

> BR-18：已取消订单不可被支付回调"复活"，回调到达时若订单已是 CANCELLED，直接走退款。
> BR-19：发货后超过 15 天未确认，系统自动确认收货。

### 5.3 提交订单 —— 最关键的接口

**请求头必须带**：`Idempotency-Key: <UUID>`

请求：

```json
{
  "addressId": "A2001",
  "cartItemIds": ["I80001", "I80002"]
}
```

**不要从前端传价格和总金额**，服务端自己算（防止篡改）。

响应 `data`：

```json
{
  "orderId": "O50001",
  "orderNo": "2026102012345678901",
  "payAmount": 11800,
  "expireAt": "2026-10-20 21:30:00"
}
```

**服务端处理顺序（写代码严格按这个顺序）**：

```
1. 校验幂等令牌，已处理则直接返回首次结果     ← 50002 不作错误，返回原数据
2. 调用 cart-service 取勾选的购物车项
3. 调用 product-service 校验各 SKU 状态与价格
4. 创建订单主记录（status = PENDING_PAYMENT）
5. 创建订单明细（价格快照、标题快照）
6. 调用 product-service 预占库存
   ├─ 成功：更新订单 status 保持 PENDING_PAYMENT，返回
   └─ 失败：删除订单主记录与明细，返回 30003 库存不足
7. 调用 cart-service 删除已下单的购物车项
8. 生成超时取消任务（30 分钟后触发）
```

**为什么先建订单再预占库存**：预占失败时只需删掉订单，回滚范围最小。反过来先预占再建单，如果建单失败，就要额外调用释放接口，多一次可能失败的远程调用。

> BR-14：订单号全局唯一且不可枚举 —— 用「日期 + 雪花 ID」，不用自增。
> BR-12：金额以提交瞬间的价格快照为准。
> BR-13：收货地址快照存入订单。

### 5.5 取消订单

```
PUT /api/orders/{orderId}/cancel
```

- 仅 `PENDING_PAYMENT` 可取消，其他状态返回 `50003`
- 取消后调用 `product-service/skus/release` 释放库存
- **幂等**：重复取消返回成功，不重复释放（BR-17）

### 5.6 超时取消（定时任务）

order-service 内部 `@Scheduled` 每 60 秒扫描一次：

```sql
SELECT order_id FROM `order`
WHERE status = 'PENDING_PAYMENT'
  AND created_at < DATE_SUB(NOW(), INTERVAL 30 MINUTE)
  AND is_deleted = 0
LIMIT 100;
```

对每笔订单：

```
1. 加分布式锁（Redis SETNX，key = order:cancel:{orderId}）
2. 重读订单状态，确认仍是 PENDING_PAYMENT
3. 条件更新：UPDATE `order` SET status='CANCELLED' 
   WHERE order_id=? AND status='PENDING_PAYMENT'   ← 影响行数 0 说明被并发改了，放弃
4. 调用 product-service 释放库存
5. 释放锁
```

> BR-16：超时时限默认 30 分钟，可配置（`order.timeout.minutes`）。

## 六、payment-service / 支付服务

### 6.1 状态枚举

**支付单状态**：

| 值 | 说明 |
| --- | --- |
| PENDING | 待支付 |
| SUCCESS | 支付成功 |
| FAILED | 支付失败 |
| CLOSED | 已关闭（订单取消） |
| REFUNDED | 已退款 |

**退款状态**：

| 值 | 说明 |
| --- | --- |
| PENDING | 待审核 |
| REJECTED | 审核驳回 |
| SUCCESS | 退款成功 |
| FAILED | 退款失败 |

### 6.2 接口列表

| 方法 | 路径 | 说明 | 需登录 |
| --- | --- | --- | --- |
| POST | /api/payments | 发起支付 | 买家 |
| GET | /api/payments/{paymentId} | 查询支付单 | 买家 |
| GET | /api/payments/order/{orderId} | 按订单查支付单 | 买家 |
| POST | /api/payments/callback | 接收支付平台回调 | 否（验签） |
| POST | /api/payments/{paymentId}/refund | 申请退款 | 买家 |
| PUT | /api/payments/refunds/{refundId}/audit | 审核退款 | 卖家/管理员 |

### 6.3 发起支付

```json
POST /api/payments
{ "orderId": "O50001", "channel": "ALIPAY" }
```

`channel` 取值：`ALIPAY` / `WECHAT` / `MOCK`（开发期用 MOCK 模拟）

响应 `data`：

```json
{
  "paymentId": "PAY90001",
  "payNo": "P202610200001",
  "amount": 11800,
  "payUrl": "https://..."
}
```

**实现要求**：

- `amount` 由服务端调用 order-service 查询订单应付金额，**不接受前端传入**（BR-22）
- 同一订单若已有 PENDING 状态的支付单，直接返回它，不重复创建（BR-21）

### 6.4 支付回调 —— 第二关键接口

```
POST /api/payments/callback
```

**处理顺序（严格按此执行）**：

```
1. 验签
   └─ 失败：记录日志，返回 60002，不更新任何状态
2. 幂等去重
   └─ INSERT INTO payment_callback(trade_no, ...) 
      UNIQUE KEY uk_trade_no (trade_no)
   └─ 唯一键冲突 = 重复回调，直接返回成功，不重复处理（BR-24）
3. 查支付单与订单
   └─ 支付单不存在：返回 60001
4. 金额核对
   └─ 回调金额 != 支付单金额：返回 60003，不更新订单（BR-25）
5. 更新支付单 status = SUCCESS, paidAt = now
6. 更新订单：
   └─ 订单是 PENDING_PAYMENT：调用 order 的支付成功接口，置 PAID，
      并调用 product-service/skus/confirm 确认扣减
   └─ 订单是 CANCELLED：说明已超时取消，走退款（BR-18）
7. 返回成功
```

**回调报文示例**（MOCK 渠道）：

```json
{
  "tradeNo": "ALI20261020000001",
  "payNo": "P202610200001",
  "amount": 11800,
  "status": "SUCCESS",
  "payTime": "2026-10-20 21:05:33",
  "sign": "xxx"
}
```

**幂等表的表结构**：

```sql
CREATE TABLE payment_callback (
  callback_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
  trade_no      VARCHAR(64) NOT NULL,
  payment_id    VARCHAR(32) NOT NULL,
  raw_payload   TEXT,
  sign_verified TINYINT(1) NOT NULL DEFAULT 0,
  received_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_trade_no (trade_no)
);
```

> `UNIQUE KEY uk_trade_no` 是去重的唯一保障。**不要用「先查再插」的写法**，并发下会有窗口期，必须靠数据库唯一约束。

### 6.5 退款

```json
POST /api/payments/{paymentId}/refund
{ "amount": 5900, "reason": "商品有瑕疵" }
```

- 退款金额不得超过实付金额（BR-26）
- 同一订单允许多次部分退款，累计不超过实付（BR-27）
- 退款成功后，按退款成功的明细回补库存（BR-28）

## 七、服务间调用关系

```
                    ┌──────────┐
        前端 ──────►│ gateway  │
                    └────┬─────┘
                         │
     ┌───────────┬───────┼────────┬────────────┐
     ▼           ▼       ▼        ▼            ▼
  user       product    cart     order      payment
     ▲           ▲       ▲         │            │
     │           │       │         │            │
     │           └───────┼─────────┘            │
     │    预占/释放/确认  │  查商品、清购物车     │
     │                   │                      │
     └─── 查地址 ────────┘                      │
                                                │
     order ◄────── 支付成功通知 ────────────────┘
```

| 调用方 | 被调方 | 接口 | 时机 |
| --- | --- | --- | --- |
| order | user | GET /users/{userId}/addresses | 下单取地址快照 |
| order | product | POST /products/skus/reserve | 下单预占 |
| order | product | POST /products/skus/release | 取消 / 超时 |
| order | cart | DELETE /cart/items | 下单后清购物车 |
| payment | order | GET /orders/{orderId} | 发起支付时取金额 |
| payment | order | POST /orders/{orderId}/paid | 回调成功后通知 |
| payment | product | POST /products/skus/confirm | 支付成功后确认扣减 |
| cart | product | GET /products/{productId} | 展示时取价格库存 |

**内部调用鉴权**：服务间调用带内部令牌 `X-Internal-Token: <配置的密钥>`，网关不转发这个头，外部无法伪造。

```
mall_user / mall_product / mall_cart / mall_order / mall_payment
```
