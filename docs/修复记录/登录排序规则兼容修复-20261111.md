# 登录排序规则兼容修复及名称统一

## 现场事实

2026-11-11新版实际登录返回code500“系统繁忙”，用户服务selectAuthState报错：`Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='`。旧user与新user_auth_version连接条件直接比较user_id列，继承不同排序规则。此前H2回归并不能覆盖MySQL的排序规则兼容。

## 最小修复

UserMapper.selectAuthState改为单条SELECT中的参数化标量子查询：分别以同一绑定用户ID查询user与user_auth_version，而不直接比较两张表的字符串列。保留单语句账号/状态/角色/版本快照与无版本记录默认0语义，索引点查不变，不移除旧JWT撤销校验。不对真实库执行ALTER、改排序规则、清数据、改密码或角色。

新增回归确认用户版本隔离、缺失用户不返回，以及原冻结/角色往返撤销与事务回滚测试保留。H2仍不证明MySQL现场成功，必须重启后核对真实登录与受保护接口，不以编译成功结案。

## 名称

按课程题目统一可见名称为“在线商城 / ONLINE MALL”；页头、登录注册、页脚、浏览器入口标题同步。页脚项目说明为“云原生微服务架构的在线商城教学项目”，不再擅自限定校园场景。未改学校名称、历史课程材料或数据里的地址。

## 结果

第1轮隔离回归与构建：user-service 14用例全通过、package成功；前端12项测试通过、Vite构建成功。随后冒烟启动暴露启动器对大小写重名环境变量（NO_PROXY/no_proxy）处理不足，Windows进程环境本就不区分大小写；修复只收敛为“启动前临时清除重名键、临时注入默认不恢复父进程”，保留`RestoreParentTemporaryVariables`开关供既有回归使用，启动器测试增至21项全通过。未关闭网络策略或改写系统代理。

现场重启后核对：六后端health均UP；`/api/users/login`写入真实口令返回code0并下发令牌；携带该令牌的`/api/users/me`返回code0；不带内部令牌直连内部认证接口为HTTP403；前端HTTP200且标题为“在线商城”。数据库排序规则、真实账号、角色与业务数据未被改动。

未提交推送。未修改原项目其余源码。第2轮仅复验受影响启动器与前端，不重复已通过的全量后端测试；真实浏览器登录点击未做自动化截图验收。
