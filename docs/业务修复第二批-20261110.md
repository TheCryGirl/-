# 第二批业务修复：资金口径、风控覆盖与收货摘要

## 授权与边界

用户明确授权本批最多2轮验证。第一批预算不重置，本批单独计数；不启动/停止应用服务，不改真实业务数据、账号、密码，不提交或推送。不修改已确认成员材料。

## 管理员资金汇总

新增两个端点，均经第一批网关/内部令牌边界，并要求非空X-User-Id以及严格ADMIN角色：

- `GET /api/orders/admin/finance-summary`：SQL聚合全部is_deleted=0订单，返回gmv、orderCount、paidCount、paidAmount、cancelledCount、byStatus及daily。普通订单列表的买家/卖家过滤不变。
- `GET /api/payments/admin/finance-summary`：SQL聚合全部is_deleted=0退款，返回refundedCount、refundedAmount、pendingRefundAmount、daily。

金额单位分；已收状态沿用PAID/SHIPPED/COMPLETED/REFUNDED，已退只算SUCCESS。按日收款用paid_at、退款用audited_at，不再使用创建日期。两服务的返回分别读取，不是跨库原子快照，也不等于真实支付渠道账单。

前端资金页不再拉取订单/退款第一页并冒充平台总额；响应缺失或字段不合法明确失败，不把错误响应显示成零余额。

## 风控范围

保留课程演示规则，不扩成新的全量风控平台：每类加载前100条退款、在售商品和用户，并逐类展示已加载/服务端总数。明确提示样本外数据未扫描，高频退款仅样本内累计，冻结卖家匹配仅覆盖加载用户。移除原本未参与规则计算的当前管理员订单请求。

商品明确以ADMIN状态筛选ON_SALE，走管理列表，因此含库存为0的在售商品；不使用原先排除零库存的公开商品列表。增加loading guard，避免同页重复扫描请求乱序。

## 卖家收货摘要

原列表`GET /api/orders?role=seller`继续按当前userId过滤。只有卖家视角的本人订单附带`addressSnapshot`：receiver原收货人、phone前3后4脱敏、fullAddress=null；短号码全部掩码。买家列表不新增该信息，其他卖家查不到本订单；详情接口按原资源归属提供完整地址，不改变。

待发货页沿用该字段显示，并明确提示列表已脱敏、完整地址需到详情核对。不再显示“参数未在契约定义，待后端补充”的过时说明。
