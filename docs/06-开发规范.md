## 二、项目结构

每个微服务是一个独立的 Maven 工程，目录结构统一：

```
<service-name>/
├── pom.xml
└── src/main/
    ├── java/com/mall/<service>/
    │   ├── <Service>Application.java     启动类
    │   ├── controller/                   接口层，只做参数校验与转发
    │   ├── service/                      业务逻辑
    │   │   └── impl/
    │   ├── mapper/                       数据访问
    │   ├── entity/                       数据库实体，与表一一对应
    │   ├── dto/                          传输对象
    │   │   ├── request/                  入参
    │   │   └── response/                 出参
    │   ├── client/                       Feign 客户端（调别的服务）
    │   ├── config/                       配置类
    │   ├── common/                       常量、枚举、工具
    │   └── exception/                    自定义异常与全局异常处理
    └── resources/
        ├── application.yaml
        ├── schema.sql                    建表语句
        ├── data.sql                      初始数据（仅 product-service 需要）
        └── mapper/                       MyBatis XML
```

**分层职责**：

| 层 | 该做什么 | 不该做什么 |
| --- | --- | --- |
| controller | 接收参数、基础校验、调用 service、返回结果 | 不写业务逻辑，不直接调 mapper |
| service | 业务逻辑、事务控制、调用其他服务 | 不处理 HTTP 相关的东西 |
| mapper | 只负责 SQL | 不写业务判断 |

## 三、命名规范

### 3.1 Java

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 类 | 大驼峰 | `OrderService`、`PaymentCallback` |
| 方法 / 变量 | 小驼峰 | `createOrder`、`payAmount` |
| 常量 | 全大写下划线 | `MAX_RETRY_TIMES` |
| 包名 | 全小写 | `com.mall.order.service` |
| 数据库表 | 小写下划线 | `order_item`、`payment_callback` |
| 数据库字段 | 小写下划线 | `order_id`、`created_at` |

### 3.2 实体与 DTO 命名

| 后缀 | 用途 | 示例 |
| --- | --- | --- |
| 无后缀 | 数据库实体 | `Order`、`Sku` |
| `XxxRequest` | 接口入参 | `CreateOrderRequest` |
| `XxxResponse` | 接口出参 | `OrderDetailResponse` |
| `XxxDTO` | 服务间传输 | `ProductDTO`、`StockReserveDTO` |

**不要把 Entity 直接当接口入参或出参**。Entity 跟着表走，接口跟着业务走，混在一起会导致「加个表字段，接口就变了」。

### 3.3 枚举

状态值统一用枚举类，**不要用魔法数字或字符串字面量**：

```java
// ✅ 正确
public enum OrderStatus {
    PENDING_PAYMENT, PAID, SHIPPED, COMPLETED, CANCELLED, REFUNDED
}

// ❌ 错误
if (order.getStatus().equals("1")) { ... }
```

枚举值必须与 [接口契约](05-接口契约.md) 中的定义**完全一致**（大写 + 下划线）。

## 四、接口实现规范

### 4.1 统一返回结构

所有接口返回 `Result<T>`，不要直接返回对象或 `ResponseEntity`：

```java
@Data
public class Result<T> {
    private int code;
    private String message;
    private T data;
    private long timestamp;

    public static <T> Result<T> success(T data) {
        Result<T> r = new Result<>();
        r.setCode(0);
        r.setMessage("success");
        r.setData(data);
        r.setTimestamp(System.currentTimeMillis());
        return r;
    }

    public static <T> Result<T> fail(int code, String message) {
        Result<T> r = new Result<>();
        r.setCode(code);
        r.setMessage(message);
        r.setTimestamp(System.currentTimeMillis());
        return r;
    }
}
```

### 4.2 全局异常处理

每个服务都要有 `GlobalExceptionHandler`，把业务异常转成统一返回结构：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining("; "));
        return Result.fail(10001, msg);
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("未预期异常", e);
        // 不要把堆栈信息返回给前端
        return Result.fail(500, "系统繁忙，请稍后重试");
    }
}
```

**业务异常用 `BizException`**，错误码统一放常量类，不要在各处直接写数字。

### 4.3 参数校验

用 `jakarta.validation` 注解，不要手写一堆 if：

```java
@Data
public class CreateOrderRequest {
    @NotBlank(message = "收货地址不能为空")
    private String addressId;

    @NotEmpty(message = "请选择要结算的商品")
    private List<String> cartItemIds;
}
```

Controller 上加 `@Valid`：

```java
@PostMapping("/orders")
public Result<CreateOrderResponse> create(@Valid @RequestBody CreateOrderRequest req) { ... }
```

### 4.4 Feign 客户端

**必须配置超时和降级**，否则下游卡死会拖垮上游：

```java
@FeignClient(
    name = "product-service",
    fallbackFactory = ProductClientFallback.class,
    configuration = FeignTimeoutConfig.class
)
public interface ProductClient {

    @PostMapping("/products/skus/reserve")
    Result<ReservationResponse> reserve(@RequestBody ReserveRequest req);
}
```

```yaml
feign:
  client:
    config:
      default:
        connect-timeout: 2000    # 连接超时 2s
        read-timeout: 5000       # 读取超时 5s
```

**降级逻辑要想清楚**：库存预占失败时，不能假装成功，必须抛异常让上层回滚。

## 五、数据库规范

### 5.1 建表模板

每张表都要有这些字段：

```sql
CREATE TABLE `order` (
  -- 主键：字符串，不用自增，防止被枚举
  order_id      VARCHAR(32)  NOT NULL COMMENT '订单ID',
  order_no      VARCHAR(32)  NOT NULL COMMENT '订单号，对外展示',

  -- 业务字段...

  -- 以下五个是标配
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  created_by    VARCHAR(32)  DEFAULT NULL COMMENT '创建人',
  updated_by    VARCHAR(32)  DEFAULT NULL COMMENT '更新人',
  is_deleted    TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '逻辑删除：0未删 1已删',

  PRIMARY KEY (order_id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_buyer_status (buyer_id, status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单主表';
```

**要求**：

- 表必须有注释，字段必须有注释
- 字符集统一 `utf8mb4`（要存 emoji）
- 存储引擎统一 `InnoDB`
- 金额字段用 `BIGINT` 存分，**不用 DECIMAL 或 DOUBLE**
- 时间用 `DATETIME`，不用 `TIMESTAMP`

### 5.2 索引

- 主键、唯一键必须有
- 查询频繁的条件加普通索引
- **联合索引遵循最左前缀**：`(buyer_id, status, created_at)` 能支持「按买家查」「按买家+状态查」「按买家+状态+时间排序」，但支持不了「只按状态查」
- 不要在低基数字段（如 `is_deleted`、`status` 只有几个值）上单独建索引，没意义

### 5.3 查询

**禁止 `SELECT *`**，明确列出需要的字段。原因：表加字段后 `SELECT *` 会把大字段（TEXT）也查出来，白白增加 IO。

**分页必须带 `ORDER BY`**，否则翻页结果不稳定：

```sql
-- ✅ 正确
SELECT order_id, order_no, status FROM `order`
WHERE buyer_id = #{buyerId}
ORDER BY created_at DESC
LIMIT #{offset}, #{size};

-- ❌ 错误：没有 ORDER BY，翻页可能重复或丢数据
SELECT * FROM `order` WHERE buyer_id = #{buyerId} LIMIT #{offset}, #{size};
```

### 5.4 逻辑删除

统一用 `is_deleted` 字段，**不做物理删除**（订单、支付记录尤其不能删）。

MyBatis-Plus 可以配全局逻辑删除：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: isDeleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

## 六、并发与一致性

这几条是本项目最容易出问题的地方，代码里必须严格照做。

### 6.1 库存扣减必须用条件 UPDATE

**绝对不能「先查库存再更新」**：

```java
// ❌ 错误：并发下超卖
Sku sku = skuMapper.selectById(skuId);
if (sku.getStockAvailable() >= quantity) {
    sku.setStockAvailable(sku.getStockAvailable() - quantity);
    skuMapper.updateById(sku);
}
```

```xml
<!-- ✅ 正确：一条 SQL 完成判断与扣减，靠数据库保证原子性 -->
<update id="reserveStock">
    UPDATE sku
    SET stock_locked = stock_locked + #{quantity},
        stock_available = stock_available - #{quantity},
        version = version + 1
    WHERE sku_id = #{skuId}
      AND stock_available >= #{quantity}
</update>
```

判断影响行数：`0` 表示库存不足。

### 6.2 状态变更必须用条件 UPDATE

订单状态流转同理，避免并发覆盖：

```xml
<update id="cancelIfPending">
    UPDATE `order`
    SET status = 'CANCELLED', updated_at = NOW()
    WHERE order_id = #{orderId}
      AND status = 'PENDING_PAYMENT'
</update>
```

影响行数 `0` 说明状态已被别人改过，直接放弃本次操作。

> 这样写的好处：**不需要先加锁再判断再更新**，一条 SQL 解决，性能更好也更可靠。

### 6.3 幂等必须靠唯一约束

**不要用「先查再插」实现幂等**：

```java
// ❌ 错误：两个并发请求可能都查到"不存在"，然后都插入
if (callbackMapper.findByTradeNo(tradeNo) == null) {
    callbackMapper.insert(callback);
    // 处理业务...
}
```

```java
// ✅ 正确：靠数据库唯一约束，插入失败就是重复
try {
    callbackMapper.insert(callback);   // uk_trade_no 唯一
    // 处理业务...
} catch (DuplicateKeyException e) {
    log.info("重复回调，忽略: {}", tradeNo);
    return Result.success(null);
}
```

### 6.4 分布式锁

按 [接口契约 9.2 节](05-接口契约.md) 的写法：

```java
String requestId = UUID.randomUUID().toString();
Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(key, requestId, 30, TimeUnit.SECONDS);
if (!Boolean.TRUE.equals(locked)) {
    return;  // 没抢到锁，交给别的实例处理
}
try {
    // 业务逻辑
} finally {
    // 解锁必须校验持有者，用 Lua 保证原子性
    unlockScript.execute(redisTemplate, Collections.singletonList(key), requestId);
}
```

### 6.5 事务边界

- `@Transactional` **加在 service 方法上**，不要加在 controller
- 事务里**不要做远程调用**（Feign）。远程调用耗时长，会把数据库连接一直占着；而且远程调用不走本地事务，回滚不了
- 需要「本地事务 + 远程调用」时，用「先本地提交，再远程调用，失败补偿」的模式

## 七、日志

### 7.1 用什么打日志

统一用 `@Slf4j`（Lombok），**禁止 `System.out.println`**。

### 7.2 日志级别

| 级别 | 用在哪 |
| --- | --- |
| `error` | 需要人介入的问题：库存释放失败、回调验签失败、资金相关异常 |
| `warn` | 可自愈但需关注：重复回调被忽略、重试成功 |
| `info` | 关键业务节点：下单成功、支付成功、订单状态变更 |
| `debug` | 调试信息，生产环境关闭 |

### 7.3 日志内容

**关键业务操作必须记录足够的上下文**：

```java
// ✅ 正确：有单号、有金额、能回溯
log.info("订单创建成功, orderNo={}, buyerId={}, amount={}", 
         order.getOrderNo(), order.getBuyerId(), order.getPayAmount());

// ❌ 错误：什么都看不出来
log.info("创建成功");
```

**不要在日志里打敏感信息**：密码、完整手机号、支付令牌。手机号要脱敏：`138****8000`。

## 九、代码审查要点

PR 提交后，审查的人重点看这几条（花几分钟就够）：

- [ ] 有没有 `SELECT *`
- [ ] 库存或状态变更有没有用条件 UPDATE（而不是先查再改）
- [ ] 幂等有没有用唯一约束（而不是先查再插）
- [ ] Feign 调用有没有配超时
- [ ] 事务里有没有远程调用
- [ ] 有没有硬编码的配置（密钥、IP、端口）
- [ ] 关键业务有没有打日志
- [ ] 有没有 `System.out.println`

## 十、本地开发环境

### 10.1 需要装的东西

| 工具 | 版本 | 用途 |
| --- | --- | --- |
| JDK | 17 | 后端 |
| Maven | 3.8+ | 后端构建 |
| MySQL | 8.0 | 数据库 |
| Redis | 7.x | 缓存与锁 |
| Nacos | 2.3.x | 注册中心 |
| Node.js | 18+ | 前端 |
| pnpm | 9+ | 前端包管理 |

### 10.2 启动顺序

```
1. MySQL       → 建五个库
2. Redis       → 默认 6379
3. Nacos       → startup.cmd -m standalone，访问 localhost:8848/nacos
4. 各微服务    → 按需启动
5. gateway     → 最后启动
6. 前端        → pnpm dev
```

### 10.3 环境变量

口令和密钥**一律从环境变量读**，不要写进代码或配置文件：

| 变量 | 说明 |
| --- | --- |
| `DB_USER` | 数据库用户名 |
| `DB_PASSWORD` | 数据库口令 |
| `JWT_SECRET` | JWT 签名密钥 |
| `MOCK_SECRET` | 模拟支付签名密钥 |

PowerShell 临时设置：

```powershell
$env:DB_PASSWORD = "你的口令"
$env:JWT_SECRET = "一段随机字符串"
```
