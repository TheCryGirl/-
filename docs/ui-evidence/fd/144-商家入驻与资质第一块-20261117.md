关键口径：

1. `publishable = applyStatus == APPROVED && depositPaid`，`depositPaid` 把 `deposit_amount IS NULL`（规则生效前的历史店铺）视为已缴；
2. 首次申请建店即 `status=SUSPENDED`、`applyStatus=PENDING`、`deposit_amount=0`；审核中重复申请、已过审再申请都返回 `10001`；只有 `REJECTED` 可重新提交，重提后回到 `PENDING`，`rejectReason` 仍返回给卖家对照；
3. 审核通过且保证金 > 0 才置 `ACTIVE`，并按 #49 的既有约定调用 `POST /products/internal/seller-visibility`；同步失败返回 `10005` 且审核结论与流水一起回滚；
4. 驳回必填理由；已过审的店铺不能回头驳回（停止营业走 #49 的停用接口）；
5. `GET /api/shops/mine` 不再自动建店，未申请时返回 `shopId=null` + `publishable=false`；
6. `GET /api/shops/seller/{sellerId}` 在 `publishable=false` 时对外一律报 `SUSPENDED`——上架、商品审核通过、下单因此继续沿用 #49 的 `shop.status` 单点拦截，所以「未过审不能发布商品」在接口层成立而不需要改别人的服务；
7. `PUT /api/shops/{shopId}/status` 对未过审 / 未缴保证金的店铺拒绝恢复 `ACTIVE`（`10001`），防住「手工改库绕过」。

## 关键口径

1. **表**：`commission_rule`（`scope` PLATFORM/CATEGORY/SHOP，`rate` 万分比整数，`uk_scope_target`）、
   `settlement`（`uk_seller_period`，状态 PENDING/CONFIRMED/PAID，默认 PENDING）、
   `settlement_item`（`uk_item_order`，一单一明细）。
2. **数据源**：跨库直读 `mall_order.order`（两服务同 MySQL 实例，组长口径「直接读 order 表即可」）；
   H2 测试里 `CREATE SCHEMA mall_order` 镜像同结构，SQL 两环境一致。
3. **完成时间口径**：订单 `updated_at`（order-service 完成操作只写 status + updated_at，无 completed_at 列）。
4. **佣金**：订单实付 × 万分比费率，按分四舍五入只一次；店铺 > 类目 > 平台回退，类目本期只建结构不参与计算
   （order_item 无类目快照，遗留项）；无规则费率 0。
5. **剔除**：只算 `COMPLETED` 订单；存在 SUCCESS 退款单的订单直接剔除。
6. **幂等/冻结**：唯一键 + `ON DUPLICATE KEY UPDATE x=x` 无操作插入 + `UPDATE ... WHERE status='PENDING'` 条件累加；
   重复生成不翻倍；已确认/已打款的结算单整店跳过（`skippedFrozen`）。
7. **接口权限**：GET 卖家仅本人（查别人 10003）、管理员全部；generate / status 仅 ADMIN；
   状态接口本期只支持标 PAID，非法目标 10001、不存在 60007、重复打款 60008。
