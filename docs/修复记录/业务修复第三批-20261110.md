# 第三批：旧JWT撤销与退款补偿

## 范围与授权

用户授权：只修旧JWT撤销、退款成功后的订单通知与库存回补，最多两轮验证；保持六后端停止，不改真实账号/业务数据、不提交推送、不轮换签名密钥或数据库口令。保留前两批未提交改动和确认成员材料。子代理仅china/deepseek-v4.1-flash，未委托其运行测试或编译。

## 旧JWT撤销

- 新增用户服务持久表`user_auth_version(user_id,token_version)`，不向现有user表强加ALTER列；schema与独立migration均为CREATE IF NOT EXISTS。未执行真实库SQL。
- 角色/状态管理变更与版本递增在同一事务；冻结后解冻、降权后恢复仍递增，旧版本JWT不会复活。普通资料修改不变更令牌版本，且资料SQL不再重写读到的角色/状态，避免并发覆盖管理员操作。
- 登录从当前用户状态/角色/版本的单条查询签发tokenVersion；历史不含版本的JWT要求重新登录。
- 网关通过带内部令牌的用户服务接口`/users/internal/auth-state/{userId}`实时核对userId、ACTIVE、role、tokenVersion，无正向缓存。默认使用Nacos服务名user-service及负载均衡WebClient，不通过公共网关递归调用。
- 受保护请求核验失败或服务不可用时401；公开只读路径降为匿名且无身份头，保留匿名浏览能力。下游业务异常不会被当验证失败重发匿名请求。
- 已经过核验且正在执行的请求不强制中断；承诺边界是变更提交后的后续核验。不是全局撤销正在进行的分布式事务。
- 用户服务不可用会影响所有受保护请求，这是fail-closed的明确可用性取舍；不偷偷回退信任旧JWT。
- 本批不实现“只注销单一设备JWT”的黑名单。冻结/角色变更是用户维度撤销；原logout接口语义未扩展。

## 退款补偿

- 普通全额退款审核成功后，与退款事务一起插入`refund_notification_task`两事件：ORDER_REFUNDED、STOCK_RESTOCK；orderId+eventType唯一。部分退款、驳回与原autoRefund notifyOrder=false路径不扩大通知行为。
- 提交后立即投递保持原交互；每个事件独立完成。失败或进程中断后，持久任务由定时调度扫描；DONE不重复发，PENDING按退避到期重试。
- 120秒PROCESSING租约、条件UPDATE抢占、attempts递增，并用attempts作为完成/失败写回的代次校验。旧工作者不得覆盖新工作者的结果。网络调用发生在数据库事务之外；抢占/完成/失败用REQUIRES_NEW独立提交，避免afterCommit残留事务资源导致结果不落库。
- 指数退避默认30秒，上限600秒，持续失败不静默丢任务，定时扫描默认60秒且每批50项；不等于恰在next_retry_at那一毫秒执行。长期故障仍需运维处理。
- 下游成功但写DONE前崩溃可能重复通知，这是至少一次交付；依赖现有订单退款状态机和商品预占退款状态机幂等。不是未经证明的“恰好一次”。
- 不落任意异常message或下游响应正文，只保留固定失败原因或业务错误码，避免携带URL/令牌/个人信息。历史失败退款不会自动扫描回填本次之前丢失的通知，需另行核对后授权补任务。
- 新增任务表schema与migration仅定义结构，不改已有支付/退款/订单数据。应用下次启动按项目原sql-init执行CREATE；本轮保持服务停止，未作用于真实库。
