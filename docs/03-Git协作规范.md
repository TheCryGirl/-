# Git 协作与版本留痕规范

指导书要求：「必须使用 Git 进行版本控制，并有清晰的 Commit 记录，以体现协作过程」「组长需在报告中提供基于 Git 提交记录和任务完成情况的组内互评表」。

本文说明本项目如何让每一次改动都留下可追溯的记录。

## 一、留痕的四层结构

一次完整的工作流会同时产生四种记录，它们互相链接：

```
Issue（要做什么）
   ↓ 关联
分支（在哪里做）
   ↓ 提交
Commit（做了什么）
   ↓ 合并
Pull Request（谁审查、何时合入）
   ↓ 关联
Project 看板（进度到哪）
```

老师在报告里看到的「组内互评」依据，就来自这四层：谁认领了哪个 Issue、谁在哪个分支提交了多少次、谁审查了谁的 PR。

## 二、Issue：每件事先建卡

**规则：任何超过半小时的工作，先建 Issue 再动手。**

Issue 标题写清楚要做什么，不要用「改一下」「优化」这类模糊表述。

**Issue 类型与标签**：

| 标签 | 用途 | 示例标题 |
| --- | --- | --- |
| `需求` | 需求分析与建模 | 绘制商品模块用例图并编写用例规约 |
| `设计` | 架构与数据库设计 | 设计库存预占的数据一致性方案 |
| `开发` | 编码实现 | 实现订单下单接口与幂等令牌校验 |
| `测试` | 测试用例与执行 | 编写并发下单不超卖的测试用例 |
| `文档` | 报告与规范 | 撰写实验二设计规格说明书 |

**Issue 正文模板**：

```markdown
## 背景
为什么要做这件事

## 具体任务
- [ ] 任务 1
- [ ] 任务 2

## 验收标准
怎样算做完

## 关联
- 依赖：#12
- 对应报告章节：2.3.4
```

## 三、分支：一个 Issue 一个分支

**规则：不在 main 分支直接改代码。**

| 分支类型 | 命名格式 | 用途 | 示例 |
| --- | --- | --- | --- |
| 主分支 | `main` | 始终可运行 | — |
| 功能分支 | `feature/<issue号>-<简短描述>` | 新功能开发 | `feature/12-order-create` |
| 修复分支 | `fix/<issue号>-<简短描述>` | 缺陷修复 | `fix/35-callback-dedupe` |
| 文档分支 | `docs/<简短描述>` | 文档更新 | `docs/env-and-plan` |

**流程**：

```bash
# 1. 从最新的 main 拉分支
git checkout main
git pull origin main
git checkout -b feature/12-order-create

# 2. 开发，分多次小提交
git add .
git commit -m "feat(order): 实现下单接口与幂等令牌校验 (#12)"

# 3. 推送到远端
git push -u origin feature/12-order-create

# 4. 在 GitHub 上创建 Pull Request，关联 Issue
```

## 四、Commit：写清楚改了什么

### 提交信息格式

```
<类型>(<范围>): <简短描述> (#Issue号)
```

**类型**：

| 类型 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构（不改变外部行为） |
| `test` | 测试代码 |
| `chore` | 构建、依赖、配置 |

**实际示例**：

```
feat(order): 实现下单接口与幂等令牌校验 (#12)
fix(payment): 回调去重改为数据库唯一约束 (#35)
docs(report): 补充实验一表1-17名词短语统计 (#8)
refactor(product): 库存预占改为条件UPDATE避免超卖 (#21)
test(order): 增加并发下单100并发的测试用例 (#40)
```

### 提交粒度

**一次提交只做一件事。** 不要把「新增三个接口 + 改了两个页面的样式 + 更新了文档」塞进同一个 commit。

判断标准：如果提交信息需要用「和」「以及」连接两件不相关的事，就该拆成两次提交。

### 禁止的提交信息

以下写法无法体现工作内容，一律不要用：

- `update`、`修改`、`提交`、`更新一下`
- `fix bug`（哪个 bug？）
- `aaa`、`111`、`测试`
- 连续多个 `update` 提交

## 五、Pull Request：合入前有人看一眼

**规则：功能分支必须通过 PR 合入 main，不允许本地直接 merge 后强推。**

**PR 标题**：与对应的 Issue 标题保持一致或相近。

**PR 正文模板**：

```markdown
## 关联 Issue
Closes #12

## 改动内容
- 新增下单接口 POST /api/orders
- 实现幂等令牌校验
- 补充单元测试

## 自测情况
- [x] 本地跑通完整下单流程
- [x] 重复提交同一令牌只创建一笔订单

## 截图（如涉及界面）
```

**审查要求**：至少一名其他成员 approve 后合入。PR 的审查记录同样是「协作过程」的证据。

## 六、Project 看板：进度可视化

看板地址：https://github.com/users/TheCryGirl/projects/1

**看板列（Status 字段）**：

| 列 | 含义 | 何时移动 |
| --- | --- | --- |
| Todo | 已建卡，尚未开始 | 建 Issue 时自动进入 |
| In Progress | 正在做 | 开始动手时 |
| Done | 已完成 | PR 合入后 |

**其他字段**：

| 字段 | 用途 |
| --- | --- |
| Assignees | 这个任务谁负责 |
| Labels | 任务类型（需求 / 设计 / 开发 / 测试 / 文档） |
| Milestone | 归属哪个实验阶段 |
| Linked pull requests | 自动关联的 PR |

**要求**：任务状态与实际一致。不要出现卡在 Todo 但代码已经写完的情况——看板的意义就是反映真实进度。

## 七、里程碑设置

用 Milestone 把 Issue 按实验阶段归类：

| Milestone | 含义 | 截止时间 |
| --- | --- | --- |
| 实验一：需求分析与迭代规划 | 需求、建模、报告第一部分 | 第 2 周末 |
| 实验二：系统设计与技术选型 | 架构、数据库设计、报告第二部分 | 第 4 周末 |
| 实验三：系统原型构建与实现 | 五个微服务编码、报告第三部分 | 第 6 周末 |
| 实验四：软件测试与部署 | 测试、压测、部署、报告第四部分 | 第 8 周末 |

## 八、组内互评的数据来源

指导书表 5-1 要求「组内互评表」，评分依据是可核实的记录。具体取数方式：

| 互评维度 | 取数来源 | 查看方式 |
| --- | --- | --- |
| 工作量 | 每人关联 Issue 的数量与关闭数量 | 看板按 Assignee 筛选 |
| 代码贡献 | 每人的 commit 数量与代码行数 | `git shortlog -sn`、GitHub Insights → Contributors |
| 参与度 | PR 提交数、代码审查数 | GitHub Insights → Pulse |
| 任务完成质量 | Issue 是否按期关闭、PR 是否被打回 | Milestone 完成率 |

**示例命令**：

```bash
# 查看每个人的提交次数
git shortlog -sn --all

# 查看某人的提交明细
git log --author="姓名" --oneline

# 查看某个时间段的整体提交
git log --since="2026-10-01" --until="2026-10-31" --oneline
```

## 九、从零开始的落地步骤

本项目当前状态：仓库为空，实验一文档已完成但未入库。

**第一步：建立仓库基础结构**（本项目实际执行的顺序）

```bash
# 1. 克隆仓库
git clone https://github.com/TheCryGirl/-.git
cd -

# 2. 建立目录结构，放入 README 与项目文档
# 3. 首次提交
git add README.md docs/
git commit -m "docs: 初始化仓库结构，补充实验环境说明与总体规划 (#3)"
git push origin main
```

**第二步：建立看板任务**

为每个实验建立 Issue，纳入对应 Milestone，分配负责人。

**第三步：按规范开发**

每次改动走「建 Issue → 拉分支 → 小提交 → PR → 合入 → 移动看板卡片」的完整流程。

## 十、常见问题

**Q：实验一的报告是一开始就写好的，没有中间提交记录怎么办？**

A：如实说明。报告文件作为一次性成果提交（`docs(report): 提交实验一需求规格说明书 (#4)`），不伪造中间的修改历史。指导书要求的是「体现协作过程」，从实验二的开发开始严格执行即可。如果实验一有后续修订（如根据老师反馈调整），那时的修改会有真实的提交记录。

**Q：两个人同时改同一个文件冲突了怎么办？**

A：先 `git pull origin main` 拉最新，再解决冲突。文本文件（`.puml`、`.md`、`.java`、`.vue`）冲突可直接编辑解决；二进制文件（`.docx`）无法合并，约定同一时间只有一人修改文档。

**Q：提交后发现漏了文件怎么办？**

A：如果还没推送，可以 `git commit --amend` 追加；如果已经推送，再补一次提交（`git commit -m "chore: 补充遗漏的配置文件 (#12)"`）。**不要用 `git push --force` 覆盖历史**，那会让留痕失去意义。
