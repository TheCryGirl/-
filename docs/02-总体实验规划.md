# 总体实验规划

本文把《软件工程实验》的四个实验与本项目的四个 Sprint 对齐，说明每个阶段做什么、交付什么、怎么验收。

## 一、整体路线

指导书要求「采用敏捷开发模式，以 1-2 周为一个迭代周期，每个迭代结束时提交可工作的软件增量」。本项目共 8 周，划分为 4 个 Sprint，每个 Sprint 2 周。四个实验与 Sprint 的对应关系如下：

| 实验 | 对应 Sprint | 周期 | 核心产出 | 交付物 |
| --- | --- | --- | --- | --- |
| 实验一 需求分析与迭代规划 | Sprint 0 + Sprint 1 前半 | 第 0–2 周 | 用户故事地图、用例模型、域模型 | 第一部分：需求规格说明书 |
| 实验二 系统设计与技术选型 | Sprint 1 后半 + Sprint 2 前半 | 第 2–4 周 | 架构图、类图、数据库设计 | 第二部分：设计规格说明书 |
| 实验三 系统原型构建与实现 | Sprint 1–3 全过程 | 第 1–6 周 | 至少三个微服务可运行、核心流程可演示 | 第三部分：原型构建与实现 |
| 实验四 软件测试与部署 | Sprint 3 + Sprint 4 | 第 5–8 周 | 测试用例与报告、压测结果、部署方案 | 第四部分：测试报告 |

> 四个实验不是严格串行的：实验一的成果直接作为实验二设计的输入，实验三的编码在 Sprint 1 就已开始，实验四的测试随每个 Sprint 的增量同步进行。上表的周期表示该实验的**主要投入时段**。

## 二、Sprint 划分与目标

沿用实验一表 1-2 的规划：

| Sprint | 周期 | 核心目标 | 主要交付物 | 完成判据 |
| --- | --- | --- | --- | --- |
| Sprint 0 | 第 0 周 | 技术验证与建仓 | 版本锁定清单、服务骨架、Git 仓库与分支规范 | Nacos + 网关 + 空服务可联通 |
| Sprint 1 | 第 1–2 周 | MVP 交易闭环 | 用户、商品、订单三服务；登录、列表、下单、模拟支付 | 单人可完成一次下单并看到订单 |
| Sprint 2 | 第 3–4 周 | 购物车与真实支付链路 | 购物车服务、支付服务、库存预占、超时取消 | 并发下单不超卖；重复回调不重复扣款 |
| Sprint 3 | 第 5–6 周 | 一致性与可观测性 | 消息补偿、链路追踪、容器化编排、压测报告 | Docker Compose 一键起全栈；压测达标 |
| Sprint 4 | 第 7–8 周 | 售后、治理与收尾 | 退款、商品审核、报表；测试报告与文档定稿 | 测试用例全部执行完毕，报告成稿 |

## 三、各实验的具体内容

### 实验一：需求分析与迭代规划

**指导书要求**：按照特定的软件选题，调研分析、建立用户故事地图、确定软件的系统需求，并应用 UML 建立软件问题模型。

**已完成的工作**：

| 项目 | 内容 | 位置 |
| --- | --- | --- |
| 行业调研 | 2024 年网上零售额、CNNIC 第 55 次报告数据、转化漏斗数据 | 报告 1.1.1 |
| 迭代规划 | 4 个 Sprint 的划分与交付物、18 条用户故事的 Backlog | 报告 1.2.1、1.2.2 |
| 用户故事地图 | 买家主旅程一张、卖家与管理员一张 | 报告 1.2.3，图 1-1、1-2 |
| 角色分析 | 6 个角色（访客、买家、卖家、管理员、第三方支付平台、定时调度器） | 报告 2.1，表 1-4 |
| 用例分析 | 37 个用例（UC-01~UC-37），含角色、优先级、描述 | 报告 2.2，表 1-5 |
| 用例建模 | 按 5 个功能模块拆分 5 张用例图、10 张用例规约表 | 报告 2.3，图 1-3~1-7、表 1-7~1-16 |
| 活动图 | 4 张复杂事件流活动图（下单、支付回调、超时取消、退款） | 报告 2.3.6，图 1-8~1-11 |
| 数据建模 | 名词短语分析、CRC 卡片、域模型 | 报告 2.4，图 1-12、表 1-17、1-18 |
| 非功能需求 | 性能、可用性、安全、可维护性指标 | 报告 3 |

**质量要点**：
- 用例图按微服务边界拆分为 5 张，每张对应一个独立部署的服务，符合指导书「不要将整个系统的所有用例集中在一张用例图中」的要求；
- 37 个用例编号连续，正文引用无悬空；
- 图 1-1~1-12、表 1-1~1-19 编号连续无重号。

### 实验二：系统设计与技术选型

**指导书要求**：应用软件设计知识设计出能够满足问题描述和约束条件的软件系统解决方案，并应用 UML 建立软件设计模型。

**计划工作**：

| 章节 | 内容 |
| --- | --- |
| 1 引言 | 设计目标、设计原则、约束条件 |
| 2.1 体系结构设计 | 架构风格选型对比（单体 / 分层 / 微服务）；系统逻辑架构图；系统物理架构图 |
| 2.2 模块设计 | 核心类模型、关键类的详细设计（类图、状态图）、关键算法活动图 |
| 3 数据库设计 | 域模型到表的映射、数据库表清单、每张表的详细字段说明 |

**技术重点**（选题六明确要求的分析与设计重点）：

1. **微服务拆分方案**：五个服务（用户、商品、购物车、订单、支付）的职责边界与拆分依据；
2. **服务间通信**：同步调用（OpenFeign）+ 异步消息（RocketMQ / RabbitMQ）的选型与使用场景划分；
3. **数据一致性方案**：库存预占（可用 / 锁定双字段）+ 订单超时取消 + 补偿机制，不依赖 Seata 等强一致方案；
4. **网关路由**：Spring Cloud Gateway 的统一入口、鉴权过滤、路由规则；
5. **系统逻辑与物理架构图**：逻辑分层与容器化部署拓扑。

**交付物**：第二部分「设计规格说明书」。

### 实验三：系统原型构建与实现

**指导书要求**：应用适当的软件开发工具进行软件原型搭建，并选取部分模块编码实现。鼓励使用 AI 辅助生成代码骨架和测试代码，但须经过人工审查和修改。

**选题六的实现要求**：实现至少三个核心微服务，完成服务间联调，验证一个核心业务流程（如用户下单）。

**计划实现范围**（按优先级）：

| 优先级 | 服务 | 说明 |
| --- | --- | --- |
| P0 | user-service | 注册、登录、JWT 签发、角色鉴权 |
| P0 | product-service | 商品 CRUD、SKU 管理、库存预占与释放 |
| P0 | order-service | 下单、订单状态机、超时取消、幂等令牌 |
| P1 | cart-service | 购物车增删改查、勾选结算 |
| P1 | payment-service | 支付单、回调验签、幂等去重、退款 |

**核心业务流程**：用户下单 → 库存预占 → 支付 → 回调确认 → 发货 → 确认收货。

**报告结构**：

| 章节 | 内容 |
| --- | --- |
| 1 引言 | 原型构建思路、选取实现的模块 |
| 2 模块实现 | 各模块的功能展示（界面截图 + 功能说明）、核心代码片段（关键算法与业务逻辑） |

**交付物**：第三部分「系统原型构建与实现」。

### 实验四：软件测试与部署

**指导书要求**：设计软件测试方案，并对已实现的系统模块设计测试用例，实施测试，分析测试结果并写出部署方案。

**计划工作**：

| 章节 | 内容 |
| --- | --- |
| 1 引言 | 测试方法、测试过程、测试工具 |
| 2 模块测试 | 按模块设计测试用例，记录测试数据、结果与执行人 |
| 3 功能测试 | 对已实现功能的测试用例、输入数据、测试结果 |
| 4 测试结论 | 系统强度、性能、容量、可靠性统计结论 |
| 部署方案 | 容器化编排、云服务器部署步骤、运维要点 |

**选题六的测试要求**：进行简单的压力测试，验证系统的可扩展性。

**计划测试场景**：

- 并发下单不超卖（库存 100，500 并发下单，成交数 ≤ 100）；
- 支付回调重复到达不重复扣款（同一 `tradeNo` 重复推送 10 次，只处理一次）；
- 订单超时自动取消并释放库存（30 分钟时限，模拟时钟推进）；
- 压力测试：下单接口的 QPS 与响应时间分布，观察横向扩容后的吞吐变化。

**交付物**：第四部分「测试报告」。

## 四、实验总结（第五部分）

四个实验完成后，撰写第五部分：

1. 小组实验总结；
2. 成员个人实验总结（每人 200–400 字）；
3. 组内互评表（表 5-1，含自评分、互评分、个人贡献系数）；
4. **AI 使用记录**（不少于 300 字）：用了什么工具、在哪些环节使用、做了哪些修改、对效率的影响、下次会如何调整。

## 六、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 微服务联调耗时超预期 | 挤压测试与文档时间 | Sprint 1 先做单体可跑通的核心流程，再拆服务 |
| 团队成员进度不同步 | 合并冲突、返工 | 按服务划分负责人，接口先定契约再并行开发 |
| 云服务器试用期限制 | 无法长期在线演示 | 本地 Docker Compose 为主，云端仅用于验收演示 |
| AI 生成内容需要大量返工 | 偏离设计要求 | 先人工确定接口与数据结构，AI 只生成骨架与模板代码 |
