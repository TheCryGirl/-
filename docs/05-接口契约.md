| 服务 | 端口 | 职责 | 负责人 |

| gateway | 9000 | 统一入口、路由、鉴权过滤 | 哭女 |

前端只访问网关 `http://localhost:9000`，**不直连任何服务**。

### 1.2 路径规则

- 网关对外：`/api/<服务名>/<资源>`，例如 `/api/orders/123`
- 服务内部：不带 `/api` 前缀，例如 order-service 自身监听 `/orders/123`
- 内部服务间调用走 `FeignClient`，不经过网关

### 1.3 统一响应结构

**所有接口**返回这个结构，HTTP 状态码只用于表达协议层结果（200 / 401 / 403 / 500），业务成功与否看 `code`。

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1761000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | int | 0 成功，非 0 失败 |
| message | string | 出错时给用户看的中文提示 |
| data | object | 业务数据，失败时为 null |
| timestamp | long | 服务器毫秒时间戳，用于排查 |

### 1.5 认证

- 登录成功后签发 JWT，前端存放在 `localStorage.token`
- 除白名单接口外，所有请求带 `Authorization: Bearer <token>`
- JWT payload：`{ "userId": "U001", "role": "BUYER", "exp": 1761000000 }`
- **网关统一校验**，校验通过后把 `userId` / `role` 放进请求头 `X-User-Id` / `X-User-Role` 传给下游服务；下游服务**不再重复解析 JWT**
- JWT 密钥只从环境变量 `JWT_SECRET`（≥ 32 位）读取，未配置时网关与 user-service 启动即失败，配置里不留硬编码默认值

**白名单**（无需令牌即可访问）：

```
POST /api/users/register
POST /api/users/login
POST /api/payments/callback      # 支付回调，靠签名验真而不是登录态
GET  /api/products
GET  /api/products/{productId}   # {productId} 不为 mine / skus / images
GET  /api/categories/**
GET  /images/**
GET  /actuator/**
GET  /avatars/**
OPTIONS **                       # 浏览器跨域预检，不带令牌
```

**白名单不再等于「强制匿名」**：白名单路径上如果带了有效 `Authorization: Bearer <token>`，网关照常解析并注入 `X-User-Id` / `X-User-Role`；令牌缺失或无效时按匿名放行，不返回 401。

> 这样卖家/管理员访问自己的 PENDING 商品（`GET /api/products/{id}`）时下游才拿得到身份，否则会被当成访客拒绝。
> 相关改动见 Issue #38（`JwtAuthFilter`）。

> 商品发布、修改、上下架、审核与 `/api/products/mine` 均需登录，
> 因此不能整体放行 `GET /api/products/**` 之外的任何商品路径。
> 网关按「方法 + 路径」精确判定白名单。

### 1.5.1 要点

- 网关路由转发时统一 `StripPrefix=1`，下游服务收到的路径不带 `/api`
- `/images/**`、`/avatars/**` 原样转发，不加 StripPrefix（静态资源与服务内映射路径一致）
- `/api/products/{x}` 白名单判定时，`mine` / `skus` / `images` / `batch` / `internal` 是功能路径而不是商品 ID，必须登录
- 网关校验通过后覆盖客户端传入的 `X-User-Id` / `X-User-Role`，防止伪造

### 1.6 分页

请求：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| page | int | 1 | 从 1 开始 |
| size | int | 20 | 每页条数，上限 100 |

响应 `data`：

```json
{
  "page": 1,
  "size": 20,
  "total": 137,
  "pages": 7,
  "list": []
}
```

### 1.7 时间与金额

| 项 | 约定 |
| --- | --- |
| 时间 | `yyyy-MM-dd HH:mm:ss`，统一北京时间 |
| 金额 | **分为单位的整数**（`long`），避免浮点误差。`10050` 表示 100.50 元 |
| ID | 字符串（`String`），不用自增数字，防止被枚举 |

> 金额用整数的原因见 BR-04「价格精确到分」。前端展示时除以 100，不要在传输层用小数。

### 1.8 幂等

涉及创建订单、支付这类可能重复提交的接口，必须在请求头带：

```
Idempotency-Key: <UUID>
```

由前端每次提交时生成。服务端按 key 去重，重复请求返回首次的结果（不报错，返回同样内容）。

**约束（与实现一致）**：

- 适用接口：`POST /api/orders`、`POST /api/payments`
- key 长度 8–64 位；缺失返回 `10001`
- 同一个 key 换了请求内容（order-service 比对 `buyerId + addressId + cartItemIds` 的 SHA-256）→ 返回 `50002`，不复用首次结果
- order-service 首次下单失败时会释放该 key，允许用同一个 key 重试；并发重复提交正在处理时返回 `50002`，提示稍后重试

### 2.3 关键接口详情

#### POST /api/users/register

请求：

```json
{
  "account": "zhangsan",
  "password": "abc123456",
  "nickname": "张三",
  "phone": "13800138000"
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| account | 是 | 4-20 位，字母数字下划线 |
| password | 是 | 6-32 位 |
| nickname | 是 | 2-20 位 |
| phone | 否 | 11 位数字 |

响应 `data`：

```json
{ "userId": "U10001" }
```

失败：`20002` 账号已存在、`20003` 昵称被占用。

> BR-01 账号全局唯一且不可修改、BR-02 密码不得明文存储。

#### POST /api/users/login

请求：

```json
{ "account": "zhangsan", "password": "abc123456" }
```

响应 `data`：

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "user": {
    "userId": "U10001",
    "account": "zhangsan",
    "nickname": "张三",
    "role": "BUYER",
    "avatar": null
  }
}
```

失败：`20001` 账号或密码错误、`20004` 账号已冻结。

#### GET /api/users/{userId}/addresses → 供 order-service 内部调用

响应 `data`：

```json
[
  {
    "addressId": "A2001",
    "receiver": "张三",
    "phone": "13800138000",
    "province": "天津市",
    "city": "北辰区",
    "detail": "河北工业大学 3 号宿舍楼 502",
    "isDefault": true,
    "defaultAddress": true
  }
]
```

> 这个接口 order-service 下单时会调用，取地址生成快照（BR-13）。
> `defaultAddress` 与 `isDefault` 同值，前者是 #51 新增的字段名，前端两个都兼容。
> 默认地址的维护规则见 11.3。

#### PUT /api/users/{userId}/role

管理员把用户设置为买家、卖家或管理员。注册接口只创建 `BUYER`，卖家权限通过这里开通。

请求：

```json
{ "role": "SELLER" }
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| role | 是 | `BUYER` / `SELLER` / `ADMIN` |

规则：

- 只有管理员可调用，不能变更自己的角色（避免把自己降级后无人可管理）
- 角色写进 JWT，**变更后对方需重新登录**才会拿到新角色
- 管理员账号可通过环境变量 `ADMIN_BOOTSTRAP_ACCOUNT` / `ADMIN_BOOTSTRAP_PASSWORD` 初始化，详见《本地启动指南》

分类管理接口使用同一统一响应结构。新增、修改请求字段如下：

### 3.5 低库存阈值与预警

低库存预警只提供提示，不参与库存预占条件判断，不会阻塞正常交易。

| 方法 | 路径 | 说明 | 需登录 |
| --- | --- | --- | --- |
| GET | /api/products/low-stock-threshold | 查询全局默认阈值 | 管理员 |
| PUT | /api/products/low-stock-threshold | 修改全局默认阈值 | 管理员 |
| PUT | /api/products/skus/{skuId}/low-stock-threshold | 设置 SKU 覆盖阈值 | 卖家/管理员 |
| GET | /api/products/skus/low-stock-alerts | 查询低库存 SKU 预警 | 卖家/管理员 |

阈值为非负整数，默认值为 5。SKU 的有效阈值为 `lowStockThreshold` 不为空时的单 SKU 覆盖值，否则使用全局默认值。库存满足 `stockAvailable < 有效阈值` 时进入预警列表；卖家只能查询自己商品，管理员查询全平台。修改阈值后查询立即按新值生效。

预警响应示例：

```json
{
  "skuId": "S40001",
  "productId": "P30001",
  "productTitle": "罗技 G102 鼠标",
  "specName": "黑色",
  "stockAvailable": 3,
  "stockLocked": 2,
  "threshold": 5
}
```
### 3.5 库存预占 —— **本项目最关键的一组接口**

#### POST /api/products/skus/reserve

由 order-service 在下单时调用。

请求：

```json
{
  "orderId": "O50001",
  "expireAt": "2026-10-20 21:30:00",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

响应 `data`：

```json
{
  "reservationId": "R60001",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

**实现要求**：

```sql
-- 每个 SKU 一条，先到先得；任一条失败则回滚整批
UPDATE sku
SET stock_locked = stock_locked + #{quantity},
    stock_available = stock_available - #{quantity},
    version = version + 1
WHERE sku_id = #{skuId}
  AND stock_available >= #{quantity};
```

**影响行数为 0 表示库存不足**，返回 `30003`，调用方必须整体回滚（BR-15 不得留下半成品订单）。

**幂等要求**：同一 `orderId` 重复调用，返回首次的 `reservationId`，不重复扣减（利用 `orderId` 唯一索引）。

#### POST /api/products/skus/release

订单超时取消或买家主动取消时调用。

请求：

```json
{ "orderId": "O50001" }
```

响应 `data`：`{ "released": true }`

**实现要求**：

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    s.stock_available = s.stock_available + r.quantity,
    r.status = 'RELEASED'
WHERE r.status = 'LOCKED';
```

> BR-17：释放必须幂等，重复调用不得重复回补。靠 `r.status = 'LOCKED'` 这个条件保证，已释放的不会再匹配。

#### POST /api/products/skus/confirm

支付回调成功后调用，把预占转为真实扣减。

请求：`{ "orderId": "O50001" }`

响应 `data`：`{ "confirmed": true }`

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    r.status = 'CONFIRMED'
WHERE r.status = 'LOCKED';
```

#### POST /api/products/skus/refund-restock

退款审核通过后由 payment-service 调用，把已扣减的库存加回可售数量（BR-28）。

请求：`{ "orderId": "O50001" }`

响应 `data`：`null`（成功即代表已回补或无需回补）

**幂等要求**：先用条件更新把预占状态从 `CONFIRMED` 改为 `REFUNDED`，只有更新成功的那一次才真正加库存。重复调用时预占已不是 `CONFIRMED`，直接返回，不会重复加库存。

```sql
-- 1. 抢占状态，保证只有一个调用者回补
UPDATE stock_reservation SET status = 'REFUNDED'
WHERE order_id = #{orderId} AND status = 'CONFIRMED';

-- 2. 按预占明细逐 SKU 回补（仅在第 1 步影响行数 > 0 时执行）
UPDATE sku SET stock_available = stock_available + #{quantity}
WHERE sku_id = #{skuId} AND is_deleted = 0;
```

> **变更说明（2026-10-27）**：本节为新增。原契约 6.5 写了「退款成功后按退款明细回补库存」，
> 但未定义接口，payment-service 也未实现，导致退款后库存不恢复。现补齐接口与幂等要求。
>
> **实现已落地（#40）**：`StockController#refundRestock` + `StockService#refundRestock`，由 payment-service
> `RefundServiceImpl` 在「全额退款审核通过、事务提交后」调用。三处与上文 SQL 示意略有差异，按实现理解：
> ① 预占记录不存在（`30004`）时直接返回错误，不静默成功；② 预占状态不是 `CONFIRMED` 时直接返回成功（无需回补）；
> ③ 状态抢占用的是带前后状态条件的 `updateStatus(orderId, CONFIRMED, REFUNDED, now)`，效果等价。
> 请求体字段为 `{ "orderId": "..." }`（复用 `ConfirmStockRequest`），与其他三个内部库存接口一致。

### 4.5 order-service 如何取购物车项

- 没有使用「批量内部接口」是有意的取舍。订单一次最多结算 50 条（`MAX_CART_ITEMS`），拉全量购物车的额外开销可以接受，换来的是**不必新增接口、不必改 cart-service**
- `X-User-Id` 由网关注入，order-service 内部调用时直接透传当前买家 ID
- **`X-Internal-Token` 在这里没有传、cart-service 也没有校验**。`/cart/**` 的隔离目前只靠网关不暴露，见 7 章「内部调用鉴权」

> 两个批量内部接口。实际实现（order-service `CartClient`）采用上述复用公开接口的方式，
> 已验证可行且无需改动 cart-service，故契约按实现同步修订。

### 5.3 提交订单 —— 最关键的接口

**请求头必须带**：`Idempotency-Key: <UUID>`

请求：

```json
{
  "addressId": "A2001",
  "cartItemIds": ["I80001", "I80002"]
}
```

**不要从前端传价格和总金额**，服务端自己算（防止篡改）。

响应 `data`：

```json
{
  "orderId": "O50001",
  "orderNo": "2026102012345678901",
  "payAmount": 11800,
  "expireAt": "2026-10-20 21:30:00"
}
```

**服务端处理顺序（写代码严格按这个顺序）**：

```
1. 校验幂等令牌，已处理则直接返回首次结果     ← 命中已有的 key 不算错误，返回原数据
2. 调用 cart-service 取购物车，按 cartItemIds 过滤（未勾选 / 已失效的条目直接报错）
3. 调用 product-service 取商品详情，校验状态与价格，算总额
   └─ 一次只能结算同一卖家的商品，否则返回 10001
4. 创建订单主记录（status = PENDING_PAYMENT）与明细（价格快照、标题快照），同一本地事务
5. 调用 product-service 预占库存
   ├─ 成功：标记幂等 key 为 SUCCESS，返回
   └─ 失败：软删除订单主记录与明细、释放幂等 key，并把订单写入库存释放补偿表，再返回错误码
6. 逐条调用 cart-service 删除已下单的购物车项（失败只记 warn 日志，不影响下单结果）
```

- **没有「生成超时取消任务」这一步**：订单自带 `expire_at`（下单时间 + `order.timeout.minutes`），由 `OrderTimeoutJob` 定时扫描，见 5.7
- 预占失败时调用的是**软删除**（`is_deleted = 1`），不是物理删除；同时会写补偿任务，防止「预占请求超时但下游稍后提交」留下悬挂库存

**为什么先建订单再预占库存**：预占失败时只需删掉订单，回滚范围最小。反过来先预占再建单，如果建单失败，就要额外调用释放接口，多一次可能失败的远程调用。

> BR-14：订单号全局唯一且不可枚举 —— 用「日期 + 雪花 ID」，不用自增。
> BR-12：金额以提交瞬间的价格快照为准。
> BR-13：收货地址快照存入订单。

### 5.6 内部接口：支付成功 / 退款成功通知

payment-service 调用 order-service 的两个内部通知接口。**当前实现只传路径参数 `orderId`，请求头 `X-Internal-Token` 由 payment-service 的 Feign 拦截器按配置统一附加，order-service 侧不校验该令牌**（见 7 章「内部调用鉴权」）。

#### POST /api/orders/{orderId}/paid

payment-service 在回调处理成功后调用，通知订单「钱已到账」。

```
POST /api/orders/{orderId}/paid
X-Internal-Token: <内部令牌>      # 由 Feign 拦截器附加，order-service 当前未校验
```

请求体：**无**（金额、支付单号以 payment-service 本地已落库的支付单为准，order-service 不再二次核对）

响应 `data`：`null`，成功即 HTTP 200 + `code = 0`

**要求**：

- 用**条件更新**：`UPDATE order SET status='PAID', paid_at=? WHERE order_id=? AND status='PENDING_PAYMENT'`
- 订单已是 `PAID` → 直接返回成功，**不报错**（重复回调导致，属正常幂等场景）
- 订单是 `CANCELLED` → 返回 `50003`（订单状态不允许该操作）；payment-service 捕获后自主发起退款，不依赖这个报错（BR-18）
- 影响行数 0 且重读后仍不是 `PAID` → 返回 `50003`

> **与 v1.2 的差异**：5.6 原先写的「请求体含 `paymentId` / `payNo` / `amount` / `paidAt`、金额不一致返回 `10001`、`CANCELLED` 返回 `10003`」并未实现。
> 实际 `OrderController#paid` 只接收 `orderId`，`OrderService#markPaid` 也不接收金额；金额一致性由 payment-service 回调侧核对（6.5 第 4 步，返回 `60003`）。

#### POST /api/orders/{orderId}/refunded

退款审核通过后由 payment-service 调用，把订单置为已退款。

```
POST /api/orders/{orderId}/refunded
X-Internal-Token: <内部令牌>      # 由 Feign 拦截器附加，order-service 当前未校验
```

请求体：**无**

响应 `data`：`null`，成功即 `code = 0`

**规则**：

- 订单已是 `REFUNDED` → 直接返回成功（幂等）
- 只有 `PAID` / `SHIPPED` / `COMPLETED` 可置为 `REFUNDED`，其他状态返回 `50003`
- 用条件更新保证并发下不会被重复改状态

> 触发条件（以 `RefundServiceImpl` 实现为准）：退款审核**通过**且该支付单**已全额退款**时才通知；
> 订单因超时取消后收到支付回调的自动退款走 `autoRefund`，**不**调本接口（订单状态是 `CANCELLED`，不接受置为 `REFUNDED`）。

### 5.7 超时取消（定时任务）

order-service 内部 `@Scheduled` 每 60 秒扫描一次：

```sql
SELECT order_id FROM `order`
WHERE status = 'PENDING_PAYMENT'
  AND created_at < DATE_SUB(NOW(), INTERVAL 30 MINUTE)
  AND is_deleted = 0
LIMIT 100;
```

对每笔订单：

```
1. 条件更新：UPDATE `order` SET status='CANCELLED'
   WHERE order_id=? AND status='PENDING_PAYMENT'   ← 影响行数 0 说明被并发改了，放弃
2. 更新成功才调用 product-service 释放库存
3. 释放失败不阻塞，写入补偿任务表，由定时任务退避重试（见 9.1）
```

> **不加分布式锁**。取消的并发安全由「数据库条件更新（CAS）」保证：只有把状态从 `PENDING_PAYMENT`
> 改成 `CANCELLED` 的那个调用者才继续释放库存，其余调用直接返回 `false`。
> 同一订单的重复释放由 product-service 侧的预占状态条件更新兜底（3.5）。

> BR-16：超时时限默认 30 分钟，可配置（`order.timeout.minutes`）；扫描间隔 `order.timeout.scan-interval-ms`（默认 60 秒）、单批条数 `order.timeout.batch-size`（默认 100）。

- 只接受白名单内的键，其余直接返回 `10001`，**不会**触发配置中心请求
- 取值先做范围校验，非法值不发布
- 每次真实变更写入 `config_audit` 表：操作人、配置键、原值、新值、时间
- 业务侧通过 `PlatformConfigService#currentLong` 实时回源（非缓存），所以改完立即生效

> **变更说明（2026-10-27）**：本节为 Issue #43 新增。此前管理端「系统配置」页只把参数存在浏览器
> localStorage，改了不影响任何服务；现在改为 Nacos 托管并留痕。

| 接口 | 用途 | 请求体 |
| --- | --- | --- |
| `POST /api/payments/mock/pay` | 模拟支付成功，触发回调 | `{ "paymentId": "PAY90001" }` |
| `POST /api/payments/mock/duplicate` | 重复推送指定交易号的回调，验证幂等 | `{ "tradeNo": "MOCK2026..." }` |
| `POST /api/payments/mock/refund` | 模拟退款：创建退款单并直接审核通过 | `{ "paymentId": "PAY90001", "amount": 5900, "reason": "商品有瑕疵" }` |

### 6.5 支付回调 —— 第二关键接口

```
POST /api/payments/callback
```

**处理顺序（严格按此执行）**：

```
1. 验签 md5(tradeNo + payNo + amount + MOCK_SECRET)
   └─ 失败：记录日志，返回 60002，不更新任何状态
2. 按 payNo 查支付单
   └─ 支付单不存在：返回 60001
3. 幂等去重（本地事务内）
   └─ INSERT INTO payment_callback(trade_no, ...)
      UNIQUE KEY uk_trade_no (trade_no)
   └─ 唯一键冲突 = 重复回调，按幂等成功返回，不重复处理（BR-24）
4. 金额核对
   └─ 回调金额 != 支付单金额：流水标记 AMOUNT_MISMATCH，返回 60003，不更新订单（BR-25）
5. 更新支付单 status = SUCCESS, paidAt = now（条件更新；已被并发处理则按幂等成功返回）
6. 事务提交后，再按订单当前状态决定后续：
   └─ 订单是 PENDING_PAYMENT：POST /orders/{orderId}/paid 置 PAID，
      再 POST /products/skus/confirm 确认扣减
   └─ 订单是 CANCELLED / REFUNDED：已超时取消或已退款，发起自动全额退款（BR-18），不再通知置 PAID
7. 返回成功
```

> 回调状态只接受 `SUCCESS`，其他值返回 `10001`。远程调用（通知订单、确认库存）放在本地事务提交之后，
> 避免占用数据库连接，也避免远程失败回滚已完成的支付状态；失败只记 error 日志、待人工补偿。

**回调报文示例**（MOCK 渠道）：

```json
{
  "tradeNo": "ALI20261020000001",
  "payNo": "P202610200001",
  "amount": 11800,
  "status": "SUCCESS",
  "payTime": "2026-10-20 21:05:33",
  "sign": "xxx"
}
```

**幂等表的表结构**：

```sql
CREATE TABLE payment_callback (
  callback_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
  trade_no      VARCHAR(64) NOT NULL,
  payment_id    VARCHAR(32) NOT NULL,
  raw_payload   TEXT,
  sign_verified TINYINT(1) NOT NULL DEFAULT 0,
  received_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_trade_no (trade_no)
);
```

> `UNIQUE KEY uk_trade_no` 是去重的唯一保障。**不要用「先查再插」的写法**，并发下会有窗口期，必须靠数据库唯一约束。

### 6.6 退款

```json
POST /api/payments/{paymentId}/refund
{ "amount": 5900, "reason": "商品有瑕疵" }
```

- 退款金额不得超过实付金额（BR-26）
- 同一订单允许多次部分退款，累计不超过实付（BR-27）
- 退款成功后，按退款成功的明细回补库存（BR-28）

**退款到「已退款」的完整链路（已实现，#40）**：

```
1. 买家申请退款 → 生成 PENDING 退款单；同时用 payment.refunded_amount 条件更新预占额度，
   并发申请也不会超过实付（BR-26 / BR-27）
2. 卖家或管理员审核通过（PUT /api/payments/refunds/{refundId}/audit，body { approved, remark }）
3. 该支付单累计退款达到实付 → 支付单置 REFUNDED，事务提交后依次触发：
   ├─ POST /orders/{orderId}/refunded     把订单置为 REFUNDED（5.6）
   └─ POST /products/skus/refund-restock  按预占明细回补库存（3.5，失败只记日志、需人工补偿）
4. 审核驳回 → 释放第 1 步预占的退款额度，支付单回到 SUCCESS
```

- 只有**全额退款**才回补库存并通知订单；部分退款不改变订单状态，也不回补库存
- 库存回补幂等由 product-service 侧「预占状态 `CONFIRMED` → `REFUNDED`」的条件更新保证，重复调用不会重复加库存
- 订单超时取消后又收到支付成功回调时，payment-service 自动全额退款（`autoRefund`），此时**不调用** `/orders/{orderId}/refunded`
- **审核归属（v1.4）**：`SELLER` 只能审核 `refund.seller_id = 当前登录用户` 的退款，审核他店退款返回 `10003`；`ADMIN` 不受限
- **售后复用（v1.5）**：售后单中 `REFUND_ONLY` 在卖家同意时立即复用本退款流程；`RETURN_REFUND` 在卖家确认收货后复用；两种类型都走 `payment.refunded_amount` 条件预占，满额退款才通知订单并回补库存

### 6.8 售后中心（v1.5）

#### 6.8.1 类型与状态

| 类型 | 说明 |
| --- | --- |
| `REFUND_ONLY` | 仅退款，卖家同意后立即退款 |
| `RETURN_REFUND` | 退货退款，买家先退货，卖家确认收货后退款 |
| `EXCHANGE` | 换货，买家退货后卖家重新发货 |

| 状态 | 说明 |
| --- | --- |
| `PENDING` | 待卖家处理 |
| `APPROVED` | 卖家已同意（退货退款 / 换货） |
| `BUYER_SHIPPED` | 买家已回填退货物流 |
| `SELLER_RECEIVED` | 卖家已确认收到退货（退款执行前的内部过渡态） |
| `REFUNDED` | 退款完成（退款类型终态） |
| `COMPLETED` | 换货完成（换货类型终态） |
| `REJECTED` | 卖家/管理员驳回（终态） |

允许的状态流转：

```
REFUND_ONLY:    PENDING -> (APPROVED) -> REFUNDED | REJECTED
RETURN_REFUND:  PENDING -> APPROVED -> BUYER_SHIPPED -> SELLER_RECEIVED -> REFUNDED | REJECTED
EXCHANGE:       PENDING -> APPROVED -> BUYER_SHIPPED -> COMPLETED | REJECTED
```

> `REFUND_ONLY` 的 `APPROVED`、`RETURN_REFUND` 的 `SELLER_RECEIVED` 是同一事务内的过渡态，通常不会持久化给前端看到。

#### 6.8.4 卖家/管理员处理

```
PUT /api/payments/after-sales/{ticketId}/audit
{ "approved": true, "remark": "同意" }
```

- 只有 `PENDING` 可审核；驳回后进入 `REJECTED`，释放进行中标记
- `REFUND_ONLY` 同意后立即复用 6.6 退款流程，完成后状态 `REFUNDED`
- `RETURN_REFUND` / `EXCHANGE` 同意后状态 `APPROVED`，等待买家退货

```
PUT /api/payments/after-sales/{ticketId}/return-shipment
{ "trackingNo": "SF1234567890" }
```

- 仅买家本人、类型为 `RETURN_REFUND` / `EXCHANGE`、状态为 `APPROVED` 时可用
- 状态变为 `BUYER_SHIPPED`；重复提交同一物流单号幂等，不同单号拒绝

```
PUT /api/payments/after-sales/{ticketId}/receive
{ "remark": "已收到退货" }
```

- 仅 `RETURN_REFUND`、状态为 `BUYER_SHIPPED`（或重试时 `SELLER_RECEIVED`）可用
- 卖家确认收货后执行退款，状态变为 `REFUNDED`；退款金额/额度规则与 6.6 相同

```
PUT /api/payments/after-sales/{ticketId}/reship
{ "trackingNo": "SF0987654321", "remark": "已换新寄出" }
```

- 仅 `EXCHANGE`、状态为 `BUYER_SHIPPED` 时可用
- 记录换货物流，状态变为 `COMPLETED`；换货不产生退款，不通知订单退款

#### 6.8.5 并发与兼容

- 所有状态流转使用条件 UPDATE（`WHERE ticket_id=? AND status=前置状态 AND seller_id/buyer_id=?`），影响行数为 0 时重读并按幂等/冲突处理
- 同一订单的进行中售后单由 `after_sale_ticket.uk_order_active (order_id, active_flag)` 唯一键保证；进入终态时 `active_flag` 置 NULL
- 退款金额仍由 `payment.refunded_amount` 条件预占，售后单不能绕过 BR-26 / BR-27
- **存量兼容**：原 `refund` 表与 `POST /payments/{paymentId}/refund` 流程保持不变，售后单是增量表；历史仅退款数据无需迁移
- 退款成功后订单通知与库存回补由 6.6 的统一链路处理：只有全额退款才触发，部分退款不触发
- 错误码：售后单不存在 `60005`；状态不允许 `60006`；金额超过剩余可退 `60004`；越权 `10003`

## 七、服务间调用关系

```
                    ┌──────────┐
        前端 ──────►│ gateway  │
                    └────┬─────┘
                         │
     ┌───────────┬───────┼────────┬────────────┐
     ▼           ▼       ▼        ▼            ▼
  user       product    cart     order      payment
     ▲           ▲       ▲         │            │
     │           │       │         │            │
     │           └───────┼─────────┘            │
     │    预占/释放/确认  │  查商品、清购物车     │
     │                   │                      │
     └─── 查地址 ────────┘                      │
                                                │
     order ◄────── 支付成功通知 ────────────────┘
```

| 调用方 | 被调方 | 接口 | 时机 |
| --- | --- | --- | --- |
| order | user | GET /users/{userId}/addresses | 下单取地址快照 |
| order | cart | GET /cart | 下单时拉取购物车（4.5） |
| order | product | POST /products/skus/reserve | 下单预占 |
| order | product | POST /products/skus/release | 取消 / 超时 |
| order | cart | DELETE /cart/items/{cartItemId} | 下单后逐条清购物车（4.5） |
| payment | order | GET /orders/{orderId} | 发起支付时取金额 |
| payment | order | POST /orders/{orderId}/paid | 回调成功后通知（5.6） |
| payment | order | POST /orders/{orderId}/refunded | 全额退款审核通过后通知（5.6） |
| payment | product | POST /products/skus/confirm | 支付成功后确认扣减 |
| payment | product | POST /products/skus/refund-restock | 全额退款后回补库存（3.5） |
| cart | product | GET /products/{productId} | 展示时取价格库存 |

> 定时任务不算「调用关系」但同属跨库协作：order-service 的 `OrderTimeoutJob` 兜底释放未释放的已取消订单；
> product-service 的 `releaseExpiredReservations()` 兜底释放过期预占。

**内部调用鉴权**：服务间调用带内部令牌 `X-Internal-Token: <配置的密钥>`，网关不转发这个头，外部无法伪造。**当前各服务的实际状态不同，不能一律宣称“已校验”**：

| 被调方 | 实际校验情况 | 代码位置 |
| --- | --- | --- |
| product-service `/products/skus/{reserve,release,confirm,refund-restock}` | **已校验**：配置了 `product.internal-token`（即 `INTERNAL_TOKEN`）时，请求头必须与之相同，否则返回 `10003`；未配置时放行（开发期默认不校验） | `InternalTokenVerifier` |
| order-service `/orders/{orderId}/paid`、`/refunded` | **未校验**：接口只接收 `orderId`，没有读取或比对 `X-Internal-Token`；令牌由调用方附加但服务端不检查 | `OrderController` |
| cart-service `/cart`、`/cart/items/{cartItemId}` | **未启用**：`WebConfig` 与 `CartController` 都没有内部令牌校验；order-service 调用时也不传该头部。所谓“内部接口”目前只靠网关不暴露 `/cart/**` 来隔离，不是令牌鉴权 | `CartController`、`WebConfig` |

> 结论：只有 product-service 的库存内部接口真正启用了令牌校验。order-service 与 cart-service 属于**待补**项，
> 在补齐之前不得在文档、答辩或测试报告里声称内部令牌已全链路生效。

> **变更说明（2026-10-22）**：本表按实际实现同步。5.6 的 `/orders/{orderId}/paid` 为新增；
> order 取购物车改为复用 cart 的公开接口（见 4.5），不再使用 `/internal/` 前缀的批量接口。
>
> **变更说明（2026-10-27）**：补上支付成功后的 `refunded` 通知与退款回补库存两条调用（#40），
> 并把内部令牌的实际校验状态逐服务写清（见上表）。

内部接口令牌校验状态（配置 `INTERNAL_TOKEN` 后强制比对；未配置时仅开发环境放行）：

| 服务 | 接口 | 校验状态 | 说明 |
| --- | --- | --- | --- |
| product-service | POST /products/skus/reserve、/release、/confirm | 已校验 | 与 product-service 的 `InternalTokenVerifier` 一致 |
| order-service | POST /orders/{orderId}/paid、/refunded | 已校验 | payment-service 必须传 `X-Internal-Token` |

> 第 1、2 项曾定稿为「Redis List 异步队列 + Redis 分布式锁」，但**没有落地**，代码里也没有引入 Redis 客户端或队列代码。
> 现按实际实现改写；Redis 只作为**后续可选基础设施**（`src/docker/docker-compose.yml` 里留了一个 redis 服务，
> 但没有任何微服务依赖它），本文档不宣称 Redis 已被使用或已部署。

### 9.1 服务间通信

**全部用 OpenFeign 同步调用，不做消息队列，也不用 Redis List 做异步队列。** 理由：

- 下单、预占库存这类操作**必须知道结果**（成功还是库存不足），异步反而麻烦；
- 一个组件少一层排查成本，出问题直接看调用链日志；
- 课程作业规模下，RPC 的耦合风险远小于引入 MQ 的运维成本。

**取消/超时后释放库存的补偿原则仍然成立**，但实现不用队列，而是「同步调用 + 失败落表 + 定时任务补偿」：

```
1. 取消或超时把订单置为 CANCELLED（条件更新）后，同步调用 product-service /products/skus/release
2. 释放成功 → 订单表 inventory_released = 1
3. 释放失败（超时、下游不可用等）→ 写入 order 服务本库的 compensation 表（状态 PENDING、下次重试时间）
4. OrderTimeoutJob 每轮（默认 60 秒）额外做两件事：
   - retryUnreleasedInventory()：捞 inventory_released = 0 的已取消订单重新释放
   - retryCompensations()：按 next_retry_at 捞到期的补偿任务重试
5. 补偿任务指数退避（30s 起，最多 300s），累计 8 次仍失败标为 DEAD，转人工处理
6. product-service 侧另有 releaseExpiredReservations() 定时任务（默认 60 秒）兜底过期的 LOCKED 预占
```

对应代码：`CompensationService`、`OrderTimeoutJob`、`OrderService#releaseInventory` / `#retryUnreleasedInventory` / `#retryCompensations`。
幂等由两层条件更新保证：订单侧「CANCELLED 才释放一次」、库存侧「预占状态 `LOCKED` → `RELEASED` 只有一次成功」。

**Feign 超时已配置**（各服务 `application.yaml` 的 `spring.cloud.openfeign.client.config.default`）：连接 2s、读取 5s。网关侧下游超时为连接 2s、读取 6s。调用方捕获异常后转成业务错误码（如 `10005` 服务暂不可用），不做框架级降级。

### 9.2 并发控制（原「分布式锁」）

**当前没有分布式锁，也没有引入 Redis 或 Redisson。** 并发安全全部由数据库层保证，三处典型用法：

| 场景 | 做法 | 代码位置 |
| --- | --- | --- |
| 库存预占 | `UPDATE sku SET stock_locked = stock_locked + ? , stock_available = stock_available - ? WHERE sku_id = ? AND stock_available >= ?`，影响行数 0 即库存不足 | `StockService#reserve`（见 3.5） |
| 订单状态流转 | 条件更新 `WHERE order_id = ? AND status = ?`，影响行数 0 说明被并发改过，放弃本轮 | `OrderMapper#markPaid / #markCancelled / #markRefunded` |
| 请求幂等 | `idempotency` 表 `idem_key` 唯一键；`payment_callback` 表 `uk_trade_no` 唯一键；退款金额靠 `payment.refunded_amount` 条件更新预占 | `OrderService#create`、`CallbackTxService`、`RefundServiceImpl` |

**为什么这样够用**：上述场景的并发点都落在同一行数据的同一次条件更新上，数据库的行锁 + 唯一约束天然提供原子性；单库单服务的前提下，引入分布式锁只多一层故障点（锁失效、死锁、锁服务不可用）。

**如果后续确实要多实例并行同一订单的操作**，再引入 Redis 锁，但要按 9.2 早期的定稿原则来：`SET key value NX EX` 加锁、解锁校验持有者并用 Lua 保证原子性。Redis 目前不在已部署的基础设施里，不作为本阶段的实现要求。

### 9.3 支付模拟

不接真实支付宝/微信，自建 `MOCK` 渠道。

**流程**：

```
1. 用户点"支付" → payment-service 创建支付单（channel = MOCK）
2. 返回"收银台"页面，显示金额和一个【模拟支付成功】按钮
3. 点击按钮 → 前端调用 POST /api/payments/mock/pay
4. payment-service 按真实回调的完整流程走一遍：
   构造回调报文 → 验签（MOCK 用固定的签名算法）→ 幂等去重 → 更新状态
```

**关键**：模拟支付**必须走完整的回调流程**，不能直接把支付单状态改成 SUCCESS。否则回调的去重、验签、金额核对这些逻辑等于没测，实验四的测试报告也就没有内容。

**MOCK 签名算法**（韬哥实现，需与前端约定）：

```
sign = md5(tradeNo + payNo + amount + MOCK_SECRET)
```

`MOCK_SECRET` 从环境变量读，不硬编码。

**手动补充接口**：

| 接口 | 用途 |
| --- | --- |
| POST /api/payments/mock/pay | 模拟支付成功，触发回调 |
| POST /api/payments/mock/refund | 模拟退款：创建退款单并审核通过（请求体 `paymentId + amount`，详见 6.4） |
| POST /api/payments/mock/duplicate | 重复推送同一回调，用于验证幂等 |

第三个接口是给实验四测试用的，可以反复触发重复回调验证去重是否生效。

## 十、数据库隔离规则

**五个服务各用一个独立的库，禁止跨库查询。**

| 服务 | 库名 | 包含的表 |
| --- | --- | --- |
| user-service | `mall_user` | user、address |
| product-service | `mall_product` | product、sku、category、stock_reservation |
| cart-service | `mall_cart` | cart、cart_item |
| order-service | `mall_order` | `order`、order_item |
| payment-service | `mall_payment` | payment、payment_callback、refund、after_sale_ticket |

### 10.1 为什么必须分库

微服务的核心约束是「每个服务独占自己的数据」。分库不是形式主义，它带来两个实质好处：

1. **服务真正可独立演进**。商品表加字段不影响订单服务；商品库换存储引擎不用动别人。
2. **边界清晰，防止偷懒**。如果不能 JOIN，就逼着你通过接口拿数据，服务边界才立得住。

如果五个服务共用一个库、代码里随便 JOIN，那本质上还是单体应用，实验二画的微服务架构图就是假的，答辩时很容易被问穿。

### 10.2 从校园二手交易平台搭到商城分库，代码怎么改

既有原型 `campusEasy` 是单库单表，复用它的代码时按下表处理：

| 原型的写法 | 分库后怎么改 | 能复用吗 |
| --- | --- | --- |
| 实体类（Entity）、Mapper 单表 CRUD | 原样搬，只改库配置 | ✅ 直接复用 |
| 单表条件查询（按 id 查、按条件筛选） | 原样搬 | ✅ 直接复用 |
| **多表 JOIN 查询** | **拆成两次接口调用，在 Service 层组装** | ❌ 必须重写 |
| 分布式事务（下单时同时改订单表和库存表） | 改成「本地事务 + 调用库存服务 + 失败补偿」 | ❌ 必须重写 |
| 统一返回结构、拦截器、工具类 | 原样搬 | ✅ 直接复用 |

**典型例子**：原型里「查询订单并带出商品名称」可能是一条 JOIN：

```sql
-- ❌ 分库后不可用
SELECT o.*, p.title FROM `order` o
LEFT JOIN product p ON o.product_id = p.product_id
WHERE o.buyer_id = ?
```

改成：

```java
// ✅ 先查订单
List<Order> orders = orderMapper.selectByBuyerId(buyerId);
// ✅ 再调商品服务批量取标题
List<String> productIds = orders.stream().map(Order::getProductId).toList();
Map<String, ProductDTO> products = productClient.batchGet(productIds);
// ✅ 在 Service 层组装
```

**注意**：订单表其实**已经存了价格和标题快照**（`order_item.product_title`、`price_snapshot`），历史订单不需要再查商品服务，这是 BR-12 带来的好处。只有展示「实时价格」的场景才需要调商品服务。

### 10.3 多数据源怎么配

每个服务只连**自己的库**，不需要配多数据源——一个服务一个库，普通 Spring Boot 配置即可：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mall_order?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:}
```

**不要为了省事让一个服务连多个库**，那等于绕过了服务边界。

### 10.4 本地怎么建这五个库

```sql
CREATE DATABASE IF NOT EXISTS mall_user    DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_product DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_cart    DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_order   DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_payment DEFAULT CHARSET utf8mb4;
```

每个服务的建表语句放各自的 `src/main/resources/schema.sql`，启动时自动执行。

### 11.1 店铺资料与营业状态（#49）

店铺状态是营业状态的**唯一真相**，存于 `mall_user.shop`，一个卖家一条（`uk_shop_seller`）。

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| GET | /api/shops/mine | 卖家查看自己的店铺（不存在时按昵称自动初始化） | 卖家 |
| PUT | /api/shops/mine | 卖家维护店铺资料 | 卖家 |
| GET | /api/shops | 分页查询店铺（keyword 匹配名称或卖家 ID，status 过滤） | 管理员 |
| PUT | /api/shops/{shopId}/status | 停用 / 恢复店铺 | 管理员 |
| GET | /api/shops/seller/{sellerId} | 按卖家查店铺（供 order-service 下单校验） | 内部 |

`data` 统一为 `ShopResponse`：

```json
{
  "shopId": "SH50001",
  "sellerId": "U10002",
  "name": "数码小铺",
  "logo": "/images/shop1.png",
  "description": "主营键鼠外设",
  "contactPhone": "13800138000",
  "contactWechat": "mall_shop_1",
  "status": "ACTIVE",
  "createdAt": "2026-10-28 20:00:00",
  "updatedAt": "2026-10-28 20:10:00"
}
```

**PUT /api/shops/mine** 请求：

```json
{
  "name": "数码小铺",
  "logo": "/images/shop1.png",
  "description": "主营键鼠外设",
  "contactPhone": "13800138000",
  "contactWechat": "mall_shop_1"
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| name | 是 | 1-64 字 |
| logo | 否 | ≤255 字，图片地址（可用 `POST /api/products/images` 上传） |
| description | 否 | ≤255 字 |
| contactPhone | 否 | 手机号或区号座机：`^$|^1[3-9]\d{9}$|^0\d{2,3}-?\d{7,8}$` |
| contactWechat | 否 | ≤64 字，微信 / 旺旺等在线联系方式 |

保存为**整体覆盖**语义：`logo`、`description`、`contactPhone`、`contactWechat` 传空字符串或 `null` 即清空原值，
前端「清除头像 / 清空简介」保存后能真正落库（`UpdateInfo` 不做非空跳过）。

**PUT /api/shops/{shopId}/status** 请求：

```json
{ "status": "SUSPENDED" }
```

`status` 只允许 `ACTIVE` / `SUSPENDED`，其余返回 `10001`；店铺不存在返回 `20007`。

**停用 / 恢复的跨服务影响（一致性约定）**：

1. user-service 先更新 `shop.status`；
2. 再通过 Feign 调 `POST /products/internal/seller-visibility`（带 `X-Internal-Token`），把该卖家 `ON_SALE` 的商品批量置为 `SUSPENDED`，恢复时反向改回 `ON_SALE`；
3. 同步失败则**回滚 `shop.status`** 并返回 `10005`，避免出现「店铺已停用但商品还在卖」；
4. product-service 在卖家上架、管理员审核通过时用 ShopClient 二次确认店铺状态，停用则落 `SUSPENDED` 并返回 `30006`；
5. order-service 下单时按 `sellerId` 再查一次店铺状态，停用返回 `30006`，作为 Feign 同步失败时的兜底。

> Issue #49 要求「商品可见性与下单校验在 product / order 侧的落点与 yy 对齐后实施」。
> 当前落点：product-service 商品状态新增 `SUSPENDED`（不改商品表结构）、order-service 增加下单前校验，均已在 Issue 评论说明。
> 商品服务不可用时按「正常营业」放行，避免单服务调试与集成测试整体不可用。

### 11.2 头像上传（#51）

```
POST /api/users/avatar
Content-Type: multipart/form-data
字段：file
```

| 校验项 | 规则 |
| --- | --- |
| 格式 | 只允许 jpg / jpeg / png / webp / gif |
| 大小 | 不超过 5 MB（`spring.servlet.multipart.max-file-size` 同步为 5MB） |
| 文件名 | UUID 重命名，防同名覆盖与路径穿越 |
| 存储 | `uploads/avatars/`，静态映射 `/avatars/**`，与商品图片同一套方案 |

服务端落盘后**直接写回用户档案**，响应为上传结果：

```json
{ "avatar": "/avatars/4f1c9b24e7ab4c1f9d0b8e2a6c5d3f10.png" }
```

前端拿到返回值即可刷新头像，无需再调 `PUT /api/users/me`；失败返回 `10001`（格式 / 大小）或 `10005`（写盘失败）。

### 11.3 收货地址默认规则（#51）

- 用户的第一条地址**自动成为默认地址**；
- `PUT /api/users/addresses/{addressId}/default` 切换默认，同一用户只保留一条；
- 删除当前默认地址后，自动把剩余最早的一条提升为默认；
- 编辑地址不会取消默认标记（请求体可不传 `defaultAddress`）；
- 列表每条同时输出 `isDefault` 与 `defaultAddress`（同值）；
- 历史数据若一条默认都没有，`GET /api/users/addresses` 会把最早一条补为默认（自愈，无需手工修数据）；
- 下单页默认选中默认地址，没有默认时退回第一条。

地址不存在返回 `20006`。

### 11.4 收藏（#52）

存储：`mall_user.favorite`，唯一键 `(user_id, product_id)`。商品标题、图片、价格、状态**通过商品接口批量取，不跨库 JOIN**。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/favorites | 收藏商品，重复收藏幂等返回已有记录 |
| DELETE | /api/favorites/{productId} | 取消收藏（原本未收藏也返回成功） |
| GET | /api/favorites?page=1&size=20 | 收藏夹分页 |
| GET | /api/favorites/status?productId= | 查询当前用户是否已收藏 |

`POST /api/favorites` 请求：

```json
{ "productId": "P30001" }
```

商品不存在返回 `10001`；`GET /api/favorites/status` 返回：

```json
{ "productId": "P30001", "favorited": true }
```

分页列表的 `data`：

```json
{
  "page": 1,
  "size": 12,
  "total": 1,
  "list": [
    {
      "favoriteId": "F60001",
      "productId": "P30001",
      "title": "罗技 G102 鼠标",
      "mainImage": "/images/p30001.jpg",
      "price": 5900,
      "status": "SUSPENDED",
      "invalid": true,
      "invalidReason": "店铺已停用",
      "createdAt": "2026-10-28 20:20:00"
    }
  ]
}
```

### 11.5 浏览足迹（#52）

存储：`mall_user.browse_history`，唯一键 `(user_id, product_id)`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/history | 记录一次浏览，同一商品只更新 `visited_at`（去重） |
| GET | /api/history?limit=20 | 最近 N 条，按 `visited_at` 倒序，`limit` 上限 50 |
| DELETE | /api/history/{productId} | 删除单条足迹 |
| DELETE | /api/history | 清空足迹 |

`data` 为数组，元素字段与收藏项一致（`historyId` 代替 `favoriteId`，`visitedAt` 代替 `createdAt`），`invalid` / `invalidReason` 由商品状态计算：

| 商品状态 | invalid | invalidReason |
| --- | --- | --- |
| ON_SALE | false | null |
| PENDING | true | 商品待审核，暂不可购买 |
| OFF_SHELF | true | 商品已下架 |
| REJECTED | true | 商品审核未通过 |
| SUSPENDED | true | 店铺已停用 |
| 查不到（已删除） | true | 商品已删除或不存在 |

### 11.6 商品批量查询（#52 依赖）

```
GET /api/products/batch?ids=P30001,P30002
```

- 供 user-service 组装收藏夹与足迹，**不按状态过滤**（失效商品也要能返回给前端置灰）；
- 单次最多 100 个 ID，超出部分丢弃；重复 ID 先去重；
- 只返回存在的商品，无 SKU 的商品 `price` 为 `0`。

`data` 为数组，元素为 `ProductBriefResponse`：

```json
{
  "productId": "P30001",
  "sellerId": "U10002",
  "title": "罗技 G102 鼠标",
  "mainImage": "/images/p30001.jpg",
  "categoryId": "C10",
  "status": "ON_SALE",
  "price": 5900
}
```

**同步商品可见性（内部）**：

```
POST /api/products/internal/seller-visibility
X-Internal-Token: <INTERNAL_TOKEN>
{ "sellerId": "U10002", "visible": false }
```

响应：`{ "sellerId": "U10002", "visible": false, "affected": 6 }`，`affected` 为被改成 `SUSPENDED`（或恢复成 `ON_SALE`）的商品数。

> 未配置 `INTERNAL_TOKEN` 时不校验令牌，便于本地联调；配置后必须携带匹配值。

### 11.7 分类顺序与详情分类名（#50）

- `GET /api/categories` 返回**扁平列表**，顺序为：顶级分类按 `sort_no` 升序，每个子分类紧随其父级之后，父级已删除的孤儿分类追加在末尾。前端下拉按 `parentId` 是否为空决定是否缩进；
- `GET /api/products/{productId}` 新增 `categoryName`，详情页直接展示，无需前端按 `categoryId` 反查。

### 11.8 前端筛选与地址栏同步（#50）

商品列表把筛选条件写回地址栏，刷新、前进后退、分享链接都能还原对应结果：

```
/products?keyword=鼠标&categoryId=C10&sort=price_asc&minPrice=50&maxPrice=300&page=2
```

| 参数 | 说明 |
| --- | --- |
| keyword | 搜索关键词，输入后 400ms 防抖触发 |
| categoryId | 分类 ID，选项来自 `GET /api/categories` |
| sort | 与 `GET /api/products` 的 sort 一致 |
| minPrice / maxPrice | 页面输入单位为**元**，请求时乘 100 转成**分** |
| page | 页码，>1 时才写入地址栏 |

无结果时展示当前生效的筛选条件并提供「清空筛选条件」一键重置。
