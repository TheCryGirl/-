## 一、总体约定

### 1.1 服务与端口

| 服务 | 端口 | 职责 | 负责人 |
| --- | --- | --- | --- |
| gateway | 9000 | 统一入口、路由、鉴权过滤 | 哭女 |
| user-service | 9001 | 用户、地址、认证 | 来财 |
| product-service | 9002 | 商品、SKU、库存 | yy |
| cart-service | 9003 | 购物车 | fd |
| order-service | 9004 | 订单、状态机 | yy |
| payment-service | 9005 | 支付、回调、退款 | 韬哥 |

前端只访问网关 `http://localhost:9000`，**不直连任何服务**。

### 1.2 路径规则

- 网关对外：`/api/<服务名>/<资源>`，例如 `/api/orders/123`
- 服务内部：不带 `/api` 前缀，例如 order-service 自身监听 `/orders/123`
- 内部服务间调用走 `FeignClient`，不经过网关

### 1.3 统一响应结构

**所有接口**返回这个结构，HTTP 状态码只用于表达协议层结果（200 / 401 / 403 / 500），业务成功与否看 `code`。

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1761000000000
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | int | 0 成功，非 0 失败 |
| message | string | 出错时给用户看的中文提示 |
| data | object | 业务数据，失败时为 null |
| timestamp | long | 服务器毫秒时间戳，用于排查 |

### 1.5 认证

- 登录成功后签发 JWT，前端存放在 `localStorage.token`
- 除白名单接口外，所有请求带 `Authorization: Bearer <token>`
- JWT payload：`{ "userId": "U001", "role": "BUYER", "tokenVersion": 0, "exp": 1761000000 }`
- 第三批撤销机制：角色/状态变更与`user_auth_version.token_version`递增同事务提交；冻结后解冻或角色恢复不复活旧版本令牌。网关逐请求通过内部受保护接口`/users/internal/auth-state/{id}`核对ACTIVE、角色和版本，无正向缓存。无版本旧JWT须重新登录。受保护请求在核验失败/超时/用户服务不可用时401；公开路径降为无身份匿名访问。已经通过核验的在途请求不强制中断；本机制不等于单设备logout黑名单。
- **网关统一校验**，校验通过后把 `userId` / `role` 放进请求头 `X-User-Id` / `X-User-Role` 传给下游服务；下游服务**不再重复解析 JWT**
- JWT 密钥只从环境变量 `JWT_SECRET`（≥ 32 位）读取，未配置时网关与 user-service 启动即失败，配置里不留硬编码默认值

**白名单**（无需令牌即可访问）：

```
POST /api/users/register
POST /api/users/login
POST /api/payments/callback      # 支付回调，靠签名验真而不是登录态
GET  /api/products
GET  /api/products/{productId}   # {productId} 不为 mine / skus / images
GET  /api/categories/**
GET  /images/**
GET  /actuator/**
GET  /avatars/**
OPTIONS **                       # 浏览器跨域预检，不带令牌
```

**白名单不再等于「强制匿名」**：白名单路径上如果带了有效 `Authorization: Bearer <token>`，网关照常解析并注入 `X-User-Id` / `X-User-Role`；令牌缺失或无效时按匿名放行，不返回 401。

> 这样卖家/管理员访问自己的 PENDING 商品（`GET /api/products/{id}`）时下游才拿得到身份，否则会被当成访客拒绝。
> 相关改动见 Issue #38（`JwtAuthFilter`）。

> 商品发布、修改、上下架、审核与 `/api/products/mine` 均需登录，
> 因此不能整体放行 `GET /api/products/**` 之外的任何商品路径。
> 网关按「方法 + 路径」精确判定白名单。

### 1.5.1 要点

- 网关路由转发时统一 `StripPrefix=1`，下游服务收到的路径不带 `/api`
- `/images/**`、`/avatars/**` 原样转发，不加 StripPrefix（静态资源与服务内映射路径一致）
- `/api/products/{x}` 白名单判定时，`mine` / `skus` / `images` / `batch` / `internal` 是功能路径而不是商品 ID，必须登录
- 网关校验通过后覆盖客户端传入的 `X-User-Id` / `X-User-Role`，防止伪造

### 1.7 时间与金额

| 项 | 约定 |
| --- | --- |
| 时间 | `yyyy-MM-dd HH:mm:ss`，统一北京时间 |
| 金额 | **分为单位的整数**（`long`），避免浮点误差。`10050` 表示 100.50 元 |
| ID | 字符串（`String`），不用自增数字，防止被枚举 |

### 1.8 幂等

涉及创建订单、支付这类可能重复提交的接口，必须在请求头带：

```
Idempotency-Key: <UUID>
```

由前端每次提交时生成。服务端按 key 去重，重复请求返回首次的结果（不报错，返回同样内容）。

**约束（与实现一致）**：

- 适用接口：`POST /api/orders`、`POST /api/payments`
- key 长度 8–64 位；缺失返回 `10001`
- 同一个 key 换了请求内容（order-service 比对 `buyerId + addressId + cartItemIds` 的 SHA-256）→ 返回 `50002`，不复用首次结果
- order-service 首次下单失败时会释放该 key，允许用同一个 key 重试；并发重复提交正在处理时返回 `50002`，提示稍后重试

### 1.9 链路追踪（TraceId）

> **补录（2026-11-01）**：本节此前未收录，实现已上线。

**请求头**：`X-Trace-Id`

| 情况 | 行为 |
| --- | --- |
| 请求带 `X-Trace-Id` 且长度 ≤ 64 | 原样沿用 |
| 未带或格式不合法 | 网关自动生成 32 位十六进制 |

**响应**：网关在响应头**回写** `X-Trace-Id`，前端可在出错时展示给用户便于排查。

**实现路径**：

- `gateway` 的 `TraceIdFilter`（order = -200，早于 JWT 鉴权的 -100）
- 五个业务服务各有 `TraceIdFilter`，从请求头恢复到 MDC，请求结束清理
- 服务间 Feign 调用由 `TraceFeignConfig` 的 `RequestInterceptor` 透传
- 日志格式含 `[%X{traceId:-}]`，未获取到 traceId 时显示为空

**排查方式**：拿到一个 traceId 后，在各服务日志里按该值 grep，即可串起整条调用链。

### 2.3 关键接口详情

#### POST /api/users/register

请求：

```json
{
  "account": "zhangsan",
  "password": "abc123456",
  "nickname": "张三",
  "phone": "13800138000"
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| account | 是 | 4-20 位，字母数字下划线 |
| password | 是 | 6-32 位 |
| nickname | 是 | 2-20 位 |
| phone | 否 | 11 位数字 |

响应 `data`：

```json
{ "userId": "U10001" }
```

失败：`20002` 账号已存在、`20003` 昵称被占用。

> BR-01 账号全局唯一且不可修改、BR-02 密码不得明文存储。

#### POST /api/users/login

请求：

```json
{ "account": "zhangsan", "password": "abc123456" }
```

响应 `data`：

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "user": {
    "userId": "U10001",
    "account": "zhangsan",
    "nickname": "张三",
    "role": "BUYER",
    "avatar": null
  }
}
```

失败：`20001` 账号或密码错误、`20004` 账号已冻结。

#### GET /api/users/{userId}/addresses → 供 order-service 内部调用

响应 `data`：

```json
[
  {
    "addressId": "A2001",
    "receiver": "张三",
    "phone": "13800138000",
    "province": "天津市",
    "city": "北辰区",
    "detail": "河北工业大学 3 号宿舍楼 502",
    "isDefault": true,
    "defaultAddress": true
  }
]
```

> 这个接口 order-service 下单时会调用，取地址生成快照（BR-13）。
> `defaultAddress` 与 `isDefault` 同值，前者是 #51 新增的字段名，前端两个都兼容。
> 默认地址的维护规则见 11.3。

#### PUT /api/users/{userId}/role

管理员把用户设置为买家、卖家或管理员。注册接口只创建 `BUYER`，卖家权限通过这里开通。

请求：

```json
{ "role": "SELLER" }
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| role | 是 | `BUYER` / `SELLER` / `ADMIN` |

规则：

- 只有管理员可调用，不能变更自己的角色（避免把自己降级后无人可管理）
- 角色写进 JWT，**变更后对方需重新登录**才会拿到新角色

### 3.5 库存预占 —— **本项目最关键的一组接口**

#### POST /api/products/skus/reserve

由 order-service 在下单时调用。

请求：

```json
{
  "orderId": "O50001",
  "expireAt": "2026-10-20 21:30:00",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

响应 `data`：

```json
{
  "reservationId": "R60001",
  "items": [
    { "skuId": "S40001", "quantity": 2 },
    { "skuId": "S40002", "quantity": 1 }
  ]
}
```

**实现要求**：

```sql
-- 每个 SKU 一条，先到先得；任一条失败则回滚整批
UPDATE sku
SET stock_locked = stock_locked + #{quantity},
    stock_available = stock_available - #{quantity},
    version = version + 1
WHERE sku_id = #{skuId}
  AND stock_available >= #{quantity};
```

**影响行数为 0 表示库存不足**，返回 `30003`，调用方必须整体回滚（BR-15 不得留下半成品订单）。

**幂等要求**：同一 `orderId` 重复调用，返回首次的 `reservationId`，不重复扣减（利用 `orderId` 唯一索引）。

#### POST /api/products/skus/release

订单超时取消或买家主动取消时调用。

请求：

```json
{ "orderId": "O50001" }
```

响应 `data`：`{ "released": true }`

**实现要求**：

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    s.stock_available = s.stock_available + r.quantity,
    r.status = 'RELEASED'
WHERE r.status = 'LOCKED';
```

> BR-17：释放必须幂等，重复调用不得重复回补。靠 `r.status = 'LOCKED'` 这个条件保证，已释放的不会再匹配。

#### POST /api/products/skus/confirm

支付回调成功后调用，把预占转为真实扣减。

请求：`{ "orderId": "O50001" }`

响应 `data`：`{ "confirmed": true }`

```sql
UPDATE sku s
JOIN stock_reservation r ON r.sku_id = s.sku_id AND r.order_id = #{orderId}
SET s.stock_locked = s.stock_locked - r.quantity,
    r.status = 'CONFIRMED'
WHERE r.status = 'LOCKED';
```

#### POST /api/products/skus/refund-restock

退款审核通过后由 payment-service 调用，把已扣减的库存加回可售数量（BR-28）。

请求：`{ "orderId": "O50001" }`

响应 `data`：`null`（成功即代表已回补或无需回补）

**幂等要求**：先用条件更新把预占状态从 `CONFIRMED` 改为 `REFUNDED`，只有更新成功的那一次才真正加库存。重复调用时预占已不是 `CONFIRMED`，直接返回，不会重复加库存。

```sql
-- 1. 抢占状态，保证只有一个调用者回补
UPDATE stock_reservation SET status = 'REFUNDED'
WHERE order_id = #{orderId} AND status = 'CONFIRMED';

-- 2. 按预占明细逐 SKU 回补（仅在第 1 步影响行数 > 0 时执行）
UPDATE sku SET stock_available = stock_available + #{quantity}
WHERE sku_id = #{skuId} AND is_deleted = 0;
```

> **变更说明（2026-10-27）**：本节为新增。原契约 6.5 写了「退款成功后按退款明细回补库存」，
> 但未定义接口，payment-service 也未实现，导致退款后库存不恢复。现补齐接口与幂等要求。
>
> **实现已落地（#40）**：`StockController#refundRestock` + `StockService#refundRestock`，由 payment-service
> `RefundServiceImpl` 在「全额退款审核通过、事务提交后」调用。三处与上文 SQL 示意略有差异，按实现理解：
> ① 预占记录不存在（`30004`）时直接返回错误，不静默成功；② 预占状态不是 `CONFIRMED` 时直接返回成功（无需回补）；
> ③ 状态抢占用的是带前后状态条件的 `updateStatus(orderId, CONFIRMED, REFUNDED, now)`，效果等价。
> 请求体字段为 `{ "orderId": "..." }`（复用 `ConfirmStockRequest`），与其他三个内部库存接口一致。

### 5.1 订单状态机

```
        ┌──────────┐
        │ 待支付   │ PENDING_PAYMENT
        └────┬─────┘
             │ 支付成功回调
      ┌──────▼──────┐        超时/买家取消
      │  待发货      │        ┌──────────┐
      │ PAID        │        │  已取消   │
      └──────┬──────┘        │ CANCELLED│
             │ 卖家发货        └──────────┘
      ┌──────▼──────┐
      │  已发货      │
      │ SHIPPED     │
      └──────┬──────┘
             │ 买家确认收货 / 15 天自动
      ┌──────▼──────┐
      │  已完成      │
      │ COMPLETED   │
      └──────┬──────┘
             │ 退款成功
      ┌──────▼──────┐
      │  已退款      │
      │ REFUNDED    │
      └─────────────┘
```

### 5.3 提交订单 —— 最关键的接口

**请求头必须带**：`Idempotency-Key: <UUID>`

请求：

```json
{
  "addressId": "A2001",
  "cartItemIds": ["I80001", "I80002"]
}
```

**不要从前端传价格和总金额**，服务端自己算（防止篡改）。

响应 `data`：

```json
{
  "orderId": "O50001",
  "orderNo": "2026102012345678901",
  "payAmount": 11800,
  "expireAt": "2026-10-20 21:30:00"
}
```

**服务端处理顺序（写代码严格按这个顺序）**：

```
1. 校验幂等令牌，已处理则直接返回首次结果     ← 命中已有的 key 不算错误，返回原数据
2. 调用 cart-service 取购物车，按 cartItemIds 过滤（未勾选 / 已失效的条目直接报错）
3. 调用 product-service 取商品详情，校验状态与价格，算总额，按商品归属卖家分组
   ├─ 只有一家店：按原单店流程创建一条订单（不产生主订单层级）
   └─ 跨店（#135）：创建 1 条 main_order + 每店 1 条子订单（order.main_order_id 指向主订单）
4. 创建订单主记录（status = PENDING_PAYMENT）与明细（价格快照、标题快照），同一本地事务
   （跨店时主订单、全部子订单与明细在同一事务落库）
5. 调用 product-service 预占库存（跨店按子订单逐店预占，预占记录以子订单号为键）
   ├─ 成功：标记幂等 key 为 SUCCESS，返回
   └─ 失败：软删除全部订单记录与明细（跨店含主订单）、释放已预占成功的店、释放幂等 key，
      并把各子订单写入库存释放补偿表，再返回错误码
6. 逐条调用 cart-service 删除已下单的购物车项（失败只记 warn 日志，不影响下单结果）
```

> **变更说明（#135，2026-11-17）**：原第 3 步「一次只能结算同一卖家的商品，否则返回 10001」已被多店铺合并结算取代：跨店勾选不再报错，改为按店拆分生成主订单 + 子订单。单店结算的请求、响应与处理顺序保持不变（响应新增字段均为 null）。

**跨店结算的响应扩展（#135）**：单店时以下新增字段为 `null`；跨店时 `orderId/orderNo` 为第一个子订单，`payAmount` 为主订单应付合计：

```json
{
  "orderId": "O50001",
  "orderNo": "2026111712345678901",
  "payAmount": 19000,
  "expireAt": "2026-11-17 21:30:00",
  "mainOrderId": "M202111111111160001abcdef",
  "mainOrderNo": "2026111712345678902",
  "subOrders": [
    { "orderId": "O50001", "orderNo": "2026111712345678901", "sellerId": "U10002", "payAmount": 5000 },
    { "orderId": "O50002", "orderNo": "2026111712345678903", "sellerId": "U10003", "payAmount": 14000 }
  ]
}
```

- **没有「生成超时取消任务」这一步**：订单自带 `expire_at`（下单时间 + `order.timeout.minutes`），由 `OrderTimeoutJob` 定时扫描，见 5.7
- 预占失败时调用的是**软删除**（`is_deleted = 1`），不是物理删除；同时会写补偿任务，防止「预占请求超时但下游稍后提交」留下悬挂库存

**为什么先建订单再预占库存**：预占失败时只需删掉订单，回滚范围最小。反过来先预占再建单，如果建单失败，就要额外调用释放接口，多一次可能失败的远程调用。

> BR-14：订单号全局唯一且不可枚举 —— 用「日期 + 雪花 ID」，不用自增。
> BR-12：金额以提交瞬间的价格快照为准。
> BR-13：收货地址快照存入订单。

### 5.6 内部接口：支付成功 / 退款成功通知

payment-service 调用 order-service 的两个内部通知接口。**当前实现只传路径参数 `orderId`，请求头 `X-Internal-Token` 由 payment-service 的 Feign 拦截器按配置统一附加，order-service 侧不校验该令牌**（见 7 章「内部调用鉴权」）。

#### POST /api/orders/{orderId}/paid

payment-service 在回调处理成功后调用，通知订单「钱已到账」。

```
POST /api/orders/{orderId}/paid
X-Internal-Token: <内部令牌>      # 由 Feign 拦截器附加，order-service 当前未校验
```

请求体：**无**（金额、支付单号以 payment-service 本地已落库的支付单为准，order-service 不再二次核对）

响应 `data`：`null`，成功即 HTTP 200 + `code = 0`

**要求**：

- 用**条件更新**：`UPDATE order SET status='PAID', paid_at=? WHERE order_id=? AND status='PENDING_PAYMENT'`
- 订单已是 `PAID` → 直接返回成功，**不报错**（重复回调导致，属正常幂等场景）
- 订单是 `CANCELLED` → 返回 `50003`（订单状态不允许该操作）；payment-service 捕获后自主发起退款，不依赖这个报错（BR-18）
- 影响行数 0 且重读后仍不是 `PAID` → 返回 `50003`

> **与 v1.2 的差异**：5.6 原先写的「请求体含 `paymentId` / `payNo` / `amount` / `paidAt`、金额不一致返回 `10001`、`CANCELLED` 返回 `10003`」并未实现。
> 实际 `OrderController#paid` 只接收 `orderId`，`OrderService#markPaid` 也不接收金额；金额一致性由 payment-service 回调侧核对（6.5 第 4 步，返回 `60003`）。

#### POST /api/orders/{orderId}/refunded

退款审核通过后由 payment-service 调用，把订单置为已退款。

```
POST /api/orders/{orderId}/refunded
X-Internal-Token: <内部令牌>      # 由 Feign 拦截器附加，order-service 当前未校验
```

请求体：**无**

响应 `data`：`null`，成功即 `code = 0`

**规则**：

- 订单已是 `REFUNDED` → 直接返回成功（幂等）
- 只有 `PAID` / `SHIPPED` / `COMPLETED` 可置为 `REFUNDED`，其他状态返回 `50003`
- 用条件更新保证并发下不会被重复改状态

> 触发条件（以 `RefundServiceImpl` 实现为准）：退款审核**通过**且该支付单**已全额退款**时才通知；
> 订单因超时取消后收到支付回调的自动退款走 `autoRefund`，**不**调本接口（订单状态是 `CANCELLED`，不接受置为 `REFUNDED`）。

### 5.7 超时取消（定时任务）

order-service 内部 `@Scheduled` 每 60 秒扫描一次：

```sql
SELECT order_id FROM `order`
WHERE status = 'PENDING_PAYMENT'
  AND created_at < DATE_SUB(NOW(), INTERVAL 30 MINUTE)
  AND is_deleted = 0
LIMIT 100;
```

对每笔订单：

```
1. 条件更新：UPDATE `order` SET status='CANCELLED'
   WHERE order_id=? AND status='PENDING_PAYMENT'   ← 影响行数 0 说明被并发改了，放弃
2. 更新成功才调用 product-service 释放库存
3. 释放失败不阻塞，写入补偿任务表，由定时任务退避重试（见 9.1）
```

> **不加分布式锁**。取消的并发安全由「数据库条件更新（CAS）」保证：只有把状态从 `PENDING_PAYMENT`
> 改成 `CANCELLED` 的那个调用者才继续释放库存，其余调用直接返回 `false`。
> 同一订单的重复释放由 product-service 侧的预占状态条件更新兜底（3.5）。

> BR-16：超时时限默认 30 分钟，可配置（`order.timeout.minutes`）；扫描间隔 `order.timeout.scan-interval-ms`（默认 60 秒）、单批条数 `order.timeout.batch-size`（默认 100）。

### 5.9 多店铺合并结算（#135，2026-11-17 新增）

**数据模型**：新增 `main_order`（`main_order_id / main_order_no / buyer_id / status / pay_amount / paid_at / expire_at`），`order` 表加 `main_order_id` 列并建索引 `idx_main_order_id`，作为「店铺子订单」。历史单店订单 `main_order_id` 为 null，列表与详情按原单店逻辑兼容，不产生多余层级。建表见 order-service `schema.sql`（`CREATE TABLE IF NOT EXISTS` 可重复执行）；老库升级执行 `migration-135-main-order.sql`（幂等）。

**主订单状态机**：`PENDING_PAYMENT → PAID`（全部子订单 PAID 才生效，条件 UPDATE 保证并发下只生效一次）；`PENDING_PAYMENT → CANCELLED`（买家取消或超时，所有未支付子订单一起取消并释放库存预占）。子订单 `SHIPPED / COMPLETED / REFUNDED` 独立流转，不受兄弟订单影响，也不回改主订单状态。

#### POST /api/orders/preview

下单预览：接收购物车项与收货地址，返回**按店铺分组**的预览。校验规则与下单一致（未勾选/失效/下架/停用/库存不足都报错），但不落库、不预占。**金额一律服务端计算，前端不得自行计算应付**。

计价链（#136，顺序固定）：

```
1. 商品小计        = Σ 各店商品小计
2. 店铺/平台满减、满折   （规则来源由 #140 接入，未配置时为 0）
3. 优惠券抵扣      （券在 payment-service，#140 接入，未配置时为 0）
4. 加运费          = Σ 各店运费（按收货地区与各店商品小计计算）
5. payAmount      = totalAmount - discountAmount + freightAmount
```

```json
{ "cartItemIds": ["I80001", "I80002"], "addressId": "A10001" }
```

```json
  "discountAmount": 0,
  "payAmount": 19800,
  "shopCount": 2,
  "region": "天津市",
  "shops": [
    {
      "sellerId": "U10002",
      "shopName": "店铺A",
      "totalAmount": 5000,
      "freightAmount": 800,
      "discountAmount": 0,
      "payAmount": 5800,
      "items": [
        { "cartItemId": "I80001", "productId": "P30001", "skuId": "S40001",
          "productTitle": "罗技 G102 鼠标", "specName": "黑色", "mainImage": "https://...",
          "price": 5000, "quantity": 1, "subtotal": 5000 }
```

`shopName` 查询失败时回退为 `sellerId`，不阻塞预览。运费模板查询失败时该店运费按 0 计并记 warn 日志，不阻塞结算（宁可少收也不阻断下单，异常在日志与对账口径里可追溯）。

#### GET /api/orders/main

买家主订单列表（分页，可按 `status` 筛选），按创建时间倒序。仅返回当前买家的主订单；历史单店订单不在此列表，仍走 `GET /api/orders`。响应为分页结构，`list` 元素：`mainOrderId / mainOrderNo / status / payAmount / subOrderCount / itemCount / createdAt / expireAt`。

#### GET /api/orders/main/{mainOrderId}

主订单详情：仅买家本人或 ADMIN 可看。响应 `data`：`mainOrderId / mainOrderNo / buyerId / status / payAmount / paidAt / expireAt / createdAt / subOrders[]`，`subOrders` 为 5.4 的订单详情结构（含 `mainOrderId / mainOrderNo`）。

取消主订单：仅买家本人；仅 `PENDING_PAYMENT` 可取消，已支付返回 `50003`。条件 UPDATE 抢占主订单状态后，逐个取消未支付子订单并释放库存预占（复用 `inventory_released` 抢占标记，重复取消不重复释放）。已支付/已发货子订单不受影响。重复取消幂等返回成功。响应为主订单详情。

**超时**：`OrderTimeoutJob` 同时扫描到期主订单（`expire_at` 与子订单相同），到期整体取消；子订单扫描跳过带 `main_order_id` 的记录，避免只取消一半。

**支付**：跨店订单发起支付时 `POST /api/payments` 的 `orderId` 传**主订单ID**（M 前缀），payment-service 按主订单 `payAmount` 创建支付单（`payment.order_id` 存主订单ID，`seller_id` 为 null）。回调成功后逐个子订单调 `/orders/{orderId}/paid` 与库存确认；主订单由 order-service 在全部子订单 PAID 时自动置 PAID。主订单已取消时整笔自动退款（BR-18 同语义）。对账任务 `PaymentReconcileJob` 同样按子订单逐个补齐。

**售后与退款**：售后按子订单发起（`orderId` 传子订单ID），payment-service 先按子订单查支付单、未命中再按 `mainOrderId` 回查主订单支付单；退款通知与库存回补落到该卖家的子订单。整笔自动退款（无卖家归属）保留主订单ID，仅记录资金退回。

#### 自动确认收货（定时任务）

`AutoConfirmJob` 每 60 秒扫描一次（`order.auto-confirm.scan-interval-ms`，默认 60000）：

```sql
SELECT order_id FROM `order`
WHERE status = 'SHIPPED'
  AND shipped_at IS NOT NULL
  AND shipped_at <= NOW() - INTERVAL N MINUTE
  AND is_deleted = 0
LIMIT 100;
```

对每笔订单执行条件更新抢占：

```sql
UPDATE `order` SET status='COMPLETED', updated_at=NOW()
WHERE order_id=? AND status='SHIPPED' AND is_deleted=0;
```

- 影响行数 `0` 即跳过：说明买家已手动确认，或另一个调度实例已处理
- **不加分布式锁**，并发安全由上面的 CAS 保证；两个实例同时扫到同一单只会有一个成功
- `shipped_at IS NOT NULL` 必须显式判断：老库回填前的存量单不能凭空算成已超期
- 单批条数 `order.auto-confirm.batch-size`（默认 100）、初始延迟 `order.auto-confirm.initial-delay-ms`（默认 45000）
- `order.jobs.enabled=false` 时定时入口直接跳过，但 bean 仍注册，便于测试直接调用 `scan()`

**配置项**（并入 5.8 白名单）：

| 键 | 含义 | 取值 | 默认 |
| --- | --- | --- | --- |
| order.auto-confirm.minutes | 发货后自动确认收货的分钟数 | 1~86400 整数 | 14400（= 10 天） |

> **与旧表述的差异**：BR-19 原写「超过 15 天自动确认」，实现改为可配置，默认 10 天；配置下限 1 分钟用于验收「配成 1 分钟造到期订单」。

### 6.5 支付回调 —— 第二关键接口

```
POST /api/payments/callback
```

**处理顺序（严格按此执行）**：

```
1. 验签 md5(tradeNo + payNo + amount + MOCK_SECRET)
   └─ 失败：记录日志，返回 60002，不更新任何状态
2. 按 payNo 查支付单
   └─ 支付单不存在：返回 60001
3. 幂等去重（本地事务内）
   └─ INSERT INTO payment_callback(trade_no, ...)
      UNIQUE KEY uk_trade_no (trade_no)
   └─ 唯一键冲突 = 重复回调，按幂等成功返回，不重复处理（BR-24）
4. 金额核对
   └─ 回调金额 != 支付单金额：流水标记 AMOUNT_MISMATCH，返回 60003，不更新订单（BR-25）
5. 更新支付单 status = SUCCESS, paidAt = now（条件更新；已被并发处理则按幂等成功返回）
6. 事务提交后，再按订单当前状态决定后续：
   └─ 订单是 PENDING_PAYMENT：POST /orders/{orderId}/paid 置 PAID，
      再 POST /products/skus/confirm 确认扣减
   └─ 订单是 CANCELLED / REFUNDED：已超时取消或已退款，发起自动全额退款（BR-18），不再通知置 PAID
7. 返回成功
```

> 回调状态只接受 `SUCCESS`，其他值返回 `10001`。远程调用（通知订单、确认库存）放在本地事务提交之后，
> 避免占用数据库连接，也避免远程失败回滚已完成的支付状态；失败只记 error 日志、待人工补偿。

**回调报文示例**（MOCK 渠道）：

```json
{
  "tradeNo": "ALI20261020000001",
  "payNo": "P202610200001",
  "amount": 11800,
  "status": "SUCCESS",
  "payTime": "2026-10-20 21:05:33",
  "sign": "xxx"
}
```

**幂等表的表结构**：

```sql
CREATE TABLE payment_callback (
  callback_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
  trade_no      VARCHAR(64) NOT NULL,
  payment_id    VARCHAR(32) NOT NULL,
  raw_payload   TEXT,
  sign_verified TINYINT(1) NOT NULL DEFAULT 0,
  received_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_trade_no (trade_no)
);
```

> `UNIQUE KEY uk_trade_no` 是去重的唯一保障。**不要用「先查再插」的写法**，并发下会有窗口期，必须靠数据库唯一约束。

### 6.6 退款

```json
POST /api/payments/{paymentId}/refund
{ "amount": 5900, "reason": "商品有瑕疵" }
```

- 退款金额不得超过实付金额（BR-26）
- 同一订单允许多次部分退款，累计不超过实付（BR-27）
- 退款成功后，按退款成功的明细回补库存（BR-28）

**退款到「已退款」的完整链路（已实现，#40）**：

```
1. 买家申请退款 → 生成 PENDING 退款单；同时用 payment.refunded_amount 条件更新预占额度，
   并发申请也不会超过实付（BR-26 / BR-27）
2. 卖家或管理员审核通过（PUT /api/payments/refunds/{refundId}/audit，body { approved, remark }）
3. 该支付单累计退款达到实付 → 支付单置 REFUNDED，同事务落库两条持久通知任务，提交后分别触发：
   ├─ POST /orders/{orderId}/refunded     把订单置为 REFUNDED（5.6）
   └─ POST /products/skus/refund-restock  按预占明细回补库存（3.5，失败留任务，定时幂等重试）
4. 审核驳回 → 释放第 1 步预占的退款额度，支付单回到 SUCCESS
```

- 只有**全额退款**才回补库存并通知订单；部分退款不改变订单状态，也不回补库存
- 库存回补幂等由 product-service 侧「预占状态 `CONFIRMED` → `REFUNDED`」的条件更新保证，重复调用不会重复加库存
- 订单超时取消后又收到支付成功回调时，payment-service 自动全额退款（`autoRefund`），此时**不调用** `/orders/{orderId}/refunded`
- **审核归属（v1.4）**：`SELLER` 只能审核 `refund.seller_id = 当前登录用户` 的退款，审核他店退款返回 `10003`；`ADMIN` 不受限
- **售后复用（v1.5）**：售后单中 `REFUND_ONLY` 在卖家同意时立即复用本退款流程；`RETURN_REFUND` 在卖家确认收货后复用；两种类型都走 `payment.refunded_amount` 条件预占，满额退款才通知订单并回补库存

#### 6.6.1 持久通知补偿（第三批修复）

`refund_notification_task`以订单+事件唯一，事件为ORDER_REFUNDED和STOCK_RESTOCK；审核事务回滚则任务一起回滚。提交后立即尝试，失败由默认60秒调度扫描，指数退避30秒起、封顶600秒。PROCESSING租约120秒，过期可回收，attempts代次约束写回，DONE不重发。至少一次投递，依赖下游业务幂等，不承诺恰好一次。部分退款/驳回/原自动关闭退款不扩展为上述两事件；历史丢失通知不自动回填。长期不可用的任务保留，需运维监控。

| 状态 | 说明 |
| --- | --- |
| `PENDING` | 待卖家处理 |
| `APPROVED` | 卖家已同意（退货退款 / 换货） |
| `BUYER_SHIPPED` | 买家已回填退货物流 |
| `SELLER_RECEIVED` | 卖家已确认收到退货（退款执行前的内部过渡态） |
| `REFUNDED` | 退款完成（退款类型终态） |
| `COMPLETED` | 换货完成（换货类型终态） |
| `REJECTED` | 卖家/管理员驳回（终态） |

允许的状态流转：

```
REFUND_ONLY:    PENDING -> (APPROVED) -> REFUNDED | REJECTED
RETURN_REFUND:  PENDING -> APPROVED -> BUYER_SHIPPED -> SELLER_RECEIVED -> REFUNDED | REJECTED
EXCHANGE:       PENDING -> APPROVED -> BUYER_SHIPPED -> COMPLETED | REJECTED
```

> `REFUND_ONLY` 的 `APPROVED`、`RETURN_REFUND` 的 `SELLER_RECEIVED` 是同一事务内的过渡态，通常不会持久化给前端看到。

#### 6.8.2 申请售后

```

X-User-Id: U10001
Idempotency-Key: <UUID>
{ "orderId": "O50001", "type": "REFUND_ONLY", "amount": 5900, "reason": "商品有瑕疵" }
```

- 仅 `PAID` / `SHIPPED` / `COMPLETED` 订单可申请；支付单必须是 `SUCCESS`
- `REFUND_ONLY` / `RETURN_REFUND` 的 `amount` 必填且大于 0，不得超过 `payment.amount - payment.refunded_amount`
- `EXCHANGE` 的 `amount` 忽略，按 0 保存
- 同一订单同时只允许一条进行中的售后单；`Idempotency-Key` 重复提交返回首次创建的售后单
- `orderId`、`type` 必填；`reason` 最长 255 字符

#### 6.8.3 查询

```

```

- `BUYER` 只能看到 `buyer_id = 当前用户` 的售后单
- `SELLER` 只能看到 `seller_id = 当前用户` 的售后单
- `ADMIN` 全量可见
- 列表返回 1.6 节分页结构；详情无权访问返回 `10003`，不存在返回 `60005`

#### 6.8.4 卖家/管理员处理

```
PUT /api/payments/after-sales/{ticketId}/audit
{ "approved": true, "remark": "同意" }
```

- 只有 `PENDING` 可审核；驳回后进入 `REJECTED`，释放进行中标记
- `REFUND_ONLY` 同意后立即复用 6.6 退款流程，完成后状态 `REFUNDED`
- `RETURN_REFUND` / `EXCHANGE` 同意后状态 `APPROVED`，等待买家退货

```
PUT /api/payments/after-sales/{ticketId}/return-shipment
{ "trackingNo": "SF1234567890" }
```

- 仅买家本人、类型为 `RETURN_REFUND` / `EXCHANGE`、状态为 `APPROVED` 时可用
- 状态变为 `BUYER_SHIPPED`；重复提交同一物流单号幂等，不同单号拒绝

```
PUT /api/payments/after-sales/{ticketId}/receive
{ "remark": "已收到退货" }
```

- 仅 `RETURN_REFUND`、状态为 `BUYER_SHIPPED`（或重试时 `SELLER_RECEIVED`）可用
- 卖家确认收货后执行退款，状态变为 `REFUNDED`；退款金额/额度规则与 6.6 相同

```
PUT /api/payments/after-sales/{ticketId}/reship
{ "trackingNo": "SF0987654321", "remark": "已换新寄出" }
```

- 仅 `EXCHANGE`、状态为 `BUYER_SHIPPED` 时可用
- 记录换货物流，状态变为 `COMPLETED`；换货不产生退款，不通知订单退款

#### 6.8.5 并发与兼容

- 所有状态流转使用条件 UPDATE（`WHERE ticket_id=? AND status=前置状态 AND seller_id/buyer_id=?`），影响行数为 0 时重读并按幂等/冲突处理
- 同一订单的进行中售后单由 `after_sale_ticket.uk_order_active (order_id, active_flag)` 唯一键保证；进入终态时 `active_flag` 置 NULL
- 退款金额仍由 `payment.refunded_amount` 条件预占，售后单不能绕过 BR-26 / BR-27
- **存量兼容**：原 `refund` 表与 `POST /payments/{paymentId}/refund` 流程保持不变，售后单是增量表；历史仅退款数据无需迁移
- 退款成功后订单通知与库存回补由 6.6 的统一链路处理：只有全额退款才触发，部分退款不触发
- 错误码：售后单不存在 `60005`；状态不允许 `60006`；金额超过剩余可退 `60004`；越权 `10003`

### 6.9 支付成功对账任务

第四批状态边界：订单PAID/SHIPPED/COMPLETED均代表支付状态已前进，对账不再调用markPaid倒退状态，但仍须确认库存成功才能写reconciled_at。库存失败继续待补；CANCELLED/REFUNDED不自动确认库存或认定对账成功，保留异常处理。定时入口由payment.reconcile.enabled控制（默认true）；测试仅关闭后台自动执行，显式reconcile()回归仍验证完整逻辑。

> **补录（2026-11-01）**：本节此后未收录，实现已上线。

**背景**：回调里 `markPaid`（通知订单）与 `confirmStock`（确认库存）任一失败时，支付单已是 `SUCCESS` 但订单未变 `PAID`，而回调不会重发。此前只写 error 日志，没有补偿通道。

**机制**：`PaymentReconcileJob` 定时扫描并重放。

| 项 | 值 |
| --- | --- |
| 调度间隔 | 默认 60 秒（`payment.reconcile.interval-ms` 可配） |
| 扫描条件 | `status = 'SUCCESS'` 且 `reconciled_at IS NULL` 且支付时间在最近 72 小时内 |
| 单批行数 | 50 |
| 重放动作 | 先 `markPaid`，再 `confirmStock`，两者都成功才写 `reconciled_at` |

**幂等性**：`markPaid` 与 `confirmStock` 本身都是幂等的，重复执行安全。

**表结构变更**：`payment` 表新增可空列 `reconciled_at DATETIME`，索引 `(status, reconciled_at)`。存量库需执行 `migration-reconcile.sql`（含 information_schema 判断，可重复执行）。

**已知限制**：

- 无重试次数上限与退避，持续失败的单会每轮重试
- 毒单（前 50 条一直失败）可能阻塞后续记录
- 超过 72 小时的支付单不再自动对账，需人工处理
- 已取消订单收到成功支付时只记日志转人工，不自动退款

### 9.1 服务间通信

**全部用 OpenFeign 同步调用，不做消息队列，也不用 Redis List 做异步队列。** 理由：

- 下单、预占库存这类操作**必须知道结果**（成功还是库存不足），异步反而麻烦；
- 一个组件少一层排查成本，出问题直接看调用链日志；
- 课程作业规模下，RPC 的耦合风险远小于引入 MQ 的运维成本。

**取消/超时后释放库存的补偿原则仍然成立**，但实现不用队列，而是「同步调用 + 失败落表 + 定时任务补偿」：

```
1. 取消或超时把订单置为 CANCELLED（条件更新）后，同步调用 product-service /products/skus/release
2. 释放成功 → 订单表 inventory_released = 1
3. 释放失败（超时、下游不可用等）→ 写入 order 服务本库的 compensation 表（状态 PENDING、下次重试时间）
4. OrderTimeoutJob 每轮（默认 60 秒）额外做两件事：
   - retryUnreleasedInventory()：捞 inventory_released = 0 的已取消订单重新释放
   - retryCompensations()：按 next_retry_at 捞到期的补偿任务重试
5. 补偿任务指数退避（30s 起，最多 300s），累计 8 次仍失败标为 DEAD，转人工处理
6. product-service 侧另有 releaseExpiredReservations() 定时任务（默认 60 秒）兜底过期的 LOCKED 预占
```

对应代码：`CompensationService`、`OrderTimeoutJob`、`OrderService#releaseInventory` / `#retryUnreleasedInventory` / `#retryCompensations`。
幂等由两层条件更新保证：订单侧「CANCELLED 才释放一次」、库存侧「预占状态 `LOCKED` → `RELEASED` 只有一次成功」。

**Feign 超时已配置**（各服务 `application.yaml` 的 `spring.cloud.openfeign.client.config.default`）：连接 2s、读取 5s。网关侧下游超时为连接 2s、读取 6s。调用方捕获异常后转成业务错误码（如 `10005` 服务暂不可用），不做框架级降级。

### 9.2 并发控制（原「分布式锁」）

**当前没有分布式锁，也没有引入 Redis 或 Redisson。** 并发安全全部由数据库层保证，三处典型用法：

| 场景 | 做法 | 代码位置 |
| --- | --- | --- |
| 库存预占 | `UPDATE sku SET stock_locked = stock_locked + ? , stock_available = stock_available - ? WHERE sku_id = ? AND stock_available >= ?`，影响行数 0 即库存不足 | `StockService#reserve`（见 3.5） |
| 订单状态流转 | 条件更新 `WHERE order_id = ? AND status = ?`，影响行数 0 说明被并发改过，放弃本轮 | `OrderMapper#markPaid / #markCancelled / #markRefunded` |
| 请求幂等 | `idempotency` 表 `idem_key` 唯一键；`payment_callback` 表 `uk_trade_no` 唯一键；退款金额靠 `payment.refunded_amount` 条件更新预占 | `OrderService#create`、`CallbackTxService`、`RefundServiceImpl` |

**为什么这样够用**：上述场景的并发点都落在同一行数据的同一次条件更新上，数据库的行锁 + 唯一约束天然提供原子性；单库单服务的前提下，引入分布式锁只多一层故障点（锁失效、死锁、锁服务不可用）。

**如果后续确实要多实例并行同一订单的操作**，再引入 Redis 锁，但要按 9.2 早期的定稿原则来：`SET key value NX EX` 加锁、解锁校验持有者并用 Lua 保证原子性。Redis 目前不在已部署的基础设施里，不作为本阶段的实现要求。

### 9.3 支付模拟

不接真实支付宝/微信，自建 `MOCK` 渠道。

**流程**：

```
1. 用户点"支付" → payment-service 创建支付单（channel = MOCK）
2. 返回"收银台"页面，显示金额和一个【模拟支付成功】按钮
3. 点击按钮 → 前端调用 POST /api/payments/mock/pay
4. payment-service 按真实回调的完整流程走一遍：
   构造回调报文 → 验签（MOCK 用固定的签名算法）→ 幂等去重 → 更新状态
```

**关键**：模拟支付**必须走完整的回调流程**，不能直接把支付单状态改成 SUCCESS。否则回调的去重、验签、金额核对这些逻辑等于没测，实验四的测试报告也就没有内容。

**MOCK 签名算法**（韬哥实现，需与前端约定）：

```
sign = md5(tradeNo + payNo + amount + MOCK_SECRET)
```

`MOCK_SECRET` 从环境变量读，不硬编码。

**手动补充接口**：

| 接口 | 用途 |
| --- | --- |
| POST /api/payments/mock/pay | 模拟支付成功，触发回调 |
| POST /api/payments/mock/refund | 模拟退款：创建退款单并审核通过（请求体 `paymentId + amount`，详见 6.4） |
| POST /api/payments/mock/duplicate | 重复推送同一回调，用于验证幂等 |

第三个接口是给实验四测试用的，可以反复触发重复回调验证去重是否生效。

## 十、数据库隔离规则

**五个服务各用一个独立的库，禁止跨库查询。**

| 服务 | 库名 | 包含的表 |
| --- | --- | --- |
| user-service | `mall_user` | user、address |
| product-service | `mall_product` | product、sku、category、stock_reservation |
| cart-service | `mall_cart` | cart、cart_item |
| order-service | `mall_order` | `order`、order_item |
| payment-service | `mall_payment` | payment、payment_callback、refund、after_sale_ticket |

### 10.1 为什么必须分库

微服务的核心约束是「每个服务独占自己的数据」。分库不是形式主义，它带来两个实质好处：

1. **服务真正可独立演进**。商品表加字段不影响订单服务；商品库换存储引擎不用动别人。
2. **边界清晰，防止偷懒**。如果不能 JOIN，就逼着你通过接口拿数据，服务边界才立得住。

如果五个服务共用一个库、代码里随便 JOIN，那本质上还是单体应用，实验二画的微服务架构图就是假的，答辩时很容易被问穿。

### 10.2 从单库单表演进到商城分库，代码怎么改

单库单表的原型代码迁到分库结构时，按下表处理：

| 单库单表的写法 | 分库后怎么改 | 能复用吗 |
| --- | --- | --- |
| 实体类（Entity）、Mapper 单表 CRUD | 原样搬，只改库配置 | ✅ 直接复用 |
| 单表条件查询（按 id 查、按条件筛选） | 原样搬 | ✅ 直接复用 |
| **多表 JOIN 查询** | **拆成两次接口调用，在 Service 层组装** | ❌ 必须重写 |
| 分布式事务（下单时同时改订单表和库存表） | 改成「本地事务 + 调用库存服务 + 失败补偿」 | ❌ 必须重写 |
| 统一返回结构、拦截器、工具类 | 原样搬 | ✅ 直接复用 |

**典型例子**：单库时代「查询订单并带出商品名称」可能是一条 JOIN：

```sql
-- ❌ 分库后不可用
SELECT o.*, p.title FROM `order` o
LEFT JOIN product p ON o.product_id = p.product_id
WHERE o.buyer_id = ?
```

改成：

```java
// ✅ 先查订单
List<Order> orders = orderMapper.selectByBuyerId(buyerId);
// ✅ 再调商品服务批量取标题
List<String> productIds = orders.stream().map(Order::getProductId).toList();
Map<String, ProductDTO> products = productClient.batchGet(productIds);
// ✅ 在 Service 层组装
```

**注意**：订单表其实**已经存了价格和标题快照**（`order_item.product_title`、`price_snapshot`），历史订单不需要再查商品服务，这是 BR-12 带来的好处。只有展示「实时价格」的场景才需要调商品服务。

### 10.3 多数据源怎么配

每个服务只连**自己的库**，不需要配多数据源——一个服务一个库，普通 Spring Boot 配置即可：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mall_order?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:}
```

**不要为了省事让一个服务连多个库**，那等于绕过了服务边界。

### 10.4 本地怎么建这五个库

```sql
CREATE DATABASE IF NOT EXISTS mall_user    DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_product DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_cart    DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_order   DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS mall_payment DEFAULT CHARSET utf8mb4;
```

每个服务的建表语句放各自的 `src/main/resources/schema.sql`，启动时自动执行。

## 十一、#49 / #50 / #51 / #52 增量接口

### 11.1 店铺资料与营业状态（#49）

店铺状态是营业状态的**唯一真相**，存于 `mall_user.shop`，一个卖家一条（`uk_shop_seller`）。

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| GET | /api/shops/mine | 卖家查看自己的店铺（不存在时按昵称自动初始化） | 卖家 |
| PUT | /api/shops/mine | 卖家维护店铺资料 | 卖家 |
| GET | /api/shops | 分页查询店铺（keyword 匹配名称或卖家 ID，status 过滤） | 管理员 |
| PUT | /api/shops/{shopId}/status | 停用 / 恢复店铺 | 管理员 |
| GET | /api/shops/seller/{sellerId} | 按卖家查店铺（供 order-service 下单校验） | 内部 |

`data` 统一为 `ShopResponse`：

```json
{
  "shopId": "SH50001",
  "sellerId": "U10002",
  "name": "数码小铺",
  "logo": "/images/shop1.png",
  "description": "主营键鼠外设",
  "contactPhone": "13800138000",
  "contactWechat": "mall_shop_1",
  "status": "ACTIVE",
  "createdAt": "2026-10-28 20:00:00",
  "updatedAt": "2026-10-28 20:10:00"
}
```

**PUT /api/shops/mine** 请求：

```json
{
  "name": "数码小铺",
  "logo": "/images/shop1.png",
  "description": "主营键鼠外设",
  "contactPhone": "13800138000",
  "contactWechat": "mall_shop_1"
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| name | 是 | 1-64 字 |
| logo | 否 | ≤255 字，图片地址（可用 `POST /api/products/images` 上传） |
| description | 否 | ≤255 字 |
| contactPhone | 否 | 手机号或区号座机：`^$\|^1[3-9]\d{9}$\|^0\d{2,3}-?\d{7,8}$` |
| contactWechat | 否 | ≤64 字，微信 / 旺旺等在线联系方式 |

保存为**整体覆盖**语义：`logo`、`description`、`contactPhone`、`contactWechat` 传空字符串或 `null` 即清空原值，
前端「清除头像 / 清空简介」保存后能真正落库（`UpdateInfo` 不做非空跳过）。

**PUT /api/shops/{shopId}/status** 请求：

```json
{ "status": "SUSPENDED" }
```

`status` 只允许 `ACTIVE` / `SUSPENDED`，其余返回 `10001`；店铺不存在返回 `20007`。

**停用 / 恢复的跨服务影响（一致性约定）**：

1. user-service 先更新 `shop.status`；
2. 再通过 Feign 调 `POST /products/internal/seller-visibility`（带 `X-Internal-Token`），把该卖家 `ON_SALE` 的商品批量置为 `SUSPENDED`，恢复时反向改回 `ON_SALE`；
3. 同步失败则**回滚 `shop.status`** 并返回 `10005`，避免出现「店铺已停用但商品还在卖」；
4. product-service 在卖家上架、管理员审核通过时用 ShopClient 二次确认店铺状态，停用则落 `SUSPENDED` 并返回 `30006`；
5. order-service 下单时按 `sellerId` 再查一次店铺状态，停用返回 `30006`，作为 Feign 同步失败时的兜底。

> Issue #49 要求「商品可见性与下单校验在 product / order 侧的落点与 yy 对齐后实施」。
> 当前落点：product-service 商品状态新增 `SUSPENDED`（不改商品表结构）、order-service 增加下单前校验，均已在 Issue 评论说明。
> 商品服务不可用时按「正常营业」放行，避免单服务调试与集成测试整体不可用。

## 十二、#136 运费与优惠计价

> 版本 v1.9（2026-11-17）。运费配置在 user-service，计算在 order-service；本章只新增接口与字段，不改既有接口语义。

### 12.1 计价链（唯一口径）

顺序固定，预览与下单共用同一个实现（`OrderPricingService`），因此「预览显示多少、下单就收多少」：

```
1. 商品小计                         Σ 各店商品小计
2. 店铺/平台满减、满折（DiscountStep.order()=2）
3. 优惠券抵扣       （DiscountStep.order()=3）
4. 加运费                           Σ 各店运费
5. 应付合计 = 商品小计 - 优惠合计 + 运费合计
```

- 金额一律用「分」的整数；按比例的折扣（满折）只经 `Money.applyRate` / `Money.discountByRate` 取整一次，其余全是整数加减；
- 单店优惠合计有上下限保护：`0 ≤ 该店优惠 ≤ 该店商品小计`；
- 第 2、3 步的规则来源由 #140（促销工具：`promotion` 表与 `coupon` 表）接入，本版为占位实现返回 0，链顺序与取整口径已经固定，接规则时不需要改链；
- 运费模板服务不可用时该店运费按 0 计（记 warn），不阻塞结算。

### 12.2 运费模板配置（user-service，卖家）

```
GET /api/shops/mine/freight     # 读取（未配置时 templateId=null、freeThreshold=0、rules=[]）
PUT /api/shops/mine/freight     # 整体保存：模板 + 分地区规则，先软删旧规则再写新规则
```

需要 `X-User-Id` 且 `X-User-Role` 为 `SELLER`（或 `ADMIN`），否则 `10003`。

请求体：

```json
{
  "name": "全国运费",
  "freeThreshold": 9900,
  "rules": [
    { "regionCode": "DEFAULT", "minAmount": 0, "fee": 600 },
    { "regionCode": "河北省", "minAmount": 0, "fee": 800 }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| name | 模板名称，1~64 字符 |
| freeThreshold | 包邮门槛，单位分；`0` 表示不包邮 |
| rules[].regionCode | 省级名称（如「河北省」）或 `DEFAULT` 兜底；不区分大小写 |
| rules[].minAmount | 该档适用的最低商品金额，单位分，可配多档（如满 5000 收 300） |
| rules[].fee | 该档运费，单位分 |

校验与错误：金额为负、地区为空、同一地区同一门槛重复 → `10001`；规则最多 50 条。

响应 `data`：`templateId / shopId / sellerId / name / freeThreshold / status / rules[]`（`rules` 按地区、门槛升序）。

### 12.3 内部查询（user-service，给 order-service）

```
GET /internal/shops/{sellerId}/freight      # 需 X-Internal-Token
```

`data` 结构同上；没有店铺记录或没配置模板时返回 `templateId=null`、`freeThreshold=0`、`rules=[]`，**不报错**。

### 12.4 运费计算规则（order-service）

1. 没有模板或没有规则 → 运费 0（未配置模板的店铺不收运费，不报错）；
2. `freeThreshold > 0` 且该店商品小计 ≥ 门槛 → 0（包邮，门槛按商品小计判断，不含运费）；
3. 先按收货地址的**省份**精确匹配 `regionCode`，匹配不到回退 `DEFAULT`；两者都没有 → 0；
4. 同一地区多档时取「`minAmount` ≤ 商品小计」中门槛最高的一档；商品小计低于所有档位时取门槛最低的一档，避免出现「配了规则却不收运费」；
5. 跨店结算时每店分别计算后汇总，不做摊分。

### 12.5 订单字段与三处金额一致性

`order` 表新增（order-service `schema.sql` 已含，老库执行 `migration-136-freight-discount.sql`）：

| 字段 | 含义 |
| --- | --- |
| freight_amount | 该店运费，单位分 |
| discount_amount | 该店优惠抵扣，单位分 |

不变量：`pay_amount = total_amount + freight_amount - discount_amount`；主订单 `pay_amount` = 各子订单 `pay_amount` 之和。
历史订单两列为 0，`pay_amount` 保持原值，不变量同样成立（历史单没有运费与优惠）。

金额展示口径：

| 位置 | 展示内容 |
| --- | --- |
| 结算页（`POST /api/orders/preview`） | 商品金额 / 运费 / 优惠 / 应付合计 四行 |
| 订单详情（`GET /api/orders/{orderId}`） | `totalAmount / freightAmount / discountAmount / payAmount` 四行，应付与 `pay_amount` 一致 |
| 支付页（`GET /api/payments/order/{orderId}`、主订单支付） | 直接使用订单/主订单 `payAmount`，不再二次计算 |
| 资金对账（`GET /api/orders/admin/finance-summary`） | 仍按 `pay_amount` 汇总，因此与支付、订单三处口径一致 |

### 12.6 数据模型

```sql
shop.freight_template_id  VARCHAR(32) NULL          -- 当前生效模板
freight_template(template_id, shop_id, name, free_threshold, status, ...)   -- 一店一模板（uk shop_id）
freight_rule(rule_id, template_id, region_code, min_amount, fee, ...)        -- uk (template_id, region_code, min_amount)
```

### 12.1 检索增强（product-service）

```

```

**分词规则**（`KeywordAnalyzer`）：

| 输入 | 检索词 | 说明 |
| --- | --- | --- |
| `无线耳机` | `无线` / `线耳` / `耳机` | 连续中文按**二元组**切分，不引分词库 |
| `耳机` | `耳机` | 单字中文保留单字（`机`） |
| `5G 手机` | `5g` / `手机` | 英文与数字整体保留并转小写，大小写不敏感 |
| `降噪耳机` | `降噪` / `噪耳` / `耳机` | 多字段分别匹配，命中数越多分越高 |

**相关度评分**（可解释，写死权重）：

```
score = 标题命中词数 × 3 + 副标题命中词数 × 2 + 分类名命中词数 × 1 + SKU 规格名命中词数 × 1
```

- 同一个检索词在一段文案里重复出现只算一次；
- 排序：**得分降序 → 请求的 sort 作为第二关键字 → productId 兜底**（保证翻页稳定）；
- `sort=default` 的第二关键字是 `created_at DESC`，`sales_desc` 是销量降序，价格排序按最低 SKU 价。

**纠错提示**（只提示，不改写查询）：

- 在商品标题、副标题、分类名、规格名里滑动与查询等长的窗口，编辑距离 ≤ 1 即视为候选；
- 若文案里已包含原查询，则不给提示（没有打错字）；
- 候选词还需要**真的能搜出商品**才会返回；
- 命中时在响应 `suggestions` 里给出，前端展示「您是不是想找 X」，用户点了才换词，原查询结果不变。

**响应**（在原分页结构上新增 `suggestions`）：

```json

    "page": 1,
    "size": 20,
```

**性能**：1000 条商品量级单次检索实测最坏 154ms（本机 H2 + Maven 测试，见 `ProductSearchTest#searchStaysUnder300msWith1000Products`），满足 300ms 要求。

### 12.2 个性化推荐（product-service）

```
GET /api/products/recommend?scene=HOME|DETAIL&productId=&limit=8
```

| 参数 | 说明 |
| --- | --- |
| scene | `HOME` 首页「猜你喜欢」/ `DETAIL` 详情页「相似商品」，缺省 `HOME` |
| productId | DETAIL 场景必填，用于取同类商品并排除自身 |
| limit | 返回条数，默认 8，上限 20 |

**策略（可解释，不做模型）**：

1. 取最近浏览（user-service，20 条，每个计 1 分）与最近购买（order-service，20 条，每个计 3 分）的商品；
2. 商品 → 分类在本地商品表反查（**不跨库 JOIN**），按分类累加得分，取前 3 个分类作为推荐池；
3. DETAIL 场景把当前商品所属分类排在首位；
4. 池内按 `sales_count` 降序取商品，排除**已购买**、已下架（非 `ON_SALE`）、库存为 0、以及 DETAIL 场景的当前商品；
5. 不足 `limit` 时用全站热销补齐，**新用户也是全站热销，不会返回空数组**；
6. 行为接口异常按「无行为」降级，只记 warn，不影响接口返回。

**响应**：

```json
{
  "code": 0,
  "data": {
    "scene": "HOME",
    "coldStart": false,
    "basis": ["数码电子"],
    "items": [
      { "productId": "P30001", "sellerId": "U10002", "title": "无线降噪耳机", "mainImage": "/images/p30001.jpg",
        "categoryId": "C02", "status": "ON_SALE", "price": 19900, "stock": 12, "createdAt": "2026-11-17 10:00:00" }
    ]
  }
}
```

- `coldStart=true` 表示没有可用行为，`basis` 固定为 `["全站热销"]`；
- `basis` 是「为什么推荐」：命中的分类名，前端可直接展示。

## 十四、#137 真实支付渠道、退款异步收口与渠道对账增量接口

> 本章为 #137 增量，**只增不改**：六章既有 MOCK 支付、退款申请/审核、退款查询、售后中心语义保持不变。
> 真实渠道在 MOCK 之外新增，退款新增 `PROCESSING` 过渡态与异步收口，对账为独立只读清单。

### 12.1 渠道枚举与启用

`ChannelType`：`ALIPAY` / `WECHAT` / `MOCK`（存储值）。渠道行为由 `PaymentChannel` 实现，
`PaymentChannelRegistry` 收集已启用实现；请求未启用渠道返回 `10001`（参数不合法），消息「支付渠道未启用: {type}」。

- `MOCK`：默认启用，沿用 6.4 / 6.5 的模拟支付与 JSON 回调。
- `ALIPAY`：支付宝**沙箱**渠道，`@ConditionalOnProperty(payment.alipay.enabled=true)` 才装配。
  `appId`、应用私钥、支付宝公钥、回调通知基址**只从环境变量读取**（`ALIPAY_APP_ID`、`ALIPAY_PRIVATE_KEY`、
  `ALIPAY_PUBLIC_KEY`、`ALIPAY_NOTIFY_BASE_URL`），缺失时启动即失败（`IllegalStateException`）。
  密钥不落配置文件、不入库、不打印、不进日志/截图。签名 `RSA2`（`SHA256withRSA`），
  待签串按 key 升序 `k=v&` 拼接并剔除 `sign`、`sign_type` 与空值；金额元↔分用 `movePointRight/Left(2)`，四舍五入只一次。
- `WECHAT`：枚举预留，未实现，默认不启用。

### 12.2 发起支付的渠道增量（对 6.3 的补充）

- `POST /api/payments` 请求体 `CreatePaymentRequest` 新增必填 `channel`（`ChannelType`）；`orderId` 仍必填，金额仍由服务端向订单服务查询，不在请求体。
- 响应 `CreatePaymentResponse`：`paymentId`、`payNo`、`amount`（分）、`payUrl`。
  `MOCK` 的 `payUrl` 为空（走 6.4 模拟支付）；`ALIPAY` 返回渠道收银台跳转地址，前端新窗口打开。
- 查询支付单 `PaymentDetailResponse` 含 `channel`、`status`，不含 `payUrl`；前端如需再次跳转，复用发起支付接口取回 `payUrl`。

#### GET /api/payments/channels

已启用渠道列表，供支付页渲染渠道选项。需 `X-User-Id`（网关注入）。

```json
{ "code": 0, "message": "ok", "data": [
  { "channel": "MOCK",   "name": "模拟支付",       "sandbox": true },
  { "channel": "ALIPAY", "name": "支付宝（沙箱）", "sandbox": true }
] }
```

`sandbox=true` 表示沙箱环境，前端须标注「不产生真实扣款」。列表只含已启用渠道，顺序由注册表决定。

### 12.3 退款状态机增量：PROCESSING 异步收口

六章退款状态 `PENDING / REJECTED / SUCCESS / FAILED` 之外新增过渡态 `PROCESSING`（退款已受理、等待渠道结果）：

```
PENDING ──审核通过──> PROCESSING ──渠道成功──> SUCCESS
   │                     │
   │                     └──渠道失败──> FAILED ──人工重试──> PROCESSING
   └──审核驳回──> REJECTED（释放预占额度，终态）
```

- `MOCK` 渠道：审核通过在**同一事务**内直接置 `SUCCESS` 并写 `channel_refund_no = MOCKRF-{refundId}`，不经过 `PROCESSING`（与 6.6 既有行为一致）。
- 非 `MOCK` 渠道：审核通过置 `PROCESSING`，**事务提交后**（`afterCommit`）调渠道退款；渠道结果由 `RefundTxService` 以 `REQUIRES_NEW` 独立事务收口为 `SUCCESS`/`FAILED`，避免嵌套 `afterCommit` 同步器丢失。
- 渠道幂等键 `out_request_no = refundId`，同一退款单重复调用渠道不会重复退款。
- 渠道网络异常/未知结果：保持 `PROCESSING`，等待异步通知或人工重试，不臆断成功或失败。
- `FAILED` 保留第 1 步预占的退款额度（不释放），重试复用同一预占；`REJECTED` 才释放预占。
- 全额退款达到实付 → 支付单置 `REFUNDED`，落两条持久通知任务（订单 `refunded`、库存回补），与 6.6 / 6.6.1 链路一致；部分退款不通知订单、不回补库存。
- 退款单返回结构 `RefundResponse` 新增 `channelRefundNo`、`channelError`（失败原因，不含凭据）。

### 12.4 按渠道路由的回调接口（对 6.5 的补充）

6.5 的 `POST /api/payments/callback`（MOCK JSON）保持不变。新增按渠道路由的两个回调，**豁免网关鉴权**，靠渠道验签保证来源可信：

| 方法 | 路径 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| POST | /api/payments/callback/{channel} | 支付异步通知，`{channel}` 取 `ALIPAY`/`MOCK` | 否（验签） |
| POST | /api/payments/refund-callback/{channel} | 退款异步通知 | 否（验签） |

- 报文：`MOCK` 沿用 JSON（`PaymentCallbackRequest`）；`ALIPAY` 为 `application/x-www-form-urlencoded` 表单参数。
- 处理链与 6.5 一致：**验签 → 幂等去重 → 金额核对 → 更新状态**。退款回调去重靠 `refund_callback` 表 `uk_channel_notify (channel, notify_id)` 唯一约束（先插后判，不先查再插）；重复通知返回幂等成功，不重复收口。
- 金额不一致：落 `AMOUNT_MISMATCH` 流水，**不修改**退款单金额与状态，转人工。
- 退款回调只收口 `PROCESSING` 的退款单；对 `SUCCESS`/`REJECTED`/`FAILED` 等终态的迟到通知按幂等成功处理，不改单。
- 响应：`ALIPAY` 按渠道规定返回**纯文本** `success`/`failure`（`text/plain`）；`MOCK` 返回统一 `Result`。
- 未知渠道返回 `10001`。

### 12.5 退款人工重试

#### POST /api/payments/refunds/{refundId}/retry

渠道退款失败或滞留 `PROCESSING` 时的人工重试。需 `X-User-Id`，`X-User-Role` 为 `SELLER` 或 `ADMIN`，否则 `10003`。

- `FAILED` 可重试：条件更新 `FAILED → PROCESSING`，复用原预占额度，再次调渠道（`refundId` 为渠道幂等键，不会重复退款）；状态已变化（影响 0 行）返回 `10001`「退款单状态已变化，请刷新后重试」。
- `PROCESSING`（渠道滞留）可重试：再次驱动渠道收口，不改变状态、不重复预占。
- `PENDING`/`SUCCESS`/`REJECTED` 不可重试，返回 `10001`「仅失败或处理中的退款单可重试」；退款单不存在返回 `10001`。
- `SELLER` 只能重试本店退款（`refund.seller_id = X-User-Id`），他店 `10003`；`ADMIN` 不受限。
- 响应 `data` 为 `RefundResponse`（重试受理后的快照，`FAILED` 重试后为 `PROCESSING`，终态由渠道异步收口）；写审计日志 `REFUND_RETRY`。

### 12.6 渠道对账（仅 ADMIN，只读清单不自动修账）

导入渠道账单 CSV，逐笔比对本地 `payment`/`refund`，**只生成差异清单**供人工复核，全程只读，不修改支付/退款金额。
路径前缀 `/api/payments/admin/reconcile`，四个接口均要求 `X-User-Role` 严格等于 `ADMIN`（否则 `10003`）且 `X-User-Id` 非空（否则 `10002`）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/payments/admin/reconcile/import | 上传账单并对账，`multipart/form-data`：`channel` + `file` |
| GET | /api/payments/admin/reconcile/batches | 批次分页，`channel`（可选）、`page`、`size` |
| GET | /api/payments/admin/reconcile/differences | 差异分页，`batchId`、`diffType`、`status`（均可选）、`page`、`size` |
| PUT | /api/payments/admin/reconcile/differences/{differenceId}/resolve | 标记差异已处理，body `{ "remark": "..." }`（可选） |

**CSV 格式**（首行表头，逗号分隔，不支持引号转义，UTF-8）：

```
trade_no,bill_type,out_trade_no,amount_fen,status,trade_time
```

- `bill_type` 取 `PAYMENT`/`REFUND`；**只比对 `status=SUCCESS` 的行**，其余忽略；`amount_fen` 为非负整数（分）。
- `PAYMENT` 行按 `out_trade_no = pay_no` 匹配；`REFUND` 行按 `trade_no = channel_refund_no` 或 `out_trade_no = refund_id` 匹配。
- 表头不符、列数不是 6、金额非整数分/为负、无 `SUCCESS` 行、行数超过 **10000** 上限 → `10001`。

**差异三类**（`diffType`）：

| 值 | 含义 |
| --- | --- |
| LOCAL_ONLY | 本地有、账单无（`bill_trade_no` 为空） |
| CHANNEL_ONLY | 账单有、本地无（`local_no` 为空） |
| AMOUNT_MISMATCH | 双方都有但金额不一致 |

**响应结构**：

- `import` → `ReconcileBatch`：`batchId`、`channel`、`fileName`、`totalRows`、`diffCount`、`importedBy`、`createdAt`。
- `batches` → `PageResult<ReconcileBatch>`（`list/total/page/size/pages`，见 1.6）。
- `differences` → `PageResult<ReconcileDifference>`：`differenceId`、`batchId`、`channel`、`billType`、`diffType`、`billTradeNo`、`localNo`、`localAmount`、`channelAmount`、`status`（`PENDING`/`RESOLVED`）、`remark`、`resolvedBy`、`resolvedAt`、`createdAt`。
  `diffType` 过滤合法值 `LOCAL_ONLY/CHANNEL_ONLY/AMOUNT_MISMATCH`，`status` 过滤合法值 `PENDING/RESOLVED`，非法值 `10001`；`size` 上限 100。
- `resolve` → `ReconcileDifference`（处理后）。差异不存在或已处理（条件更新影响 0 行）返回 `10001`「差异已处理，请刷新后查看」；写审计日志 `RECONCILE_RESOLVE`。**标记已处理只更新清单状态，不改动支付/退款金额。**

### 12.7 网关白名单增量（需网关负责人评审）

## 十五、#143 售后举证与平台仲裁增量接口

> 本章为 #143 增量，**只增不改**：六章售后中心既有接口语义保持不变。
> 新增原因固定枚举、凭证上传与绑定、买家撤销、进度时间线、平台仲裁与双方补充材料。

### 13.1 状态与枚举增量

`AfterSaleStatus` 新增两个值：

- `CANCELLED`：买家撤销，终态。
- `ARBITRATING`：平台仲裁中，状态锁定（卖家不能审核）。

状态机在 6.7 基础上补充：

```
PENDING      -> CANCELLED        （买家撤销，终态）
REJECTED     -> ARBITRATING      （买家申请平台仲裁，仲裁期间锁定）
ARBITRATING  -> REFUNDED         （管理员裁定支持退款，联动退款单）
ARBITRATING  -> REJECTED         （管理员裁定驳回）
ARBITRATING  -> ARBITRATING      （双方补充材料，仅记时间线，状态不变）
```

`AfterSaleReasonCode`：`QUALITY / NOT_AS_DESCRIBED / DAMAGED / WRONG_ITEM / NO_LONGER_NEEDED / OTHER`。
选 `OTHER` 时 `reason` 补充说明必填，否则返回 `10001`。
`ArbitrationDecision`：`REFUND`（支持买家退款）/ `REJECT`（驳回申请）。

### 13.2 凭证上传（先上传后引用）

`POST /api/after-sales/attachments/upload`（需登录，任意角色）

- multipart，字段名 `files`，单次 1–3 个；超过 3 个返回 `10001`。
- 单张 ≤ 5MB，仅 `jpg/jpeg/png/webp/gif`；UUID 重命名，落盘 `{payment.upload-dir}/after-sale/`。
- 返回站内路径列表：`Result<List<String>>`，如 `/after-sale/{32位小写hex}.png`。
- 静态访问 `GET /after-sale/{file}` **公开可读**（与 `/images`、`/avatars` 同一套方案，
  网关新增静态路由 `Path=/after-sale/**` → payment-service，不 StripPrefix；白名单 `PUBLIC_GET` 增加 `/after-sale/**`）。
- 方案与商品图、头像一致：上传只落盘不绑定工单，创建/补充售后单时再引用。

### 13.3 创建售后单增量（对 6.7 create 的补充）

`POST /api/payments/after-sales`（买家）请求体 `CreateAfterSaleRequest` 新增**可选**字段，不传时保持原语义：

- `reasonCode`：`AfterSaleReasonCode`，选 `OTHER` 时 `reason` 必填。
- `attachmentUrls`：`List<String>`，最多 3 个；每个必须匹配
  `^/after-sale/[0-9a-f]{32}\.(jpg|jpeg|png|webp|gif)$`（服务端正则校验，防路径注入），否则 `10001`。

创建成功后凭证绑定到售后单（`after_sale_attachment`），并记录首条时间线事件（`NULL -> PENDING`），
三者同一事务落库；幂等命中已存在售后单时不重复绑定、不重复记录。

### 13.4 新接口清单

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | /api/after-sales/attachments/upload | 登录即可 | 上传凭证，返回站内路径列表 |
| POST | /api/after-sales/{ticketId}/cancel | 买家本人 | `PENDING` 撤销为 `CANCELLED`；请求体 `{ remark? }` |
| POST | /api/after-sales/{ticketId}/arbitration-request | 买家本人 | `REJECTED` 申请仲裁进入 `ARBITRATING`；请求体 `{ remark? }` |
| POST | /api/after-sales/{ticketId}/supplement | 买家本人/本店卖家/管理员 | 仲裁中补充材料；`{ remark?, attachmentUrls? }` 至少其一 |
| POST | /api/after-sales/{ticketId}/arbitrate | **仅 ADMIN** | 裁定；`{ decision: REFUND\|REJECT, remark 必填 }` |

> 售后中心同时映射四组前缀：`/payments/after-sales`、`/api/payments/after-sales`（既有）
> 与 `/after-sales`、`/api/after-sales`（#143 别名）。网关 payment-service 路由 `Path` 谓词
> 增加 `/api/after-sales/**`（StripPrefix=1）。
> 错误码沿用既有约定：`10001` 参数不合法、`10002` 未登录、`10003` 无权限、`60005` 售后单不存在、`60006` 售后状态不允许该操作。

### 13.5 撤销、仲裁与裁定的规则

- **撤销**：仅 `PENDING`；撤销后卖家不可再审核（`60006`）；已 `APPROVED` 及之后状态不可撤销（`60006`）。
  撤销释放 `active_flag`，同一订单可以重新申请售后。
- **申请仲裁**：仅卖家 `REJECTED` 后可申请；`ARBITRATING` 期间锁定，卖家审核接口返回 `60006`。
  同一订单已存在其他进行中售后单时返回 `10001`。
- **补充材料**：仅 `ARBITRATING`；说明与凭证至少其一；材料对买卖双方可见（详情接口返回）。
- **裁定**：仅 `ADMIN`（否则 `10003`）；`remark` 必填（否则 `10001`）；非 `ARBITRATING` 状态返回 `60006`。
  `REFUND` 只对 `REFUND_ONLY/RETURN_REFUND` 且金额 > 0 生效（换货返回 `10001`）。
  `REFUND` 复用 6.6 退款链路：渠道同步成功（MOCK）则售后单同事务置 `REFUNDED`；
  渠道异步（真实渠道）先挂 `refundId`，退款成功回调收口时再置 `REFUNDED` 并补记时间线，
  售后单与退款单状态保持一致。并发裁定依赖条件更新 + 退款额度预占，同一售后单只产生一笔退款。

### 13.6 详情与时间线

`GET /api/payments/after-sales/{ticketId}`（买家本人/本店卖家/管理员）在既有字段外新增：

- `reasonCode`：原因枚举。
- `attachments`：凭证列表（`id/ticketId/url/uploadedBy/uploaderRole/createdAt`），按时间正序。
- `events`：进度时间线（`id/fromStatus/toStatus/operatorId/remark/createdAt`），按时间正序；
  每次状态变更一条，创建记为 `NULL -> PENDING`，补充材料记为 `ARBITRATING -> ARBITRATING`。

列表接口仍是轻量结构（`attachments/events` 为 null）；列表支持 `status=ARBITRATING` 过滤
（买家可见自己的、卖家可见本店、管理员全量），对应 `GET /api/after-sales?status=ARBITRATING`。

### 13.7 数据表增量

- `after_sale_ticket` 新增可空列 `reason_code VARCHAR(24)`。
- `after_sale_attachment`：`id` 自增主键 / `ticket_id` / `url` / `uploaded_by` / `uploader_role` / `created_at`，`idx_ticket_created`。
- `after_sale_event`：`id` 自增主键 / `ticket_id` / `from_status`（创建时为 NULL）/ `to_status` / `operator_id` / `remark` / `created_at`，`idx_ticket_created`。

老库升级脚本：`src/payment-service/src/main/resources/migration-143-after-sale.sql`（幂等，可重复执行）。


## 十六、站内消息（#106）

消息由 user-service 负责，数据保存在 mall_user 的 conversation / message 表，不新增数据库或服务。网关用户服务路由包含 `/api/messages/**`，统一 StripPrefix=1；以下接口全部需要登录，不加入白名单，不提供管理员读取通道。

| 方法 | 网关路径 | 说明 |
| --- | --- | --- |
| GET | `/api/messages/conversations?page=1&size=20` | 当前用户参与的会话，按最后消息时间倒序、会话 ID 倒序 |
| GET | `/api/messages/conversations/{id}?page=1&size=30` | 会话消息按创建时间、消息 ID 正序分页 |
| POST | `/api/messages` | 发送纯文本消息 |
| PUT | `/api/messages/conversations/{id}/read` | 收到的消息标为已读，并清零当前用户对应的未读数 |

分页沿用 1.6 节的 `page/size/total/pages/list`，page 从 1 开始，size 上限 100。

首次发送：

```json
{ "sellerId": "U_SELLER", "content": "这个还有货吗", "contextProductId": "P001" }
```

已有会话双方回复：

```json
{ "conversationId": "C001", "content": "还有货，可以下单" }
```

`contextProductId` 可省略；提供时商品必须存在且属于会话卖家。商品展示信息通过现有 `GET /api/products/batch?ids=...` 获取，不建跨库外键。相同买家和卖家用唯一约束复用同一会话，换商品提问不会新建会话。用户角色为 SELLER 时仍保留作为买家向其他卖家咨询的能力。

会话项包含 `conversationId/buyerId/sellerId/buyerName/sellerName/lastMessageAt/lastPreview/buyerUnread/sellerUnread/unreadCount`。`unreadCount` 为当前用户的未读数，直接读取会话计数。消息项以及发送成功的 `data` 包含 `messageId/conversationId/senderId/content/contextProductId/readAt/createdAt`。已读成功返回 `data: null`。

发送人仅取可信 `X-User-Id`，不能由正文指定。仅会话参与者可读、发送或标记已读；第三方和管理员返回 `10003`，不存在会话返回 `20009`。禁止给自己发消息（`10001`）。收件卖家必须是未冻结的 SELLER 且店铺 ACTIVE；非卖家、无店铺或停用店铺返回 `20007`（符合 #106 的允许错误码），被冻结的卖家返回 `10003`。管理员不能新建或参与消息。正文去除首尾空白后须为 1–500 字，空或超长返回 `10001` 和中文提示；`20010 MESSAGE_EMPTY` 预留但不替代此校验码。

发送和已读操作在同一会话行锁内更新，避免清零操作丢失并发新消息。时间字段使用微秒精度，按会话发送顺序递增并以 ID 作二级排序，避免同秒消息跨页重复或丢失。未读只累计接收方；已读只修改别人发来的消息。

买家页面 `/messages`、卖家页面 `/seller/messages` 复用同一组件。此版本在进入页面、切换会话、发送后及手动刷新时拉取，不提供实时推送、图片文件、撤回或删除。

## 十七、#144 增量接口：商家入驻与资质审核（2026-11-18）

只增不改：既有章节的接口路径、语义与响应字段全部保留，本章只补新增字段与新接口。

### 17.1 新增表与列

| 位置 | 变更 | 说明 |
| --- | --- | --- |
| `mall_user.shop` | 新增 `apply_status VARCHAR(16) NOT NULL DEFAULT 'APPROVED'` | `PENDING` / `APPROVED` / `REJECTED`；默认值让历史店铺直接视为已过审 |
| `mall_user.shop` | 新增 `deposit_amount BIGINT NOT NULL DEFAULT 0` | 保证金（分），仅作记录不拦截发布；`0` 表示尚未缴纳，管理员审核时登记 |
| `mall_user.shop` | 新增 `qualification_json VARCHAR(2000) DEFAULT NULL` | 主体类型、证照编号与资质材料快照，审核阶段只读 |
| `mall_user.shop` | 新增索引 `idx_shop_apply_status (apply_status)` | 管理端「待审核」筛选 |
| `mall_user.shop_apply_log` | 新表 | 入驻审核流水，只追加不修改：`shop_id / from_status / to_status / operator_id / remark / created_at` |

增量脚本：`src/user-service/src/main/resources/migration-144-shop-apply.sql`（可重复执行，列与索引都先查 `information_schema`）。

### 17.2 新接口

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| POST | /api/shops/apply | 卖家提交 / 重新提交入驻申请 | 卖家 |
| PUT | /api/shops/{shopId}/audit | 管理员审核入驻申请，通过时登记保证金 | 管理员 |

**POST /api/shops/apply** 请求：

```json
{
  "name": "数码小铺",
  "contactPhone": "13800138000",
  "contactWechat": "mall_shop_1",
  "subjectType": "ENTERPRISE",
  "licenseNo": "91110000MA01ABCD2X",
  "materials": ["/images/shop1.png", "/images/license.png"]
}
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| name | 是 | 1-64 字 |
| contactPhone | 否 | 与 11.1 的联系电话正则一致 |
| contactWechat | 否 | ≤64 字 |
| subjectType | 是 | `PERSONAL` 个人 / `INDIVIDUAL` 个体工商户 / `ENTERPRISE` 企业，其余返回 `10001` |
| licenseNo | 否 | ≤64 字，个人可留空 |
| materials | 否 | 图片地址数组，最多 9 项（可用 `POST /api/products/images` 上传），空串与多余项按截断处理 |

返回 `data` 为 `ShopResponse`。规则：

1. 首次申请会建店：`status=SUSPENDED`、`applyStatus=PENDING`、`depositAmount=0`；
2. `applyStatus=PENDING` 时重复提交返回 `10001`（审核中），`APPROVED` 时返回 `10001`（无需重复申请）；
3. 只有 `REJECTED`（或从未申请）可以再次提交，重新提交会把店置回 `PENDING` + `SUSPENDED`；
4. 每个店铺累计提交（含首次）**最多 5 次**，超出返回 `10001`，防刷（#144 组长要求）；
5. 每次提交与每次审核都在 `shop_apply_log` 追加一条流水。

**PUT /api/shops/{shopId}/audit** 请求：

```json
{ "decision": "APPROVED", "reason": null, "depositAmount": 50000 }
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| decision | 是 | 只允许 `APPROVED` / `REJECTED`，其余返回 `10001` |
| reason | 驳回时必填 | ≤255 字，卖家侧作为「驳回理由」展示；通过时忽略 |
| depositAmount | 否 | ≥0，单位**分**。不传沿用已登记金额；`0` 表示已要求但尚未缴纳。保证金仅作记录，不拦截发布 |

规则（`data` 仍为 `ShopResponse`）：

1. 非 `ADMIN` 调用返回 `10003`，店铺不存在返回 `20007`；
2. 驳回缺理由返回 `10001`；已通过审核的店铺不能再驳回，返回 `10001`（停止营业请改用 11.1 的停用接口）；
3. 通过 → `applyStatus=APPROVED`、`status=ACTIVE`，并按 11.1 的约定调用
   `POST /products/internal/seller-visibility` 恢复该卖家商品可见性；保证金只登记金额与缴纳状态，不参与发布拦截；
4. 可见性同步失败 → 返回 `10005`，审核结论与流水一起回滚，不出现「审核过了但商品仍在售」的半状态。

### 17.3 既有接口的增补字段与语义

`GET /api/shops` 新增可选查询参数 `applyStatus`（`PENDING` / `APPROVED` / `REJECTED`，非法值返回 `10001`），与 `keyword`、`status` 可叠加。

`ShopResponse` 新增字段：

```json
{
  "applyStatus": "PENDING",
  "rejectReason": "资质材料不清晰",
  "depositAmount": 50000,
  "depositPaid": true,
  "publishable": false,
  "subjectType": "ENTERPRISE",
  "licenseNo": "91110000MA01ABCD2X",
  "materials": ["/images/shop1.png"]
}
```

| 字段 | 口径 |
| --- | --- |
| applyStatus | `null` 表示从未提交过申请 |
| rejectReason | 最近一次驳回理由；卖家重新提交后仍保留，便于对照 |
| depositPaid | `depositAmount > 0` 视为已缴；历史店铺默认 `0`，显示为未缴纳。仅作记录 |
| publishable | `applyStatus=APPROVED`，即「允许发布商品」；保证金不参与 |
| subjectType / licenseNo / materials | 由 `qualification_json` 解出，脏数据只记日志不影响店铺查询 |

1. `GET /api/shops/mine`：**不再自动建店**。未提交过申请时返回 `shopId=null`、`status=SUSPENDED`、
   `applyStatus=null`、`publishable=false`，由前端引导卖家先走 `POST /api/shops/apply`；
2. `PUT /api/shops/mine`：店铺不存在返回 `20007`（提示先提交申请）；未过审返回 `10001`，
   店名与联系方式在审核阶段只能通过入驻申请修改；
3. `PUT /api/shops/{shopId}/status`：`publishable=false` 的店铺请求恢复为 `ACTIVE` 返回 `10001`；
4. `GET /api/shops/seller/{sellerId}`：`publishable=false` 时对外一律返回 `status=SUSPENDED`。
   上架、商品审核通过与下单沿用 11.1 的 `shop.status` 单点拦截，product-service 与 order-service 无需改动。

### 17.4 与 #142 公开店铺主页的字段边界

`GET /api/shops/{shopId}`（#142 店铺主页）被网关列为**匿名可读**（`JwtAuthFilter.SHOP_DETAIL_PATH`，
仅 GET，保留字 `mine` / `following` / `seller` 除外），因此该接口按白名单只返回 #144 之前就公开的字段：

`shopId`、`sellerId`、`name`、`logo`、`description`、`contactPhone`、`contactWechat`、`status`、
`freightTemplateId`、`createdAt`、`updatedAt`。

17.3 新增的 8 个字段在该接口上**一律为 `null`**：`applyStatus`、`rejectReason`、`depositAmount`、
`depositPaid`、`publishable`、`subjectType`、`licenseNo`、`materials`。资质证照、保证金与审核结论属卖家隐私，
只在 `GET /api/shops/mine`（卖家本人）、`GET /api/shops`（ADMIN）与 `PUT /api/shops/{shopId}/audit`（ADMIN）返回。

`sellerId` 仍照常返回，product-service 按店铺筛选商品（`GET /api/products?shopId=`）依赖它换取卖家 ID，不受影响。
`POST /api/shops/apply` 与 `PUT /api/shops/{shopId}/audit` 不在白名单内（白名单对非 GET 直接拒绝），仍需登录与角色校验。
