# 第四批：商品审核、历史库存、经营权限与支付对账

## 范围

用户指定四项修复，保留前三批全部本地改动。不启动六个后端、不改真实业务数据、不提交推送。只修改相关业务源码/SQL映射、新增回归及说明；子代理仅china/deepseek-v4.1-flash，测试由主代理统一运行。

## 修复内容

### 1. 审核状态绕过

- 卖家上下架仅允许来源状态ON_SALE/OFF_SHELF。PENDING/REJECTED/SUSPENDED拒绝两种卖家跳转，不能通过先下架再上架抹掉待审核状态。
- 卖家状态更新采用productId+sellerId+预期状态+未删除的条件UPDATE，阻止并发编辑或审核已改变状态后被旧请求覆盖。
- 合法审核后上下架保留；修改商品仍按原规则回PENDING，需要重新审核。
- 本轮不识别/清洗修复前已经被异常转换为OFF_SHELF的历史数据；当前状态本身不包含审核履历，现场核查需另行授权。管理员审核/店铺同步仍按各自入口，未做全局状态机重构。

### 2. 商品删除不破坏既有库存账务

- 商品/SKU仍软删除，不能再出现在目录或接受新预占。
- 仅库存内部restore/confirm/refundRestock允许处理已软删除SKU，以既有预占记录和明细为依据，不开放新的销售/修改入口。
- 退款回补检查每条SKU更新数；历史SKU物理丢失时抛错，并在同一库存事务回滚REFUNDED标记，避免假成功后永失重试机会。
- 重复释放、确认与退款回补仍由预占状态机幂等；不增加第二份库存账、不改真实数据。

### 3. 降权后的商品经营角色

- 商品编辑、上下架、删除、库存修改、商品图片上传新增当前SELLER角色校验，沿用现有create/addSku的仅SELLER经营口径；ADMIN审核权限不被等同为卖家经营权限。
- 仍保留业务层资源归属校验，合法SELLER也不能操作其他卖家商品。
- 角色来自前三批网关当前状态/版本核验和可信内部入口，不从前端query参数判断。
- 本轮不改变历史订单履约/卖家售后角色政策，也不改真实账号。

### 4. 已发货/完成订单支付对账

- PaymentReconcileJob对PAID/SHIPPED/COMPLETED视作订单支付状态已经前进，不再重放markPaid倒退状态。
- 仍必须confirmStock成功后才写reconciled_at，库存失败保留待重试。
- CANCELLED/REFUNDED保留原异常人工处理分支，不自动确认库存或标记对账完成；不擅自将异常支付当正常成功。

## 回归与发现

修复前集中红灯：支付对账11例中3失败；商品第一次因新增测试TimeUtils导入包错误未编译，纠正导入后8例中5断言失败、2业务异常（审核绕过、角色越权、删除后释放/确认失败、回补假成功）。该编译错误不算业务复现。

新增ProductLifecycleRegressionTest覆盖审核洗白拒绝、正常审核上下架、编辑后再审核、CAS状态变化/他人归属、删除前预占后释放/确认/退款重复调用、新预占拒绝、物理缺失SKU回滚。新增ProductWriterRoleRegressionTest通过真实MockMvc控制器调用拒绝BUYER/ADMIN/缺失/非法经营角色，SELLER正常转交业务归属检查。

PaymentReconcileJobTest保留原4例并新增7例，覆盖已发货/完成、确认失败恢复、取消/已退款不操作、扫描与订单读取失败。

首次修复后product-service全部22例通过且打包成功；payment-service的四项目标回归通过，但第三批RefundNotificationTxServiceTest有1例抢占返回null。新任务原来将应用高精度当前时间作为next_retry_at写库，舍入后可能略晚于立即抢占时间。将新任务next_retry_at明确设为NULL（已有SQL语义=立即可投递），不改变失败重试退避条件，并补NULL及非空抢占断言；支付模块单独复验，不重跑已通过商品模块。

第二次支付复验时，退款任务时间边界已通过，但原支付对账用例发生后台scheduling-1与测试主线程同时执行，导致markPaid调用计数为2（断言仍为1）。保留断言，为生产定时入口增加payment.reconcile.enabled（默认true），测试环境仅关闭自动调度，显式reconcile()与新增scheduledReconcile开关用例继续验证完整业务逻辑。没有通过关闭业务校验或放宽计数制造通过。
