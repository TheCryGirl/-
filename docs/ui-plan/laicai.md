## 3. 核心实现约束

### 表单、金额与请求
- 页面输入组件可能产生string、number、null等不同值，必须显式保持原payload类型。不得“顺手”加强密码/地址等业务规则。
- `isOk`处理写成功，`unwrapResult`处理读数据；成功data为空不等于失败。
- 所有金额保持后端分值，显示时除100；订单金额不能由UI组件的格式化字符串倒算。
- 原幂等键的生成/复用规则保持，不因重新渲染换key；若发现既有重试风险单独登记。

### 上传与弹窗
- 只有Profile、OrderDetail中原来确有上传的部分迁移；先记录FormData字段、类型/大小限制、返回结构。
- el-upload使用原有上传流程，不同时设置自动action和自定义上传造成双请求；失败保留表单，不把临时blob地址当后端地址。
- 确认取消返回false，必须提前return，不提交、不弹error。关闭弹窗清理校验状态，但不得误删已保存数据。

### 支付特别要求
- 本次不做支付渠道选择，不增加倒计时。OrderPay原代码只支持MOCK。
- 缺支付单与加载订单失败区分；创建失败不能继续模拟支付。
- 模拟支付传paymentId，不是payNo或orderId；成功后按原逻辑刷新并跳详情。
- loading防重复触发，不将UI“已支付”当后端状态更新的替代。

## 4. 手测步骤与期望

1. L01切换分类/搜索/排序，再清空：请求字段与改造前一致；无结果为empty，接口失败为error，重试保留条件。
2. 从L01打开yy商品详情，选SKU加购后进入L02：显示对应SKU，数量/价格正确；未登录沿用原登录跳转。
3. L02修改数量、勾选/全选、取消删除、确认删除：取消无请求；确认一次请求；失效条目不能被不当结算；单项失败不使金额假更新。
4. L03无地址、无可结算条目、有效地址三组：无效状态按原规则拦截；有效请求带真实addressId和cartItemIds；快速点击只提交一次。
5. L04未创建支付单、已创建待支付、已支付订单分别打开：不把code60001等业务失败包装当数据；按钮与真实状态一致。
6. 创建支付单失败、模拟支付失败、成功：失败恢复按钮且不跳成功页；成功的mock请求包含paymentId，详情状态由刷新取得。
7. L05筛选订单后进入L06并返回：ID正确、操作条件正确；未知状态保留文本，不误归“已完成”。
8. L06对每种现有操作各测成功/取消/业务拒绝；上传如存在则测合法文件、原限制拒绝、网络失败、只发一次请求。
9. L07修改资料、地址、原头像上传：提交字段不变，失败输入仍在；刷新后显示已保存值；Header同步沿用原机制。
10. L08申请售后、重复申请被拒绝、物流提交等原有路径：类型/订单ID/状态保持；后端拒绝不能显示成功；不新增上传入口。
11. 全链慢网络、401、HTTP200业务失败、断网各测一处代表场景；未测页面异常在PR中标出。

测试数据用开发账号和可重复商品/订单，不用真实收件人资料。涉及付款仅现有MOCK。
