## 四、L-05（并发同幂等键重复预占库存）专项验证

### 4.1 测试方法

用同一个 `Idempotency-Key` 并发发多个 `POST /api/orders`，检查是否产生多个订单 / 多次库存预占。

**第一轮**：8 并发
- 结果：8 个响应全部 `code=0`，**返回同一个 orderId**（`O20261102092828158ccee17d11`）
- 库存：`available=99, locked=1`（只扣 1）
- 预留单：仅新增 1 条

**第二轮（更严格）**：16 并发，用 barrier 让所有 curl 在同一时刻出发
- 结果：16 个响应全部 `code=0`，**仍返回同一个 orderId**（`O20261102092846143a61e010ef`）
- 库存：`available=99, locked=1`（只扣 1）
- 预留单：delta=1（基线 2 → 3，只增 1 条）
- 订单表：该买家只有 1 条订单

### 4.2 结论（重要）

**在本次测试条件下，L-05 未能复现。**

Issue #74 与实验四 L-05 记录的「并发同幂等键下单仍可能重复预占库存」，在 8 并发与 16 并发两轮测试中都**没有出现**。两次都是：同键请求收敛到同一订单号、库存只扣一次、预留单只建一条。

### 4.3 这个结论的边界（必须一并写明）

本结论**只能说明**「在容器化单实例 + 16 并发 + 该测试节奏下未复现」，不能证明缺陷不存在：

1. **未压到高并发**：16 并发、单机、单实例。真实竞争窗口可能在请求到达顺序更靠前的位置（例如幂等表唯一键插入前的读-判-写间隙），并发度不足时窗口不易撞上。
2. **未做多实例**：压缩部署若扩到多副本，幂等去重依赖数据库唯一键的行为需重新验证。
3. **未做时间维度复测**：只跑了两轮，没有长时间反复压。
4. **代码层面未审计**：本次仅做行为观测，未逐行核对 `OrderService` 里 `reserve` 的调用位置。

**建议表述**：把 Issue #74 / L-05 从「未修复的缺陷」改为「**已做行为验证未复现，代码层根因未确认**」，并注明测试条件。这样比原来「已知缺陷未修」更准确，也比「已修复」更诚实。

## 五、本次发现的问题（如实记录）

### 5.1 冷启动后商品库为空（**真问题，建议处理**）

`docker/docker-compose.yml` 的 `init-db.sql` 只创建五个空库，**没有任何种子数据**。而 `category` 表有数据（说明分类是服务启动时初始化的），`product` 表是空的。

**影响**：按 README 一键部署后打开前端，商品列表为空，**演示时第一屏就是空页面**。答辩现场如果没有提前手工造数据，会很难看。

**建议**：在 `init-db.sql` 或专门的 `seed.sql` 里补几条示例商品 + SKU（含库存），或在 README 里明确写出「部署后需先注册卖家、发商品、管理员审核」的准备步骤。

### 5.2 店铺创建接口字段名（脚本问题，非缺陷）

我第一次调用 `PUT /api/shops/mine` 传 `{"shopName": ...}` 返回「店铺名称不能为空」，实读 `ShopRequest.java` 后确认字段名是 `name`，改正后成功。**这是我的脚本写错，不是接口问题**，记录以免误导。

### 5.3 校验报错信息不够明确（已知，来自来财的总结）

账号长度校验返回「账号长度须为 4-20 位」是对的；但 `PUT /api/users/{id}/role` 在 userId 为空时返回 `code=500「系统繁忙，请稍后重试」`，把参数错误包装成了系统错误。**这是可以改进的点**，与来财个人总结里「报错信息也是契约的一部分」的体会一致。
