# 团队协作限制与分工约定

> **每个人动手前先读一遍本文。**
>
> 本项目是《软件工程实验》课程作业，老师评分的重要依据之一是「Git 提交记录能否体现协作过程」。下面的限制不是为了增加难度，而是让每个人的工作都留下可核对的痕迹——包括用 AI 辅助完成的部分。

---

## 一、绝对禁止的操作

这几条一旦违反，可能直接导致他人工作丢失或课程扣分。

### 1. 禁止直接在 main 分支改代码

```bash
# ❌ 错误
git checkout main
# 改代码...
git commit -m "改了点东西"
git push
```

```bash
# ✅ 正确
git checkout main && git pull
git checkout -b feature/12-order-create
# 改代码...
git commit -m "feat(order): 实现下单接口 (#12)"
git push -u origin feature/12-order-create
```

**为什么**：main 是所有人的基线。直接推上去，别人拉代码时会撞上你未完成的半成品，而且没有 PR 记录，老师看不到谁审查过。

### 2. 禁止 `git push --force`

**为什么**：强制推送会**覆盖远端历史**，把别人的提交冲掉。这是唯一一个会让队友工作量凭空消失的操作。

如果推送被拒绝（通常因为别人先推了），正确做法是：

```bash
git pull --rebase origin main
# 解决冲突
git push
```

### 3. 禁止多人同时修改同一个 `.docx`

**为什么**：Word/WPS 文件是二进制，Git 无法自动合并。两个人同时改，后推的人要么被拒绝、要么把先推的人的修改整个覆盖掉，而**双方都不会收到明显的警告**。

**做法**：
- 每份报告指定**一个文档负责人**；
- 其他人把内容写成 `.md` 或纯文本发给负责人，由负责人统一粘贴；
- 文档负责人改之前先 `git pull`，改完立刻 `git push`，不要攒。

### 4. 禁止提交口令、密钥、个人信息

`src/campusEasy/src/main/resources/application.yaml` 里数据库口令和 `JwtUtil.java` 里的 JWT 密钥**已经改成环境变量引用**，不要改回明文。

```yaml
# ✅ 保持这样
password: ${DB_PASSWORD:请设置本机数据库口令}
```

```java
// ✅ 保持这样
private static final String SECRET_KEY = System.getenv().getOrDefault("JWT_SECRET", "dev-only-secret");
```

仓库是**公开**的，推上去的任何内容都会被搜索引擎收录。发现有人误传了密钥，立刻告诉我，需要改代码 + 清理历史。

### 5. 禁止提交 `node_modules`、`target`、`dist`

`.gitignore` 已经配好了。如果发现 `git status` 里出现这些目录，说明 `.gitignore` 被改坏了。

### 6. 禁止在自己不负责的服务目录里改代码

见第三节的服务划分。要改别人负责的代码，先在对应 Issue 里说一声。

## 二、每次改动必须走完的流程

### 步骤

```
1. 建 Issue（要做什么）
2. 拉分支（在哪做）
3. 小步提交（做了什么）
4. 推分支 + 开 PR（请人看一眼）
5. 合入 main
6. 移动看板卡片
```

### 1. 建 Issue

超过半小时的工作都要建 Issue。标题说清楚要做什么。

```
✅ 实现订单下单接口与幂等令牌校验
✅ 设计库存预占的数据一致性方案
❌ 改一下
❌ 优化
```

建卡时选好 label（需求 / 设计 / 开发 / 测试 / 文档 / 部署）和 milestone（实验一到四）。

### 2. 拉分支

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 功能 | `feature/<Issue号>-<简短描述>` | `feature/12-order-create` |
| 修复 | `fix/<Issue号>-<简短描述>` | `fix/35-callback-dedupe` |
| 文档 | `docs/<简短描述>` | `docs/env-and-plan` |

### 3. 提交

**格式**：

```
<类型>(<范围>): <简短描述> (#Issue号)
```

| 类型 | 用在哪 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `style` | 格式调整，不影响逻辑 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 测试代码 |
| `chore` | 构建、依赖、配置 |

**示例**：

```
feat(order): 实现下单接口与幂等令牌校验 (#12)
fix(payment): 回调去重改为数据库唯一约束 (#35)
test(order): 增加并发下单100并发的测试用例 (#40)
docs(report): 补充设计规格说明书第三章 (#18)
```

**粒度**：一次提交只做一件事。如果提交信息里需要「和」「以及」连接两件不相关的事，拆开提交。

**禁止的写法**（会直接扣分，也无法体现工作内容）：

```
❌ update
❌ 修改
❌ 提交一下
❌ fix bug
❌ aaa
❌ 连续多个 update
```

### 4. 开 PR

PR 标题和 Issue 标题一致或相近，正文写：

```markdown
## 关联 Issue
Closes #12

## 改动内容
- 新增下单接口 POST /api/orders
- 实现幂等令牌校验

## 自测情况
- [x] 本地跑通完整下单流程
- [x] 重复提交同一令牌只创建一笔订单
```

**至少一名其他成员 approve 后合入。** 审查不用太严肃，花两三分钟看一眼有没有明显问题就行——但这两三分钟就是老师要看到的「协作」。

### 5. 移动看板

卡片从 Todo → In Progress → Done。**状态要真实**，不要代码写完了卡片还留在 Todo。

## 四、AI 辅助的使用限制

**AI 可以用，但有几条硬线。**

### 1. 必须人工审查

指导书原话：「AI 生成的代码、测试用例、模型初稿，必须经过人工审查、修改和验证，不得直接复制粘贴作为最终成果。」

具体来说：
- 用 AI 生成的代码，**你要能解释每一行为什么这么写**；
- 涉及业务逻辑（库存扣减、金额计算、状态流转）的，**必须自己推演一遍**；
- 跑通了再提交，不要「AI 说没问题」就推上来。

### 2. 必须记录使用情况

每个人在自己负责的模块里记下：

| 记什么 | 例子 |
| --- | --- |
| 用了什么工具 | DeepSeek Harness / Copilot / Cursor |
| 在哪个环节用 | 接口骨架生成 / 单测用例初稿 / 文档润色 |
| 做了什么修改 | AI 生成的幂等校验漏了并发场景，补了条件 UPDATE |
| 效果如何 | 接口骨架省了 1 小时，但业务逻辑仍需自己设计 |

这些记录最后汇总进报告的「AI 使用记录」章节（指导书要求不少于 300 字）。

### 3. 答辩要能解释

指导书原话：「答辩时需能解释所提交代码/模型的每一处设计决策，不得以『AI 生成的』作为无法解释的理由。」

如果答辩时说不出某个设计为什么这么定，这个设计就应该重新做一遍，而不是留在代码里。

### 4. 不要让 AI 直接操作仓库

**AI 工具不要直接执行 `git push`、不要直接改 `reports/` 下的 docx。** 所有提交由人工确认后推送——否则提交记录里的「作者」和实际动手的人对不上，互评数据就没有意义了。

## 五、冲突处理

### 推送被拒（non-fast-forward）

```bash
git pull --rebase origin main
# 如果有冲突，按提示逐个解决
git rebase --continue
git push
```

### 文本文件冲突

`.puml`、`.md`、`.java`、`.vue` 这类文件冲突时，Git 会在文件里标出：

```
<<<<<<< HEAD
你的版本
=======
别人的版本
>>>>>>> origin/main
```

打开文件，决定保留哪些内容（也可能两边的都要），删掉 `<<<<<<<`、`=======`、`>>>>>>>` 这些标记行，然后：

```bash
git add <冲突的文件>
git rebase --continue
```

**看不懂谁对谁错，先问对方**，不要随手选一个。

### 不小心提交了不该提交的东西

```bash
# 刚提交还没推送
git commit --amend

# 已经推送了
git revert <commit-hash>
```

**不要用 `git push --force` 去"清理"**。

## 六、提交前的自检清单

推代码前花 30 秒过一遍：

- [ ] 我是不是在**自己的分支**上？
- [ ] commit message 有没有**说清楚改了什么**、有没有带**Issue 号**？
- [ ] `git status` 里有没有**不该提交的文件**（node_modules、target、临时文件）？
- [ ] 有没有**硬编码的口令、密钥、密码**？
- [ ] 我改的代码在**我负责的范围**内吗？
- [ ] **能不能跑通**？（不能跑就别推，或者标注 WIP）
- [ ] 看板卡片**状态对不对**？

---

## 七、遇到问题怎么办

| 情况 | 做法 |
| --- | --- |
| 不知道某个功能该谁做 | 在 Issue 里 @ 组长 |
| 要改别人负责的服务 | 先在对应 Issue 里说一声，别直接动手 |
| Git 操作把东西搞乱了 | **先停手，不要继续乱试**，把 `git status` 和 `git log --oneline -5` 的输出发出来 |
| 推送一直失败 | 检查是否已接受仓库邀请、有没有配 SSH/HTTPS 凭证 |
| 不确定某操作会不会影响别人 | 先问，不要赌 |
